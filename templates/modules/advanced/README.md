# Расширенная заготовка модуля

Это расширенный каркас для модулей, которым нужны постоянные обработчики событий. Он дополняет, но не заменяет минимальный `basic`.

## Состав первой версии

- `install/index.php` — lifecycle установщика с защитой администратора и восстановлением после частичного сбоя; при неудачном восстановлении ранее зарегистрированный модуль остаётся зарегистрированным для следующей попытки.
- При ошибке удаления установщик восстанавливает ресурсы только этапов, завершившихся успешно до сбоя; сам сбойный этап не повторяется автоматически, чтобы не создавать дубликаты при неопределённом частичном результате.
- Методы `UnInstallFiles()`, `UnInstallAgents()` и `UnInstallEvents()` должны быть атомарными при ошибке либо самостоятельно компенсировать частичное выполнение. `UnInstallDB()` вызывается последним и также должен обеспечивать безопасное выполнение; автоматического отката пользовательских данных или down-миграций нет.
- Методы `InstallFiles()`, `InstallAgents()` и `InstallEvents()` должны быть идемпотентными, поскольку используются для компенсационного восстановления. `UnInstallDB()` должен самостоятельно обеспечивать безопасное выполнение: автоматического отката пользовательских данных или down-миграций нет.
- `include.php` — автозагрузка классов модуля.
- `lib/Event/EventRegistry.php` — единый список постоянных подписок EventManager.
- `lib/Event/ExampleEventHandler.php` — пример обработчика классического события `OnAfterUserAdd` с массивом полей по ссылке.
- `lib/Agent/ExampleAgent.php` и `lib/Agent/AgentRegistry.php` — пример фонового агента и его реестр.
- `install/migrations/` — явный реестр, контракт и runner внутренних миграций; первая миграция создаёт пример таблицы.

## Настройка

1. Замените `vendor.advancedmodule` на уникальный ID модуля.
2. Замените namespace `Vendor\\AdvancedModule` и имя класса установщика `vendor_advancedmodule`.
3. Измените карту автозагрузки в `include.php`.
4. В `EventRegistry::handlers()` укажите реальные события и обработчики вашего модуля.
5. Проверьте сигнатуры событий по документации именно той версии ядра Битрикс, которую поддерживает проект.

## Постоянные обработчики

Подписка на пример классического события `main:OnAfterUserAdd` регистрируется на этапе `InstallEvents()` через `EventManager::registerEventHandlerCompatible()`. При удалении она снимается через `unRegisterEventHandler()`.

Параметры подписки хранятся в одном реестре и используются обеими операциями. Не меняйте параметры регистрации отдельно от снятия. `addEventHandler()` здесь не используется: он регистрирует обработчик только на текущий запрос.

`OnAfterUserAdd` относится к классическому API: ядро передаёт массив полей пользователя по ссылке, поэтому обработчик принимает `array &$fields` и подписывается через `registerEventHandlerCompatible()`. Для новых D7-событий используйте `registerEventHandler()` и тип `Bitrix\\Main\\Event`; не применяйте этот контракт к legacy-событиям.

## Фоновые агенты

Реестр проверяет точное имя вызова, ID модуля и системный USER_ID до регистрации, поэтому повторный запуск не создаёт дубликат. Callback возвращает строку следующего вызова через `__METHOD__ . '();'` без ведущего обратного слеша. При удалении вызывается `CAgent::RemoveAgent()` с теми же идентификаторами, затем результат проверяется через `CAgent::GetList()`: метод удаления не возвращает статус. Снятие регистрации модуля дополнительно удаляет оставшихся агентов этого модуля.

Пример не выполняет тяжёлую работу. Замените тело метода агента своей ограниченной по времени задачей.

## Внутренние миграции БД

`InstallDB()` запускает `MigrationRunner` по явному списку `MigrationRegistry` как при первой установке, так и при повторном вызове процедуры установки уже установленного модуля. При повторном вызове обновляется только схема: события, агенты и файлы исправной установки не переустанавливаются. Это позволяет применить ожидающие миграции после развёртывания новой версии модуля. ID миграции имеет формат timestamp + имя и после применения не меняется. Runner сохраняет SHA-256 файла миграции в ledger `b_vendor_advancedmodule_migrations`; изменение уже применённого файла приводит к ошибке — исправление оформляйте новой миграцией.

Runner использует `Bitrix\\Main\\Application::getConnection()`, `Connection::createTable()`, `Connection::add()` и именованную блокировку `Connection::lock()`. Первая версия намеренно поддерживает только штатную `Bitrix\\Main\\DB\\MysqliConnection` с MySQL: актуальная документация Bitrix описывает именованные блокировки как поддерживаемые только MySQL. PostgreSQL и пользовательские драйверы отклоняются до любых изменений БД.

Получение блокировки выполняется до создания или проверки ledger: даже первое создание служебной таблицы защищено от параллельного запуска.

Каждая миграция сама объявляет транзакционность. DDL-пример намеренно нетранзакционный: поведение DDL зависит от СУБД и движка таблиц. Нетранзакционные миграции обязаны быть безопасны при повторном запуске после частичного сбоя. Ledger фиксирует миграцию только после её успешного выполнения.

SiteUpdate updater выполняется до копирования файлов пакета, поэтому он не должен напрямую вызывать новые классы runner, которых ещё нет на сайте. После доставки runtime-файлов вызовите `InstallDB()` из контролируемой процедуры обновления/развёртывания либо повторно запустите установочную процедуру модуля. Uninstall не удаляет ledger и таблицу примера: данные сохраняются по умолчанию. Down-миграций и автоматического удаления данных нет. Перед применением миграций на рабочем сайте делайте резервную копию и проверяйте изменения на тестовом окружении.

Официальные API: [Connection](https://docs.1c-bitrix.ru/pages/api-reference/main/db/connection/index.html), [createTable](https://docs.1c-bitrix.ru/pages/api-reference/main/db/connection/create-table.html), [lock](https://docs.1c-bitrix.ru/pages/api-reference/main/db/connection/lock.html), [транзакции](https://docs.1c-bitrix.ru/pages/database/transactions.html).

## SiteUpdate / Marketplace updater

Отдельный пример пакета обновления находится в `docs/examples/marketplace-updater/package/`; это не runtime-каталог модуля. В нём есть обязательные `install/version.php` и `description.ru`, а также один корневой `updater.php`.

Updater проверяет `IsModuleInstalled()`, затем использует только штатный `$updater->CopyFiles()`. Он не обращается к классам текущей версии модуля: SiteUpdate выполняет updater до копирования файлов пакета. Повторный запуск приводит к тому же содержимому файлов. Внутренний MigrationRunner здесь не вызывается.

Подробности и ограничения — в [примере пакета обновления](../../../docs/examples/marketplace-updater/README.md).

## Проверка на реальном ядре

Полный сценарий интеграционной проверки на реальном ядре Bitrix и MySQL описан в [протоколе интеграционной проверки](../../../docs/testing/advanced-module-integration.md). Выполняйте его только на отдельном тестовом сайте с резервной копией.

## Ограничения

- Автономные smoke tests проверяют собственную логику на заглушках API, но не заменяют установку на реальном ядре.
- Перед публикацией модуля проверьте install, повторный install, uninstall и повторный uninstall на тестовом сайте.
