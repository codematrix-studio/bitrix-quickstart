# D7-компонент с AJAX-действиями

Заготовка использует `CBitrixComponent` и контракт `Controllerable` для вызова действий через `BX.ajax.runComponentAction()`.

## Перед использованием

1. Скопируйте каталог в собственный компонент, например `local/components/project/ajax.example/`.
2. Переименуйте `ProjectAjaxComponent` и описание компонента.
3. Реализуйте `canSubmit()`. Сейчас метод всегда возвращает `false`: это намеренное поведение fail closed, чтобы незаполненная заготовка не предоставляла доступ к действию.
4. В `submitAction()` реализуйте прикладную логику. Повторно проверяйте права на каждый объект, который передан в запросе. Нельзя полагаться только на то, что пользователь авторизован.
5. Если действие меняет данные, оставьте POST и CSRF-фильтр включёнными. Не переводите изменение состояния на GET.
6. Возвращайте массив данных, а не готовую HTML-строку. Экранируйте значения в клиентском коде в момент вывода в DOM.

## Пример вызова

```javascript
BX.ajax.runComponentAction('project:ajax.example', 'submit', {
    mode: 'class',
    data: {
        message: 'Проверочное сообщение'
    }
}).then(function (response) {
    // response.data — сериализованный результат действия.
    // Для вывода пользовательских данных используйте textContent, а не innerHTML.
    console.log(response.data);
}).catch(function (error) {
    // Не показывайте пользователю технические детали и трассировки.
    console.error('Не удалось выполнить AJAX-действие', error);
});
```

Bitrix передаёт sessid для штатной проверки CSRF в AJAX-вызове. Не отключайте фильтр `Csrf` и не подменяйте его ручной проверкой только на клиенте.

## Меры безопасности

- `HttpMethod` разрешает только POST.
- `Csrf` проверяет токен сессии.
- `CurrentUser` используется для получения текущего пользователя.
- `canSubmit()` по умолчанию запрещает действие. Реализуйте проверку ролей, групп и прав на конкретную сущность.
- Входные данные проверяются на тип и длину. Это пример минимальной проверки, а не универсальная валидация предметной области.
- Не принимайте идентификатор пользователя из запроса как основание для проверки доступа: используйте текущего пользователя и проверяйте владение/доступ к целевому объекту на сервере.
- Не возвращайте секреты, внутренние пути, SQL, исключения или отладочные трассировки.
- Не вставляйте ответ в DOM через `innerHTML` без контекстного экранирования.

## Ограничения примера

`submitAction()` не записывает данные и не запускает бизнес-операции. Она только демонстрирует структуру защищённого действия и возвращает признак успешной проверки. Перед эксплуатацией замените её прикладной реализацией и добавьте тесты на гостя, пользователя без прав, неверный CSRF-токен, GET-запрос, некорректные входные данные и доступ к чужому объекту.

Фильтры и интеграцию `Controllerable` необходимо проверить на фактической версии ядра Битрикс. Автономная проверка синтаксиса PHP не является интеграционным тестом.
