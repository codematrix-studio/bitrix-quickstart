# Работа с highload-блоками

Для работы с HL-блоками используется отдельный слой `Project\Bitrix\HLBlock`. Он получает метаданные через штатный `HighloadBlockTable`, компилирует ORM-сущность и предоставляет методы для чтения и изменения записей.

Классы не подключают модуль `highloadblock` при загрузке PHP-файла. Модуль проверяется непосредственно перед получением HL-блока.

## Получение HL-блока

Передайте ID существующего highload-блока:

```php
use Project\Bitrix\HLBlock\HlBlockManager;

$manager = new HlBlockManager();
$hlBlock = $manager->getById(12);
```

Если модуль не установлен, блок не найден или ORM-сущность не может быть скомпилирована, будет выброшено `RuntimeException`.

## Чтение записей

### Получение списка

```php
$items = $hlBlock->getList([
    'select' => ['ID', 'UF_NAME', 'UF_XML_ID'],
    'filter' => ['=UF_ACTIVE' => 1],
    'order' => ['ID' => 'ASC'],
    'limit' => 20,
]);

while ($item = $items->fetch()) {
    // Обработка записи.
}
```

Параметры передаются напрямую в штатный `DataManager::getList()`. Доступны возможности D7 ORM: `select`, `filter`, `order`, `limit`, `offset`, `runtime` и другие параметры ядра.

### Получение записи по ID

```php
$item = $hlBlock->getById(15);

if ($item !== null) {
    $name = $item['UF_NAME'];
}
```

Метод возвращает массив записи или `null`, если запись не найдена.

### Поиск по внешнему коду

```php
$item = $hlBlock->findByXmlId('external-123');
```

Метод использует поле `UF_XML_ID`. Вызывайте его только для HL-блоков, в которых такое пользовательское поле существует.

## Добавление, обновление и удаление

```php
$addResult = $hlBlock->add([
    'UF_NAME' => 'Новая запись',
    'UF_XML_ID' => 'external-123',
]);

if ($addResult->isSuccess()) {
    $newId = $addResult->getId();
} else {
    $errors = $addResult->getErrorMessages();
}

$updateResult = $hlBlock->update(15, [
    'UF_NAME' => 'Обновлённое название',
]);

$deleteResult = $hlBlock->delete(15);
```

Методы возвращают штатные объекты результатов ORM Bitrix (`AddResult`, `UpdateResult`, `DeleteResult`). Проверяйте `isSuccess()` и обрабатывайте ошибки вызывающего кода.

Класс проверяет корректность ID и запрещает пустые наборы полей при добавлении и обновлении. Проверка существования записи перед обновлением или удалением остаётся ответственностью ORM и вызывающего кода.

## Устройство слоя

- `HlBlockManager` — публичная точка входа;
- `HlBlockRepository` — получение и проверка метаданных, компиляция и кеширование ORM-класса;
- `HlBlockEntity` — операции чтения и записи для конкретного HL-блока.

Репозиторий кеширует метаданные и скомпилированные ORM-классы в пределах своего экземпляра. Для долгоживущих процессов это позволяет не компилировать одну сущность повторно.

ID используется как основной идентификатор HL-блока. Поле `NAME` не трактуется как символьный код: в штатном API Bitrix это название блока, и оно не гарантирует уникальность технического кода.

## Автономное тестирование

Зависимости репозитория (`moduleLoader`, `metadataLoader`, `entityCompiler`) можно передать через конструктор. Это позволяет проверять поведение без ядра Битрикс и без реальной базы данных.

```bash
cd local
composer test:hlblock
```

Автономные тесты не заменяют интеграционную проверку на установленном ядре Bitrix. Перед использованием на рабочем сайте необходимо проверить выборку, добавление, изменение и удаление на целевой версии модуля `highloadblock`.
