# Быстрый заказ D7 Sale

## Назначение

Быстрый заказ — отдельный сценарий оформления покупки одного выбранного товара без предварительного помещения товара в постоянную корзину покупателя. Он не заменяет обычное оформление заказа и не должен менять содержимое уже существующей корзины.

Старый `Helper\\BuyOneClickHandler` подтверждает именно товарный сценарий: его метод `CreateOrder($productId, $userId)` создаёт новую временную корзину и добавляет в неё одну позицию. Однако старый обработчик сломан на уровне передачи аргументов: `Execute()` вызывает `Buy($this->email, $this->phone)`, хотя `Buy()` ожидает ID товара и купон.

## Найденные дефекты старой реализации

- Email и телефон читаются из GET, хотя это персональные данные и действие создаёт заказ.
- В `Execute()` вместо ID товара и купона передаются email и телефон.
- При отсутствии пользователя создаётся аккаунт без согласованного сценария регистрации.
- Пароль вычисляется как MD5 от email; это предсказуемый секрет и небезопасный способ создания учётных данных.
- При отсутствии email генерируется фиктивный адрес.
- Поиск пользователя объединяет фильтры email и телефона через AND; поведение при совпадении разных пользователей не определено.
- ID инфоблока, типа плательщика, службы доставки и платёжной системы зашиты в коде.
- Цена и валюта читаются из полей элемента вместо штатного провайдера каталога.
- Результаты создания позиции корзины, назначения полей и сохранения заказа проверяются неполно.
- Купон применяется после сохранения заказа; повторный расчёт скидки не сопровождается надёжным сохранением обновлённого заказа.
- Обработчик подключает prolog самостоятельно, смешивая инфраструктуру приложения и бизнес-логику.

## Принятые решения для новой реализации

1. Быстрый заказ принимает идентификатор товара и количество. Значения email, телефона и дополнительных полей принимаются только из POST после серверной проверки.
2. Идентификатор товара и количество валидируются на сервере. Цена, валюта, название, доступность и ограничения покупки берутся из каталога/провайдера Bitrix, а не из запроса браузера.
3. Временная корзина создаётся отдельно от постоянной корзины FUSER. Быстрый заказ не должен добавлять товар в существующую корзину или очищать её.
4. Первая версия работает только для авторизованного пользователя. Гость получает понятную ошибку/ответ с указанием, что оформление для гостя пока не поддерживается. Нельзя создавать технического пользователя, угадывать существующий аккаунт по телефону/email или генерировать фиктивные адреса.
5. Тип плательщика, свойства заказа, доставка и оплата задаются конфигурацией конкретного сайта/вызывающего приложения. Никаких универсальных ID в библиотеке.
6. Email и телефон проверяются по настроенным свойствам заказа и правилам приложения. Само наличие контакта не является основанием для входа в чужой аккаунт.
7. Купон обрабатывается до финального расчёта заказа в контексте конкретного заказа/корзины. Если API конкретной версии Sale не позволяет безопасно применить купон до сохранения, сценарий должен завершаться ошибкой, а не сохранять заказ с неверной суммой.
8. Сервис не запускает платёжный обработчик, не отмечает оплату оплаченной, не отправляет письма и не создаёт пользователя.
9. HTTP/AJAX-обработчик, CSRF-проверка, ограничение частоты запросов и формат JSON-ответа остаются уровнем приложения. Библиотечный сервис не читает глобальные `$_GET`, `$_POST` и не выводит JSON.

## Архитектура

Предлагаемые роли:

- `QuickOrder` — сценарий быстрого заказа: проверяет входные значения, получает товарную позицию через адаптер каталога, создаёт временную корзину и передаёт её на оформление.
- `OrderManager` — общая логика создания заказа: тип плательщика, свойства, отгрузка, оплата, финальный расчёт и сохранение.
- Адаптер каталога — получает проверяемые данные товара и формирует позицию временной корзины штатным механизмом Bitrix.
- HTTP/AJAX-обработчик проекта — проверяет метод POST, CSRF, авторизацию и ограничения частоты запросов, затем вызывает сервис.

### Необходимое изменение OrderManager

Текущий `OrderManager::create()` всегда загружает постоянную корзину пользователя. Этого недостаточно для быстрого заказа: передача товара в текущую корзину с последующим оформлением изменит состояние корзины пользователя.

Поэтому до реализации `QuickOrder` нужно добавить в `OrderManager` отдельный публичный метод создания заказа из явно переданной временной корзины. Существующий `create()` должен сохранить прежнюю сигнатуру и поведение для обратной совместимости. Общую часть создания заказа следует вынести во внутренний метод, который принимает уже проверенную корзину. Временная корзина должна быть создана и заполнена вызывающим сценарием, а не загружаться по FUSER.

Так как PR с `OrderManager` ещё является отдельным изменением, эта работа оформляется как stacked PR: ветка быстрого заказа основана на `feature/d7-order-manager`, а PR направляется в эту ветку до слияния базового PR. После слияния базового PR целевой base быстрого заказа можно будет переключить на `main`.

## Что пока не реализуем

- Гостевой заказ и автоматическую регистрацию.
- Поиск аккаунта по email/телефону и автоматический вход.
- Отправку SMS/email и уведомлений.
- Автоматический выбор доставки и оплаты.
- Запуск платёжных систем.
- Применение купонов после сохранения заказа.
- Перенос старого `BuyOneClickHandler` или его зависимостей без переработки.

## Проверки

Автономные тесты должны подтвердить:

- временная корзина содержит только запрошенный товар и количество;
- постоянная корзина пользователя не загружается, не изменяется и не очищается;
- недопустимый ID товара и количество отклоняются;
- неавторизованный пользователь отклоняется до создания заказа;
- значения цены/валюты из клиентского запроса игнорируются;
- свойства заказа задаются по символьным кодам;
- ошибки каталога, корзины, расчёта скидок и сохранения заказа не маскируются;
- обычный `OrderManager::create()` сохраняет обратную совместимость.

Интеграционные тесты на реальном ядре Битрикс и настройках конкретного магазина обязательны перед использованием в production, но не могут быть заменены автономными тестами.

## Реализация

Добавлен сервис `Project\\Bitrix\\Sale\\QuickOrder`. Он создаёт отдельную корзину D7, добавляет в неё одну позицию через `catalog` и `CCatalogProductProvider`, а затем вызывает `OrderManager::createFromBasket()`.

Пример:

```php
use Project\\Bitrix\\Sale\\OrderManager;
use Project\\Bitrix\\Sale\\QuickOrder;

$quickOrder = new QuickOrder(new OrderManager());

$orderId = $quickOrder->create(
    productId: 123,
    quantity: 1,
    userId: $currentUserId,
    personTypeId: $personTypeId,
    propertyValues: [
        'EMAIL' => 'buyer@example.com',
        'PHONE' => '+7 900 000-00-00',
    ]
);
```

Сервис не принимает цену и валюту товара. Валюта берётся из базовой валюты проекта, а цена и доступность должны быть рассчитаны штатным провайдером каталога при пересчёте временной корзины. Временная корзина создаётся внутри сервиса на каждый вызов и не сохраняется отдельно как корзина FUSER.

## Границы ответственности

Вызывающий код до вызова сервиса обязан проверить авторизацию текущего пользователя и убедиться, что переданный `USER_ID` принадлежит текущей сессии. Также на уровне приложения проверяются POST, CSRF, ограничения частоты запросов, контактные данные и допустимость покупки товара. Одного положительного `USER_ID` недостаточно для авторизации запроса.

В первой версии сервис создаёт заказ только для зарегистрированного пользователя. Он не ищет пользователя по email/телефону и не создаёт учётные записи.

## Автономные проверки

Из каталога `local`:

```bash
composer test:d7-quick-order
```

Проверяются серверные поля позиции, передача временной корзины, параметры заказа и отклонение некорректного ID товара, количества и пользователя. Проверка реальной цены, остатков, ограничений каталога и совместимости с настройками магазина требует интеграционного теста на установленном ядре Битрикс.
