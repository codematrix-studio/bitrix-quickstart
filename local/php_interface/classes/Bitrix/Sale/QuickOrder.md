# Быстрый заказ D7 Sale

## Назначение

Быстрый заказ — отдельный сценарий оформления покупки одного выбранного товара без предварительного помещения товара в постоянную корзину покупателя. Он не заменяет обычное оформление заказа и не должен менять содержимое уже существующей корзины.

Старый `Helper\BuyOneClickHandler` подтверждает именно товарный сценарий: его метод `CreateOrder($productId, $userId)` создаёт новую временную корзину и добавляет в неё одну позицию. Однако старый обработчик сломан на уровне передачи аргументов: `Execute()` вызывает `Buy($this->email, $this->phone)`, хотя `Buy()` ожидает ID товара и купон.

## Найденные дефекты старой реализации

- Email и телефон читаются из GET, хотя это персональные данные и действие создаёт заказ.
- В `Execute()` вместо ID товара и купона передаются email и телефон.
- При отсутствии пользователя создаётся аккаунт без согласованного сценария регистрации.
- Пароль вычисляется как MD5 от email; это предсказуемый секрет и небезопасный способ создания учётных данных.
- При отсутствии email генерируется фиктивный адрес.
- Поиск пользователя объединяет фильтры email и телефона через AND; поведение при совпадении разных пользователей не определено.
- ID инфоблока, типа плательщика, службы доставки и платёжной системы зашиты в коде.
- Цена и валюта читаются из полей элемента вместо штатного провайдера каталога.
- Результаты создания позиции корзины, назначения полей и сохранения заказа проверяются неполно.
- Купон применяется после сохранения заказа; повторный расчёт скидки не сопровождается надёжным сохранением обновлённого заказа.
- Обработчик подключает prolog самостоятельно, смешивая инфраструктуру приложения и бизнес-логику.

## Принятые решения для новой реализации

1. Быстрый заказ принимает идентификатор товара и количество. Значения email, телефона и дополнительных полей принимаются только из POST после серверной проверки.
2. Идентификатор товара и количество валидируются на сервере. Цена, валюта, название, доступность и ограничения покупки берутся из каталога/провайдера Bitrix, а не из запроса браузера.
3. Временная корзина создаётся отдельно от постоянной корзины FUSER. Быстрый заказ не должен добавлять товар в существующую корзину или очищать её.
4. Первая версия работает только для авторизованного пользователя. Гость получает понятную ошибку/ответ с указанием, что оформление для гостя пока не поддерживается. Нельзя создавать технического пользователя, угадывать существующий аккаунт по телефону/email или генерировать фиктивные адреса.
5. Тип плательщика, свойства заказа, доставка и оплата задаются конфигурацией конкретного сайта/вызывающего приложения. Никаких универсальных ID в библиотеке.
6. Email и телефон проверяются по настроенным свойствам заказа и правилам приложения. Само наличие контакта не является основанием для входа в чужой аккаунт.
7. Купон обрабатывается до финального расчёта заказа в контексте конкретного заказа/корзины. Если API конкретной версии Sale не позволяет безопасно применить купон до сохранения, сценарий должен завершаться ошибкой, а не сохранять заказ с неверной суммой.
8. Сервис не запускает платёжный обработчик, не отмечает оплату оплаченной, не отправляет письма и не создаёт пользователя.
9. HTTP/AJAX-обработчик, CSRF-проверка, ограничение частоты запросов и формат JSON-ответа остаются уровнем приложения. Библиотечный сервис не читает глобальные `$_GET`, `$_POST` и не выводит JSON.

## Архитектура

Предлагаемые роли:

- `QuickOrder` — сценарий быстрого заказа: проверяет входные значения, получает товарную позицию через адаптер каталога, создаёт временную корзину и передаёт её на оформление.
- `OrderManager` — общая логика создания заказа: тип плательщика, свойства, отгрузка, оплата, финальный расчёт и сохранение.
- Адаптер каталога — получает проверяемые данные товара и формирует позицию временной корзины штатным механизмом Bitrix.
- HTTP/AJAX-обработчик проекта — проверяет метод POST, CSRF, авторизацию и ограничения частоты запросов, затем вызывает сервис.

### Интеграция с OrderManager

Текущий `OrderManager::create()` всегда загружает постоянную корзину пользователя. Этого недостаточно для быстрого заказа: передача товара в текущую корзину с последующим оформлением изменит состояние корзины пользователя.

Для этого в `OrderManager` добавлен отдельный публичный метод `createFromBasket()`. Существующий `create()` сохраняет прежнюю сигнатуру и поведение. Общая часть создания заказа использует подготовленную корзину; постоянная корзина FUSER не загружается.

Так как PR с `OrderManager` ещё является отдельным изменением, эта работа оформляется как stacked PR: ветка быстрого заказа основана на `feature/d7-order-manager`, а PR направляется в эту ветку до слияния базового PR. После слияния базового PR целевой base быстрого заказа можно будет переключить на `main`.

## Что пока не реализуем

- Гостевой заказ и автоматическую регистрацию.
- Поиск аккаунта по email/телефону и автоматический вход.
- Отправку SMS/email и уведомлений.
- Автоматический выбор доставки и оплаты.
- Запуск платёжных систем.
- Применение купонов после сохранения заказа.
- Перенос старого `BuyOneClickHandler` или его зависимостей без переработки.

## Проверки

Автономные тесты должны подтвердить:

- временная корзина содержит только запрошенный товар и количество;
- постоянная корзина пользователя не загружается, не изменяется и не очищается;
- недопустимый ID товара и количество отклоняются;
- неавторизованный пользователь отклоняется до создания заказа;
- значения цены/валюты из клиентского запроса игнорируются;
- свойства заказа задаются по символьным кодам;
- ошибки каталога, корзины, расчёта скидок и сохранения заказа не маскируются;
- обычный `OrderManager::create()` сохраняет обратную совместимость.

Интеграционные тесты на реальном ядре Битрикс и настройках конкретного магазина обязательны перед использованием в production, но не могут быть заменены автономными тестами.

## Реализация

Добавлен сервис `Project\Bitrix\Sale\QuickOrder`. Он создаёт отдельную корзину D7, добавляет в неё одну позицию через стандартный провайдер `Bitrix\Catalog\Product\Basket::getDefaultProviderName()`, а затем вызывает `OrderManager::createFromBasket()`. Передаваемый `productId` должен быть ID продаваемой записи каталога или конкретного торгового предложения, а не ID родительской карточки с SKU.

Пример:

```php
use Project\Bitrix\Sale\OrderManager;
use Project\Bitrix\Sale\QuickOrder;

$quickOrder = new QuickOrder(new OrderManager());

$orderId = $quickOrder->create(
    productId: 123,
    quantity: 1,
    userId: $currentUserId,
    personTypeId: $personTypeId,
    propertyValues: [
        'EMAIL' => 'buyer@example.com',
        'PHONE' => '+7 900 000-00-00',
    ]
);
```

Сервис не принимает и не задаёт вручную цену или валюту товара. Стандартный провайдер каталога получает эти значения из настроек товара и каталога при пересчёте временной корзины. Имя провайдера запрашивается через API Битрикс, а не зашивается в код. Временная корзина создаётся внутри сервиса на каждый вызов и не сохраняется отдельно как корзина FUSER.

## Границы ответственности

Вызывающий код до вызова сервиса обязан проверить авторизацию текущего пользователя и убедиться, что переданный `USER_ID` принадлежит текущей сессии. Также на уровне приложения проверяются POST, CSRF, ограничения частоты запросов, контактные данные и допустимость покупки товара. Одного положительного `USER_ID` недостаточно для авторизации запроса.

В первой версии сервис создаёт заказ только для зарегистрированного пользователя. Он не ищет пользователя по email/телефону и не создаёт учётные записи.

## Автономные проверки

Из каталога `local`:

```bash
composer test:d7-quick-order
```

Проверяются количество и стандартный провайдер позиции, передача временной корзины, параметры заказа и отклонение некорректного ID товара, количества и пользователя. Проверка реальной цены, остатков, ограничений каталога и совместимости с настройками магазина требует интеграционного теста на установленном ядре Битрикс.


## Сверка с документацией Битрикс

Реализация сверена с официальным сценарием создания заказа из несохранённой корзины:

- [Создание заказа: временная корзина и провайдер каталога](https://docs.1c-bitrix.ru/pages/modules/sale/order-create.html)
- [Работа с корзиной](https://docs.1c-bitrix.ru/pages/modules/sale/basket.html)

Для товара каталога используется `Bitrix\Catalog\Product\Basket::getDefaultProviderName()`. Цена и валюта не задаются вручную: их рассчитывает провайдер при `Basket::refresh()`. Корзина создаётся в памяти через `Basket::create($siteId)`, отдельно не сохраняется и передаётся в новый заказ.


## Предупреждения при сохранении заказа

Bitrix может вернуть успешный результат `Order::save()` вместе с предупреждениями. В таком случае `OrderManager` выбрасывает `OrderSaveWarningsException`, поскольку простой возврат ID скрыл бы потенциально неполное сохранение.

Исключение означает, что заказ уже сохранён. Получите ID через `getOrderId()`, список предупреждений — через `getWarnings()`. Не повторяйте создание заказа автоматически: сначала проверьте сохранённый заказ.


## Граница HTTP/AJAX-интеграции

В старом репозитории найден только один вызов `paramsToModal.buyOneClick($(this))` в `js_examples.js`. Поиск по всему репозиторию не обнаружил реализацию `paramsToModal`, вызовы `BuyOneClickHandler` или общий диспетчер обработчиков. Сам `BaseHandler` содержит только абстрактные `__construct()` и `Execute()`. Поэтому прежний URL, HTTP-метод и формат полезной нагрузки восстановить нельзя.

Для нового сайта предлагается следующий контракт. Это проектное соглашение, а не уже созданный endpoint:

- только POST; GET-запрос не должен создавать заказ;
- CSRF проверяется штатным механизмом сессии Битрикс;
- пользователь берётся из текущей авторизованной сессии, а не из POST;
- `productId` и `quantity` проверяются на сервере; ID должен относиться к продаваемому товару каталога или выбранному SKU;
- тип плательщика и свойства заказа берутся из конфигурации сайта; контакты принимаются из POST и валидируются по правилам конкретного сайта;
- доставка и оплата либо задаются конфигурацией, либо выбираются пользователем из серверного списка; переданный ID всё равно проверяется ограничениями Sale;
- повторная отправка защищается idempotency key или серверным ограничением частоты запросов;
- ответ возвращается в JSON, а подробности внутренних исключений не раскрываются клиенту;
- при `OrderSaveWarningsException` ответ должен сообщать, что заказ уже создан, и включать его ID. Клиент не должен повторять создание автоматически.

Реализовывать endpoint и JS-вызов имеет смысл после определения конфигурации конкретного сайта: URL обработчика, типа плательщика, обязательных свойств и того, откуда форма получает товар/SKU. В библиотечном сервисе эти настройки не зашиваются.

## Проверка входных данных HTTP/AJAX

Добавлен `Project\Bitrix\Sale\QuickOrderInput`. Он принимает массив параметров запроса, проверяет `productId` и `quantity` и возвращает DTO только с этими двумя значениями.

```php
use Project\Bitrix\Sale\QuickOrderInput;

$input = QuickOrderInput::fromPayload([
    'productId' => $request->getPost('productId'),
    'quantity' => $request->getPost('quantity'),
]);
```

Строковый ID допускается, только если состоит из положительных десятичных цифр и помещается в `int`. Количество может быть целым или дробным; ноль, отрицательные, нечисловые, `INF` и `NAN` отклоняются. Верхний предел количества определяется правилами магазина.

DTO намеренно не содержит `userId`. Контроллер получает идентификатор пользователя из `Bitrix\Main\Engine\CurrentUser`, а не из POST.

Автономная проверка: `composer test:d7-quick-order-input`.

## Пример AJAX-контроллера в модуле сайта

Библиотека не регистрирует универсальный контроллер и не создаёт endpoint. Контроллер размещается в модуле конкретного сайта: идентификатор модуля, namespace, настройки типа плательщика и коды свойств зависят от проекта.

Ниже — каркас действия. Замените `My\Shop`, `my.shop`, получение настроек и проверку контактов на реализацию своего модуля. Не используйте условные ID настроек в production.

```php
<?php

declare(strict_types=1);

namespace My\Shop\Controller;

use Bitrix\Main\Engine\ActionFilter\HttpMethod;
use Bitrix\Main\Engine\Controller;
use Bitrix\Main\Engine\CurrentUser;
use Bitrix\Main\Error;
use InvalidArgumentException;
use Project\Bitrix\Sale\OrderManager;
use Project\Bitrix\Sale\OrderSaveWarningsException;
use Project\Bitrix\Sale\QuickOrder;
use Project\Bitrix\Sale\QuickOrderInput;
use Throwable;

final class QuickOrderController extends Controller
{
    public function configureActions(): array
    {
        return [
            'create' => [
                // Заменяем только общий фильтр метода; Authentication и Csrf остаются.
                '-prefilters' => [HttpMethod::class],
                '+prefilters' => [new HttpMethod([HttpMethod::METHOD_POST])],
            ],
        ];
    }

    public function createAction(
        mixed $productId,
        mixed $quantity = 1,
        CurrentUser $currentUser
    ): ?array {
        $userId = (int) $currentUser->getId();
        if ($userId < 1) {
            $this->addError(new Error('Для быстрого заказа необходимо войти на сайт.', 'AUTH_REQUIRED'));
            return null;
        }

        try {
            $input = QuickOrderInput::fromPayload([
                'productId' => $productId,
                'quantity' => $quantity,
            ]);

            // Ограничение частоты, идемпотентность, проверка товара и контактов — здесь.
            // Не принимайте USER_ID, personTypeId, цену или валюту из запроса.
            $personTypeId = $this->getConfiguredPersonTypeId();
            $propertyValues = $this->buildValidatedPropertyValues();

            $orderId = $this->createQuickOrder()->create(
                productId: $input->productId,
                quantity: $input->quantity,
                userId: $userId,
                personTypeId: $personTypeId,
                propertyValues: $propertyValues,
            );

            return ['created' => true, 'orderId' => $orderId];
        } catch (OrderSaveWarningsException $exception) {
            // Заказ уже сохранён: повторять создание автоматически нельзя.
            $this->addError(new Error('Заказ создан, но Битрикс вернул предупреждения.', 'ORDER_SAVED_WITH_WARNINGS'));
            return [
                'created' => true,
                'orderId' => $exception->getOrderId(),
                'warnings' => $exception->getWarnings(),
            ];
        } catch (InvalidArgumentException $exception) {
            $this->addError(new Error($exception->getMessage(), 'INVALID_ORDER_DATA'));
            return null;
        } catch (Throwable $exception) {
            // Подробности исключения запишите в серверный журнал, не раскрывая клиенту.
            $this->addError(new Error('Не удалось оформить заказ.', 'ORDER_CREATE_FAILED'));
            return null;
        }
    }

    private function createQuickOrder(): QuickOrder
    {
        // Передайте конфигурацию и адаптеры конкретного сайта.
        return new QuickOrder(new OrderManager());
    }

    private function getConfiguredPersonTypeId(): int
    {
        // Получите ID типа плательщика из настроек модуля/сайта.
        throw new \LogicException('Реализуйте получение типа плательщика из настроек сайта.');
    }

    private function buildValidatedPropertyValues(): array
    {
        // Верните только разрешённые коды свойств после проверки контактов.
        throw new \LogicException('Реализуйте проверку контактных данных сайта.');
    }
}
```

Пример вызова из JS (замените идентификатор действия на зарегистрированный в своём модуле):

```javascript
BX.ajax.runAction('my:shop.QuickOrderController.create', {
    data: { productId: 123, quantity: 1 }
}).then(function (response) {
    // Успех: response.data.orderId
}).catch(function (response) {
    // Ошибка: response.errors
});
```

`BX.ajax.runAction()` передаёт CSRF-токен штатным заголовком. Для изменяющего состояние действия оставьте авторизацию, CSRF и POST-only. `Authentication` проверяет факт входа, но не права на дополнительные объекты — их проверяйте отдельно.

Регистрация namespace контроллера, `defaultNamespace` в `.settings.php` и точный идентификатор действия настраиваются в конкретном модуле. Проверьте пример на целевой версии ядра Битрикс.
