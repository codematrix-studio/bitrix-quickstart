# Миграция старой библиотеки lema.lib

Исходный модуль: `ASDAFF/bitrix.quickstart/local/modules/lema.lib`.

Это собственная старая библиотека CodeMatrix Studio. Её код можно перерабатывать и использовать повторно. Старый репозиторий остаётся неизменным: перенос и адаптеры размещаются отдельно в новом каркасе.

## Состав

В дереве модуля обнаружено 208 PHP-файлов. Из них 80 файлов в `lib/lib/` побайтно совпадают с соответствующими файлами из `lib/` (совпадают Git blob SHA). Это дубли, а не отдельная версия API; при переносе учитывается основная директория `lib/`.

Версия модуля — 0.1.1 от 10.11.2015. Внутри есть:
- базовые классы и обёртки окружения Bitrix;
- работа с инфоблоками и шаблонными данными;
- формы и валидаторы;
- корзина на HL-блоках и отдельная обёртка штатной Sale Basket;
- компоненты новостей, меню, хлебных крошек и форм;
- OpenGraph, GTM, ecommerce и YML;
- интеграция со Сбербанком и VK;
- обработчики событий и установщик модуля.

## Приоритеты дальнейшей переработки

### Высокий приоритет

- `lib/Forms/Form.php` и `lib/Forms/Validators/*`: сохранить правила и формат ошибок, исправить обработку массивов, boolean false, числовых значений, отсутствующих параметров regex и повторный вызов validate.
- `lib/IBlock/Element.php` и `lib/IBlock/Section.php`: **переработаны** в `Project\Bitrix\IBlock\ElementRepository` и `SectionRepository`; старые статические фасады сохранены адаптерами `Lema\IBlock\Element` и `Lema\IBlock\Section`.
- `lib/Common/Helper.php`: **основные универсальные методы переработаны** в `RussianPluralizer`, `JsonEncoder`, `CharsetConverter`, `UrlGenerator`, `PropertyAccessor` и `ImageWatermarker`; старый фасад `Lema\Common\Helper` сохранён. Методы работы с URL требуют явного доверенного базового адреса.
- `lib/Base/Markup.php` и `lib/Seo/OpenGraph.php`: **переработаны** в `Project\Seo\MetaMarkup`; старые классы и fluent API сохранены адаптерами, экранирование атрибутов перенесено на этап вывода.
- `lib/Base/StaticInstance.php`, `BitrixInstances.php` и `GlobalVars.php`: **переработаны** через `PerClassInstance`, `PerClassBitrixInstance` и `PerClassGlobalProxy`; адаптеры старых базовых классов сохранены.

### Средний приоритет

- `lib/Common/AssetManager.php`, `App.php`, `Request.php`, `Context.php`, `Server.php`, `User.php`: обёртки над Bitrix API, после проверки контракта и версий ядра.
- `lib/Base/XmlExport.php` и `lib/Seo/YmlExport.php`: переписать кеш и XML-генерацию целиком, сохранив публичные методы и формат результата.
- `lib/Template/TemplateHelper.php`: **переработан** в `Project\Bitrix\IBlock\TemplateHelper`; методы работы со списками и edit/delete actions сохранены, добавлен необязательный адаптер старого API.
- `lib/Basket/BasketHandler.php`: отдельно оценить как обёртку над штатной Sale Basket; это перспективнее старой HL-корзины.

### Не переносить без существенной переработки

- `lib/Basket/Basket.php`, `BasketPosition.php`, `HighloadBlock.php`, `Settings.php`: жёстко заданные ID инфоблоков/HL-блоков, cookie-ID на слабом генераторе, проектная схема данных и операции очистки старых корзин.
- `lib/Seo/ECommerce.php` и `GTMFormSubmit.php`: не передавать в аналитику ФИО, email, телефон, адрес и комментарии; требуется allowlist полей и удаление персональных данных.
- `lib/Forms/ReCaptcha.php`: устаревший API, singleton с одним секретом, `die()`, отсутствие таймаута и слабая обработка ответа. Реализовать заново через актуальный API.
- `lib/Sberbank/*`: в старом HTTP-клиенте отключена проверка TLS-сертификата (`CURLOPT_SSL_VERIFYHOST` и `CURLOPT_SSL_VERIFYPEER`). Платёжный API нельзя переносить до полного пересмотра TLS, таймаутов, ошибок и обработки статусов.
- `lib/Handlers/*`: большинство методов пустые заготовки.
- `lib/Components/News*.php`, `Photo.php`: есть жёстко заданные ID инфоблоков и настройки конкретных сайтов. Можно переносить только после отделения дефолтов от проекта.

## Обнаруженные дефекты исходной библиотеки

1. В `include.php` автозагрузчик не проверяет, что имя класса начинается с префикса `Lema\`, прежде чем удалять первые символы имени.
2. `StaticInstance::$instance` и `BitrixInstances::$instance` объявлены в базовых классах и не переопределены всеми наследниками. Это создаёт риск общего экземпляра между разными классами.
3. `GlobalVars::__call()` передаёт массив аргументов одним аргументом вместо распаковки.
4. `Form::setFields()` вызывает `trim()` для любого значения; массив из POST приводит к ошибке типов на современных PHP.
5. `BooleanValidator` трактует валидное значение `false` как ошибку.
6. `NumericValidator` использует `FILTER_VALIDATE_INT`, хотя имя предполагает проверку числа, включая дробные значения.
7. `RecaptchaValidator` передаёт `sitekey` в конструктор, который ожидает секретный ключ.
8. `XmlExport` проверяет наличие файла `additionalData.json`, но не записывает его; кеш может постоянно пересоздаваться. Результаты файловых операций и JSON-кодирования не проверяются.
9. `YmlExport` выводит часть данных в XML-текст и атрибуты без корректного XML-экранирования.
10. `Basket::deleteOldBaskets()` удаляет устаревшие корзины и связанные позиции в общем хранилище, поэтому требует проверки связей и транзакционности.
11. Установщик копирует файлы в общий `php_interface/include`, а деинсталлятор удаляет их без сохранения исходных файлов, которые могли быть перезаписаны.
12. В `options.php` выполнение завершается через `return` до основного кода настроек.
13. `Common/VK.php` объявляет namespace `Lema\Seo`, хотя лежит в каталоге `Common`; текущий PSR-4 загрузчик не найдёт его по ожидаемому имени `Lema\Seo\VK`.

## Правило совместимости

Сначала фиксируется старый публичный контракт: имя класса, namespace, наследование, конструктор, публичные методы, параметры, значения по умолчанию, возвращаемые значения и побочные эффекты. Затем создаётся новая реализация. Для старого API делается отдельный адаптер, который подключается явно.

Небезопасные побочные эффекты не воспроизводятся автоматически. Такие отличия документируются отдельно и требуют явного решения при миграции. Реальную совместимость с ядром Bitrix подтверждаем только тестом на установленном ядре; локальная проверка PHP не считается такой проверкой.

- Формат правила: `[имена_полей, тип_проверки, дополнительные_параметры]`.

### Исправленные дефекты

1. `trim()` больше не вызывается для массивов из POST.
2. Boolean `false` распознаётся как допустимое значение.
3. Числовой валидатор принимает дробные числа, соответствуя своему назначению.
4. Длина считается по символам UTF-8 без обязательного расширения mbstring.
5. Ошибки очищаются и пересчитываются при повторной валидации.
6. CP1251-конвертация не передаёт массив сообщений непосредственно в `iconv()`.
7. Некорректный regex не обрывает обработку формы.
8. reCAPTCHA больше не использует устаревший клиент с GET-запросом и singleton-секретом. Без внедрённой серверной проверки правило отклоняет значение.
9. Добавление элемента инфоблока не позволяет подменить `IBLOCK_ID` через входной массив.
10. Удалён вывод ошибки через `die()`; методы возвращают результат и записывают ошибку в форму.

Старый фасад сохранён в `legacy/Lema/Common/Helper.php`. Перечень методов, примеры и ограничения описаны в [classes/Support/README.md](../classes/Support/README.md).

### Обратная совместимость

Сохранены старые имена методов: `pluralize()`, `pluralizeN()`, `enc()`, `getJson()`, `utf8ToCP1251()`, `getFullUrl()`, `getImageWatermark()`, `getImageWatermarkSrc()`, `propEmpty()`, `propFilled()`, `prop()`, `propValue()`, `escPropValue()`.

Для `getFullUrl()` добавлена обязательная настройка доверенного домена через `Helper::setBaseUrl()`. Это намеренное изменение: прежний метод брал имя хоста из контекста запроса, что могло приводить к формированию ссылок на подставленный Host. Для платёжных callback/return URL домен должен задаваться конфигурацией проекта, а не заголовком запроса.

### Найденные особенности старой реализации

1. `pluralize()` проверял только целочисленный остаток и не обрабатывал отрицательные числа ожидаемым образом.
2. `enc()` зависит от Bitrix HtmlFilter или `htmlspecialcharsbx()`; при отсутствии обоих вариантов нет независимого fallback.
3. `getJson()` напрямую возвращает `json_encode()`, поэтому ошибка кодирования может быть проигнорирована вызывающим кодом.
4. `utf8ToCP1251()` не обрабатывает неудачное преобразование.
5. `getFullUrl()` формирует абсолютный URL на основе `Server::getServerName()`, зависящего от HTTP-контекста.
6. `getImageWatermark()` не проверяет наличие `CFile` и константы типа масштабирования; параметры водяного знака объединяются вручную.
7. `propEmpty()` использует `empty()`, поэтому значение строки `"0"` считается пустым. Это поведение сохранено для совместимости.
8. `escPropValue()` также считает `"0"` пустым из-за `empty()`. Это поведение сохранено; при необходимости получить ноль используйте `propValue()` и экранируйте его отдельно.

### Тестирование

Добавлен `tests/lema_helper_smoke.php`; запуск — `composer test:helper` из каталога `local`. Тесты проверяют склонение, HTML-кодирование, JSON, Windows-1251, чтение свойств и формирование URL с доверенным доменом. ### Исправленные проблемы

1. `StaticInstance` больше не использует один унаследованный статический экземпляр для всех классов-наследников. Экземпляр хранится отдельно для каждого класса.

4. `GlobalVars::__call()` передаёт аргументы метода через распаковку массива, а не передаёт весь массив одним аргументом.
5. Для тестов и длительных процессов предусмотрен явный сброс кеша экземпляра через `resetInstance()`.

Добавлен автономный тест `tests/lema_base_instances_smoke.php`; запуск — `composer test:base`. Он проверяет изоляцию экземпляров наследников, глобальных объектов и корректную передачу аргументов. Реальные фасады Bitrix дополнительно проверяются на ядре.

## ECommerce и GTMFormSubmit — требуют отдельной безопасной переработки

Старые файлы:
- `lib/Seo/ECommerce.php`;
- `lib/Seo/GTMFormSubmit.php`.

Пока не переносились. В старой реализации есть риски, которые нельзя переносить ради формальной совместимости:

- `ECommerce::getGoogleCode()` включает ФИО/название компании, email, телефон, адрес и комментарий к заказу в аналитический payload.
- `GTMFormSubmit` позволяет без ограничений добавлять произвольные значения полей формы; пример библиотеки передаёт контактные данные.
- JSON вставляется непосредственно внутрь `<script>` без набора флагов `JSON_HEX_TAG`, `JSON_HEX_AMP`, `JSON_HEX_APOS`, `JSON_HEX_QUOT`.
- Singleton хранит состояние между вызовами, поэтому данные предыдущей формы или заказа могут попасть в следующий payload.
- `ECommerce` подключает модули `sale` и `iblock` при загрузке файла, а не перед конкретной операцией.

При переработке сохраняем формат событий и структуру товарных данных, но вводим allowlist полей, исключаем персональные данные из аналитики по умолчанию, безопасно кодируем JSON и сбрасываем состояние между заказами/формами. Старые методы будут доступны через адаптеры с документированными изменениями.


Тесты Markup/OpenGraph включены в `composer test`. На PHP 8.1, 8.2, 8.3 и 8.4 успешно проверены синтаксис, старые адаптеры и автономный тест разметки. Работа с реальным `$APPLICATION` дополнительно проверяется на ядре Битрикс.


## XmlExport и YmlExport — переработано

Старые файлы:
- `lib/Base/XmlExport.php`;
- `lib/Seo/YmlExport.php`.

Найдены следующие проблемы.

### XmlExport

1. `additionalData.json` проверяется в `isNeedUpdate()`, но нигде не записывается. Из-за этого кеш постоянно считается устаревшим.
2. `loadAdditionalData()` только заменяет свойство в памяти и не сохраняет файл.
3. Ошибки `file_get_contents()`, `file_put_contents()` и `json_decode()` не проверяются.
4. Запись JSON выполняется напрямую в конечный файл: при параллельных запросах или прерывании процесса можно получить частичный кеш.
5. Нет блокировки кеша и атомарной замены файлов.
6. `limit` применяется после получения полного списка элементов, а не к запросу.
7. `storageDir` напрямую соединяется с document root; требуется нормализация пути и защита от выхода за разрешённую директорию.
8. Абсолютные URL изображений и страниц собираются конкатенацией строк, без проверки уже абсолютных URL и без единого правила завершающего слеша.
9. Загрузка разделов делает дополнительный запрос для каждого родительского раздела.
10. `showData()` в базовом классе — незаконченная заглушка.

### YmlExport

1. Имя магазина и компании берутся из `$_SERVER['HTTP_HOST']`. Это позволяет подменять их заголовком Host.
2. URL магазина, URL товара и изображения выводятся без XML-экранирования.
3. Названия категорий и часть атрибутов выводятся без экранирования.
4. `id`, `parentId`, `name`, `unit` и другие атрибуты могут содержать символы, нарушающие XML.
5. Имена XML-тегов берутся из `params['fields']` без проверки допустимости.
6. Текстовые значения экранируются через HTML-функцию `htmlspecialcharsbx()`, а не через отдельный XML-слой.
7. Дата каталога зависит от времени изменения файла секций, а не от единого времени формирования выгрузки.

### План новой реализации

- отдельный кеш JSON с проверкой ошибок, блокировкой и атомарной записью;
- единая конфигурация доверенного URL магазина и директории выгрузки;
- отдельный XML-экранировщик для текста и атрибутов;
- allowlist имён тегов для пользовательских полей;
- корректная обработка пустых/невалидных кеш-файлов;
- сохранение старых методов `loadData()`, `loadSections()`, `loadAdditionalData()`, `getProducts()`, `getSections()`, `getAdditionalData()`, `showData()`;
- адаптеры для старых классов с явной настройкой базового URL и директории.

### Новая реализация

- `Project\Support\JsonFileCache` — атомарный JSON-кеш с блокировкой, проверкой ошибок и TTL.
- `Project\Export\XmlEscaper` — отдельное экранирование XML-текста и атрибутов, удаление недопустимых XML 1.0 управляющих символов.
- `Project\Export\YmlCatalogRenderer` — формирование YML из подготовленных массивов без зависимости от Bitrix.
- `Project\Export\BitrixCatalogExporter` — получение товаров/разделов через репозитории, нормализация данных и кеширование.
- `Lema\Base\XmlExport` и `Lema\Seo\YmlExport` — необязательные адаптеры старых имён.

### Сохранённая совместимость

- Конструктор `XmlExport($iblockId, array $params = [])` сохранён.
- Сохранены `setNeedUpdate()`, `loadData()`, `loadAdditionalData()`, `getAdditionalData()`, `getProducts()`, `getSections()` и `showData()`.
- `YmlExport::showData()` по-прежнему выводит XML через `echo` и поддерживает `sendHeader`.
- Сохранены ключи `storageDir`, `serverUrl`, `productIds`, `sectionIds`, `additionalData`, `fields` и `params`.

### Исправления и намеренные изменения

1. Кеш теперь хранится одним файлом и обновляется атомарно; старые три JSON-файла больше не используются.
2. `additionalData` сохраняется и восстанавливается из кеша.
3. Подпись кеша включает ID инфоблока, выбранные ID, дополнительные данные и параметры запроса.
4. Если передан произвольный `callback`, кеш отключается, чтобы не отдавать результат чужой функции.
5. `productIds`, ранее объявленный, но не применявшийся, теперь действительно ограничивает список товаров.
6. Разделы выбираются вместе с потомками; неактивные разделы не отбрасываются.
7. Абсолютные ссылки формируются только от доверенного адреса. Внешние домены в ссылках товаров отклоняются.
8. `serverUrl` теперь обязателен. Его нельзя автоматически получать из `HTTP_HOST`.
9. `storageDir` остаётся путём относительно `DOCUMENT_ROOT`, но переходы `..` запрещены.
10. Вывод всегда UTF-8; `SITE_CHARSET` больше не определяет кодировку выгрузки.
11. Базовый `XmlExport::showData()` теперь выбрасывает `LogicException`, поскольку старая реализация выводила заглушку, а не XML-документ.

Подробное описание, примеры конфигурации и ограничения: [classes/Export/README.md](../classes/Export/README.md).

Автономные проверки: `tests/lema_export_smoke.php`; команда `composer test:export`. Проверяются кеш, XML-экранирование, YML, URL и подготовка данных через внедрённые репозитории. Реальная выгрузка с `CFile`, `CIBlockElement` и `CIBlockSection` на ядре Битрикс пока не выполнялась.


Для наследников `Lema\Base\XmlExport` сохранена точка расширения: если дочерний класс переопределяет `loadAdditionalData()`, адаптер вызывает этот метод при обновлении кеша. `YmlExport::showData()` ожидает, что `loadData()` уже был вызван, как и исходный класс; сам по себе метод только формирует и выводит подготовленные данные.

## Старый Ns\Bitrix\Helper\IBlock\Validator

Исходный файл: `ASDAFF/bitrix.quickstart/local/codes/Ns/Bitrix/Helper/IBlock/Validator.php`.

Для миграции добавлен необязательный адаптер: `legacy/Ns/Bitrix/Helper/IBlock/Validator.php`.

Сохранены методы и их наблюдаемое поведение:

- `email($email = '', $xss = true)` — при включённом `$xss` сначала обрезает пробелы и экранирует HTML, затем проверяет адрес; возвращает строку или `false`;
- `email($email, false)` — не обрезает и не изменяет исходное значение перед проверкой;
- `xss($value = '')` — обрезает внешние пробелы и экранирует HTML с флагами PHP по умолчанию старой версии.

Адаптер подключается явно после Composer autoload:

```php
require_once __DIR__ . '/legacy/Ns/Bitrix/Helper/IBlock/Validator.php';

$validator = new \Ns\Bitrix\Helper\IBlock\Validator();
$email = $validator->email($email);
$name = $validator->xss($name);
```

Старый класс наследовался от `Ns\Bitrix\Helper\HelperCore`, но сам не использовал его магические методы. Адаптер намеренно не возвращает универсальный `HelperCore` и не поддерживает вызовы `with...()` / `get...()`: этот механизм хранит произвольное состояние без типизации и не является частью контракта двух методов валидатора. Если проектный наследник старого класса использовал это наследование, его нужно мигрировать отдельно.

В новом коде не следует использовать `xss()` для очистки данных перед сохранением. Проверяйте входные данные по назначению, храните исходные значения и экранируйте их при выводе в конкретный контекст. Для этого каркас предоставляет `Project\Support\EmailValidator` и `Project\Support\HtmlEscaper`.

Автономный тест: `tests/iblock_validator_compatibility_smoke.php`; команда запуска из каталога `local`: `composer test:iblock-validator`. Тест не требует ядра Битрикс.




## Page — проверка текущего раздела сайта

Старый класс `Lema\Common\Page` перенесён в два слоя:

- `Project\Support\PagePathMatcher` — независимая от Bitrix логика сопоставления путей;

```php
if (\Lema\Common\Page::inDir(['/catalog/', '/news/'])) {

}
```

Новый API:

```php
use Project\Bitrix\Context\Page;

if (Page::inDirectory(['/catalog/', '/news/'])) {

}
```

Исправлено важное поведение старой реализации: проверка границы сегмента. Путь `/catalog-old/` больше не считается частью `/catalog/`. Метод `inRootDir()` проверяет только первый сегмент URL и не совпадает с одноимённым вложенным каталогом.

Адаптер подключается явно после Composer autoload:

```php
require_once __DIR__ . '/legacy/Ns/Bitrix/Helper/IBlock/Validator.php';

$validator = new \Ns\Bitrix\Helper\IBlock\Validator();
$email = $validator->email($email);
$name = $validator->xss($name);
```

Старый класс наследовался от `Ns\Bitrix\Helper\HelperCore`, но сам не использовал его магические методы. Адаптер намеренно не возвращает универсальный `HelperCore` и не поддерживает вызовы `with...()` / `get...()`: этот механизм хранит произвольное состояние без типизации и не является частью контракта двух методов валидатора. Если проектный наследник старого класса использовал это наследование, его нужно мигрировать отдельно.

В новом коде не следует использовать `xss()` для очистки данных перед сохранением. Проверяйте входные данные по назначению, храните исходные значения и экранируйте их при выводе в конкретный контекст. Для этого каркас предоставляет `Project\Support\EmailValidator` и `Project\Support\HtmlEscaper`.

Автономный тест: `tests/iblock_validator_compatibility_smoke.php`; команда запуска из каталога `local`: `composer test:iblock-validator`. Тест не требует ядра Битрикс.




## Page — проверка текущего раздела сайта

Старый класс `Lema\Common\Page` перенесён в два слоя:

- `Project\Support\PagePathMatcher` — независимая от Bitrix логика сопоставления путей;
- `Project\Bitrix\Context\Page` — получение текущего каталога через HTTP-запрос Bitrix;
- `legacy/Lema/Common/Page.php` — необязательный адаптер старых статических методов.

Старый код:

```php
if (\Lema\Common\Page::inDir(['/catalog/', '/news/'])) {
    // ...
}

if (\Lema\Common\Page::inRootDir('catalog')) {
    // ...
}
```

Новый API:

```php
use Project\Bitrix\Context\Page;

if (Page::inDirectory(['/catalog/', '/news/'])) {
    // ...
}

if (Page::inRootDirectory('catalog')) {
    // ...
}
```

Исправлено важное поведение старой реализации: проверка границы сегмента. Путь `/catalog-old/` больше не считается частью `/catalog/`. Метод `inRootDir()` проверяет только первый сегмент URL и не совпадает с одноимённым вложенным каталогом.

Автономный тест: `tests/page_path_matcher_smoke.php`; команда запуска из каталога `local`: `composer test:page`. Тест не требует ядра Битрикс. Фасад текущего URL требует HTTP-контекста Bitrix и проверяется интеграционно.


## AssetManager

Старый `Lema\Common\AssetManager` переработан в `Project\Bitrix\Asset\AssetManager`. Необязательный адаптер `legacy/Lema/Common/AssetManager.php` сохраняет методы `addJsArray()`, `addCssArray()`, `init()`, а также статические `get()` и `resetInstance()`. Старый `Lema\Common\Asset` не переносится: он только возвращал singleton штатного Bitrix Asset.

Основная реализация и границы интеграционного тестирования описаны в [Bitrix/Asset/README.md](../Bitrix/Asset/README.md).


## Files Checker

Старый `Ns\\Bitrix\\Helper\\Files\\Checker::chooseFileIcoClass($id)` заменён адаптером `legacy/Ns/Bitrix/Helper/Files/Checker.php`.
