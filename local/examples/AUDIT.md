# Ревизия старых заготовок

Источник: [ASDAFF/bitrix.quickstart](https://github.com/ASDAFF/bitrix.quickstart), ветка `master`.

Проверены структура `local/templates`, конфигурационные файлы `local/php_interface/config`, подборка `local/codes/blank/compilation`, примеры frontend JS и каталог заготовок компонентов. Старый репозиторий содержит тысячи файлов, поэтому это ревизия именно библиотечных заготовок и наиболее перспективных для стартового проекта каталогов, а не построчный аудит каждого файла репозитория.

## Уже адаптировано и перенесено

| Старый источник | Новый файл | Решение |
|---|---|---|
| `compilation/sectionTree.php` | [iblock/section-tree.php](iblock/section-tree.php) | Переписано в функцию, входной ID проверяется, результат возвращается массивом |
| `compilation/csv_to_array.php` | [files/csv-to-array.php](files/csv-to-array.php) | Добавлены проверка файла, закрытие ресурса через `finally`, проверка заголовков и количества колонок |
| `compilation/createZipArchive.php` | [files/create-zip-archive.php](files/create-zip-archive.php) | Добавлены проверка ZipArchive, канонизация путей, исключение ссылок и безопасное закрытие архива |

## Кандидаты на отдельную адаптацию

### Инфоблоки и данные

- `getSearchedElement.php` — поиск через модуль Search. Большой фрагмент, требует проверки фильтров, входных параметров и экранирования.
- `sectionTree.php` — идея уже перенесена.
- `getAllRegions.php`, `getPreLinkProducts.php`, `searchElements.php`, `setValueListProperty.php` — проверить назначение, зависимости и актуальность API перед переносом.
- `cache.php` — содержит несколько несвязанных примеров и устаревшие/смешанные подходы к кешированию; не переносить целиком. Для нового кода ориентироваться на D7 Cache и managed cache с тегами.

### Интернет-магазин

- `createOrderD7.php`, `Add2BasketByProductID.php`, `addToBasket.php`, `DeleteUpdateBasketItem.php`, `AddOrderProperty.php`, `GetDeliveries.php`, `AddDeliveryGroup.php` — полезная предметная область, но исходники используют жёстко заданные ID, тестовые данные, прямой вывод ответа или старые API. Переносить только после отдельной сверки с текущими классами `Bitrix/Sale` в новом проекте.
- `CCatalogDiscount.php`, `getAllDiscountByID.php`, `scu_sort_available.php`, `sort_scu.php` — проверить версию каталога и бизнес-логику; не считать универсальными рецептами.

### Компоненты

- `clear.component`, `clear.component.d7`, `empty_component`, `component_boilerplate`, `super.component*` — полезны как учебные образцы структуры. Старые реализации требуют обновления и проверки полного набора файлов, языковых ресурсов и шаблонов.
- В текущем репозитории уже есть собственные классы и документация; новые заготовки не должны дублировать существующую библиотеку.

### JavaScript

- `frontend/js/myscripts.js` — вкладки, popup и фиксация меню на jQuery.
- `frontend/js/lib_code.js` — проверка форм и popup на jQuery.
- Это исторические фрагменты, зависящие от jQuery и сторонних плагинов; часть содержит устаревшие методы. Пока оставлены в списке кандидатов, а не добавлены в стартовый набор. При переносе нужно разделить независимые примеры и явно описать зависимости.

## Не переносить без специальной причины

- `xml_parse.php` — меняет группы пользователей по данным внешнего XML, содержит жёстко заданные ID групп и не содержит достаточной защиты для безопасного запуска.
- `example_options_module.php` — привязан к модулю `itua.afa` и его настройкам.
- `example.php` — содержит пример секретоподобного ключа; даже демонстрационные ключи не должны становиться конфигурацией стартового проекта.
- `bitrix_server_test.php`, `debug_pr.php`, `percona.php`, `reindexExneded.php` и прочие диагностические/административные скрипты — не включать в публичный каркас без отдельной задачи и ограничений доступа.
- `propesIblocks.rar` и сторонние библиотеки — не копировать без проверки происхождения, лицензии и необходимости.

## Принцип дальнейшей работы

Сохранять практическую ценность старого проекта: примеры не вычищать до пустых заглушек. При этом переносить не сырой файл, а понятную и проверенную заготовку: назначение, зависимости, версия API, входные данные и предупреждения по безопасности. Если аналогичная функциональность уже есть в новом проекте, документировать ссылку на неё вместо создания дубля.
