# Ревизия старых заготовок

Источник: [ASDAFF/bitrix.quickstart](https://github.com/ASDAFF/bitrix.quickstart), ветка `master`.

Проверены структура `local/templates`, конфигурационные файлы `local/php_interface/config`, подборка `local/codes/blank/compilation`, примеры frontend JS и каталог заготовок компонентов. Старый репозиторий содержит тысячи файлов, поэтому это ревизия библиотечных заготовок и наиболее перспективных для стартового проекта каталогов, а не построчный аудит каждого файла репозитория.

## Сверка интернет-магазина с новой библиотекой

Старые примеры корзины и заказа проверены по исходному коду, а не только по названиям файлов. В новой версии уже есть более безопасные сервисы, поэтому дублирующие рецепты в `local/examples` не добавлялись.

| Старый источник | Что делает исходник | Решение в новом проекте |
|---|---|---|
| `Add2BasketByProductID.php` | Принимает ID и количество из `$_REQUEST`, напрямую вызывает legacy API и выводит JSON | Не переносить. Использовать [BasketManager](../php_interface/classes/Bitrix/Sale/BasketManager.php) или фасад [BasketHandler](../php_interface/classes/Bitrix/Sale/BasketHandler.php); HTTP endpoint отдельно проверяет метод запроса, CSRF и права |
| `addToBasket.php` | Добавляет товар и свойства COLOR/SIZE, жёстко привязанные к конкретному каталогу | Не переносить: схема свойств проектная. Для стандартного добавления — BasketManager; свойства требуют отдельной модели разрешённых свойств и проверки каталога |
| `DeleteUpdateBasketItem.php` | Удаляет строку заказа по переданным ID и вручную пересчитывает сумму заказа | Не переносить: нет проверки владельца заказа/строки, сумма рассчитывается вручную и может рассинхронизироваться. Необходим отдельный сценарий редактирования заказа с проверкой прав и штатным пересчётом |
| `createOrderD7.php` | Создаёт заказ с тестовыми контактами и жёсткими ID типа плательщика, доставки и оплаты | Заменён по назначению [OrderManager](../php_interface/classes/Bitrix/Sale/OrderManager.php); быстрый заказ из временной корзины реализован через [QuickOrder](../php_interface/classes/Bitrix/Sale/QuickOrder.php) |
| `AddOrderProperty.php` | Вручную создаёт/обновляет значения свойств заказа через legacy API | Не переносить: OrderManager устанавливает свойства по символьному коду через коллекцию D7 и проверяет обязательные поля |
| `GetDeliveries.php` | Получает активные службы доставки верхнего уровня без учёта ограничений конкретного заказа | Не использовать как готовый checkout-рецепт. OrderManager получает службы, доступные именно для создаваемого заказа, через штатный менеджер ограничений |
| `AddDeliveryGroup.php` | Короткий вызов добавления службы/группы без контекста и проверки результата | Не переносить: пример неполный и не объясняет создание/настройку службы доставки |
| `CCatalogDiscount.php` | Назначает жёстко заданные купоны по истории заказов и состоянию авторизации | Не переносить: купоны и бизнес-правила относятся к конкретному магазину; код содержит ошибочную проверку пустого массива и смешивает API купонов |
| `getAllDiscountByID.php` | Получает скидки через legacy `CCatalogDiscount::GetList` | Оставить кандидатом для отдельного современного примера только при наличии универсального сценария и проверки актуального API скидок |
| `scu_sort_available.php` | Обновляет свойства доступности, используя жёсткие ID инфоблоков 2 и 3 | Не переносить: жёсткая схема каталога, обработчик событий с побочными изменениями и риск рекурсии/лишних запросов |
| `sort_scu.php` | Рассчитывает минимальную/максимальную цену торговых предложений и пишет свойства | Не переносить как универсальный код: логика зависит от структуры SKU, валют, типов цен и событий конкретного каталога |

### Что уже покрывает новая библиотека Sale

- Корзина текущего FUSER и текущего сайта, добавление/изменение/удаление позиций: `BasketManager`.
- Фасад с безопасными массивами-снимками и ограниченным набором принимаемых полей: `BasketHandler`.
- Создание заказа из корзины пользователя, установка свойств по символьным кодам, проверка обязательных свойств, доступности доставки/оплаты и финальный пересчёт: `OrderManager`.
- Быстрый заказ из отдельной временной корзины без изменения постоянной корзины FUSER: `QuickOrder`.
- Разбор входных данных быстрого заказа: `QuickOrderInput`.

Подробности и ограничения описаны в [документации Sale](../php_interface/classes/Bitrix/Sale/README.md) и [каталоге решений](../../library/sale/README.md). Это не означает, что готовый HTTP/AJAX endpoint уже реализован: контроллер должен самостоятельно проверять CSRF, авторизацию, права, формат запроса и защиту от повторной отправки. В частности, не передавайте ID пользователя, FUSER, цены, валюту, ID доставки или оплаты как доверенные значения от клиента.

## Компоненты

Исходные материалы проверены выборочно по полным файлам и структуре: `clear.component`, `clear.component.d7`, `empty_component`, `example/compsimple`, а также каталоги `component_boilerplate` и `super.component*`.

- `clear.component` — минимальный legacy-компонент на `component.php`; практически пустая заготовка без полноценной обработки параметров и ошибок.
- `clear.component.d7` — наследуется от `CBitrixComponent`, но использует короткие PHP-теги, неинициализированное свойство `$this->page`, не передаёт сформированный результат в шаблон и ловит только `Exception`.
- `example/compsimple` — наиболее содержательный учебный материал: структура файлов, `class.php`, описание компонента, параметры, языковые ресурсы и шаблон. Однако код включает модули без необходимости, содержит неиспользуемые обёртки над глобальными объектами и не показывает полноценную стратегию кеширования/обработки ошибок.
- `component_boilerplate` и `super.component*` — наборы разных поколений и назначений; переносить целиком без проверки каждого файла, языковых ресурсов и шаблонов нельзя.

Для нового проекта подготовлена отдельная адаптированная заготовка в [components](components/README.md). Она не регистрируется автоматически и не является готовым бизнес-компонентом.

## Инфоблоки и данные

- `getSearchedElement.php` и `searchElements.php` — полезная идея поиска через модуль Search с ограничением по инфоблоку/разделу. Старые файлы смешивают поисковую логику с выводом, используют глобальные переменные и в одном случае меняют глобальную настройку каталога. Адаптирован безопасный по входному контракту пример [search-elements.php](iblock/search-elements.php): он возвращает ID элементов и разделов отдельно, не выводит HTML и не меняет настройки модулей.
- `GetPreLinkProducts.php` — пример получения соседних товаров через `nElementID`. Не переносить как универсальную функцию: выбор соседей зависит от сортировки, текущего раздела и структуры каталога. Для конкретного магазина нужно определить ожидаемое поведение, включая товары без раздела и несколько разделов.
- `getAllRegions.php` — пример Location API. Оставлен для отдельной проверки на целевой версии Sale/Location: выборка зависит от связей названий и языка, а список регионов может быть настроен по-разному.
- `setValueListProperty.php` — не переносить: используется жёстко заданный ID значения списка `1453` и конкретное свойство каталога.
- `cache.php` — содержит несколько несвязанных сценариев: очистку кеша по `$_REQUEST['PAGEN_1']` без корректного контекста каталога, смешение D7 Cache и `CPHPCache`, дублирующий вызов получения отзывов, а также функцию соседних товаров с глобальными переменными и жёстко заданным ID инфоблока. Целиком не переносить.
- `Indi\\Main\\Cache` и `Site\\Main\\Cache` из старых модулей — практически дублирующие обёртки над D7 Cache. Первая дополнительно регистрирует тег в конструкторе до фактического заполнения кеша, обе используют глобальный `$_REQUEST` для очистки, а реализация не задаёт ясный контракт по ключу/параметрам и обработке ошибок. Не переносить.
- Вместо старых заготовок добавлены самостоятельные примеры [обычного D7-кеша](cache/simple-data.php) и [тегированного кеша](cache/tagged-data.php). Описание содержит рабочие точки подключения, правила формирования ключа и пример сброса тега. Они не заменяют `JsonFileCache`: тот решает другую задачу — хранит JSON-файлы и не использует хранилище/инвалидацию кеша Битрикс.

## JavaScript

- `frontend/js/myscripts.js` — вкладки, popup и фиксация меню на jQuery. Перенесены независимые идеи вкладок и раскрывающейся панели в [ui-patterns.js](frontend/ui-patterns.js), без jQuery и Fancybox.
- `frontend/js/lib_code.js` — проверка формы, подсветка полей, popup и таймерная проверка всех форм. Перенесена только универсальная проверка HTML5-ограничений по событию отправки формы в [form-validation.js](frontend/form-validation.js). Постоянный опрос DOM каждые 500 мс и глобальная блокировка кнопок исключены.
- Внешний Fancybox и конкретное окно благодарности не переносились: это зависимость и дизайн конкретного сайта, а не универсальная библиотечная функция.

## Не переносить без специальной причины

- `xml_parse.php` — меняет группы пользователей по данным внешнего XML, содержит жёстко заданные ID групп и не содержит достаточной защиты для безопасного запуска.
- `example_options_module.php` — привязан к модулю `itua.afa` и его настройкам.
- `example.php` — содержит пример секретоподобного ключа; даже демонстрационные ключи не должны становиться конфигурацией стартового проекта.
- `bitrix_server_test.php`, `debug_pr.php`, `percona.php`, `reindexExneded.php` и прочие диагностические/административные скрипты — не включать в публичный каркас без отдельной задачи и ограничений доступа.
- `propesIblocks.rar` и сторонние библиотеки — не копировать без проверки происхождения, лицензии и необходимости.

## Принцип дальнейшей работы

Сохранять практическую ценность старого проекта: примеры не вычищать до пустых заглушек. При этом переносить не сырой файл, а понятную и проверенную заготовку: назначение, зависимости, версия API, входные данные и предупреждения по безопасности. Если аналогичная функциональность уже есть в новом проекте, документировать ссылку на неё вместо создания дубля.
