## 2. Проверенные семейства компонентов

### 2.1. `clear.component`

Минимальный классический компонент. В текущем виде это только каркас: проверка константы Bitrix, инициализация результата и кеширование. Нет PHPDoc, нормализации параметров, описания контракта результата и обработки ошибок. Подходит как источник идеи для минимального шаблона после переработки, но не для копирования без изменений.

### 2.2. `clear.component.d7`

Заготовка на `CBitrixComponent` с отдельным классом и языковыми файлами. PHPDoc присутствует, но неполный и местами некорректный: `mixed[]` не объясняет структуру параметров, методы не имеют точного контракта, а комментарии не отражают фактическое поведение. В `executeComponent()` используется `$this->page`, которая в классе не объявлена и не инициализируется. `getResult()` создаёт локальный массив, но не переносит данные в `$this->arResult`. Обработка исключений ограничена `Exception`, нет явной проверки необходимых модулей. Требуется перепроектирование.

### 2.3. `empty_component`

Простой процедурный пример с использованием D7 Request/Loc. Есть неиспользуемые переменные запроса и приложения, параметры читаются без предварительной нормализации, а пример отмены кеша привязан к произвольному условию. README описывает компонент как пустой, но не задаёт полноценную инструкцию по созданию и подключению. Не переносить без очистки и дополнения документации.

### 2.4. `super.component`

Большой исторический компонент с RSS, дополнительным кешированием, подключением некешируемых файлов и административными иконками. Сильно связан с глобальными `$USER`/`$APPLICATION`, внутренними путями шаблона и старыми API. Встречаются прямые обращения к `$_SERVER`, а поведение смешивает маршрутизацию, кеширование, вывод RSS и администрирование. Это исторический reference, не универсальный стартовый шаблон.

### 2.5. `super.component.complex`

Полезен как пример старой SEF-маршрутизации и разделения страниц списка/раздела/элемента. При этом использует старые API, непоследовательную проверку входных параметров и глобальный контекст. Переносить можно только концепцию маршрутизации после отдельной проверки актуального API и проектирования чистого примера.

### 2.6. `component_boilerplate`

Содержит каркас комплексного компонента с list/edit и пример подключения. Файлы `sample.list/component.php` и `sample.edit/component.php` практически пустые. Основной `sample/component.php` содержит SEF/non-SEF маршрутизацию, но без достаточного PHPDoc и полноценной проверки параметров. Это наиболее близкий к учебной заготовке материал, но требует завершения и тестирования.

### 2.7. `example/compsimple`

D7-ориентированный учебный компонент с проверкой модулей, получением Request и разделением точки входа и логики. В PHPDoc есть описания, но нет точных типов параметров и результата; методы с префиксом подчёркивания не соответствуют выбранному современному стилю. Компонент безусловно требует `iblock` и `sale`, хотя для универсального примера зависимость от `sale` не обоснована. Текст README полезен как справочный материал, но содержит устаревшие формулировки и ссылки.

### 2.8. `bx-components/mscoder`

Содержит повторно используемые базовые классы `StandardElementListComponent` и `StandardElementsComponent`, а также меню и демонстрационные компоненты. Это наиболее насыщенная логикой группа, но не готовая библиотека для прямого переноса.

Замеченные проблемы:
- PHPDoc в основном описательный, без точных типов, структур массивов и контрактов исключений;
- встречаются опечатки и неясные имена свойств;
- прямые обращения к `$_REQUEST`, `$_GET` и глобальному `$USER`;
- кеширование зависит от сериализованных параметров и пользовательских групп без чётко описанного контракта;
- в примере `main.block.team` опечатка `widht` в параметрах изменения размера изображения;
- демонстрационные классы зависят от базового компонента, который также нуждается в ревизии.

Нужно отдельно решить, есть ли смысл создавать собственную базовую компонентную архитектуру в новом репозитории. Не переносить эти классы до проверки их полного исходного кода, вызовов и тестируемости.

### 2.9. `sorting`

Содержит полезную идею независимого компонента сортировки и формирования ссылок. Однако параметры сортировки поступают из GET и используются при построении результата; требуется строгая проверка разрешённых полей и направлений сортировки. В текущем коде есть обращения к данным без проверки структуры, а HTML-экранирование и построение URL нужно пересмотреть. Кандидат на переработку после определения контракта, не на прямой перенос.

## 3. Заготовка модуля

`modules/empty.module` — устаревший пример установщика примерно 2014 года.

Проблемы:
- технический идентификатор модуля задан заглушкой и не согласован с именем класса;
- используются старые короткие теги PHP и стиль объявления класса;
- версия и дата вынесены в отдельный файл, но структура инициализации не оформлена как современный шаблон;
- `InstallDB()` фактически только регистрирует модуль, а `UnInstallDB()` снимает регистрацию; миграций и установки схемы нет;
- `DoInstall()` и `DoUninstall()` не проверяют и не обрабатывают ошибки всех этапов;
- установка файлов копирует каталог по фиксированным путям, удаление удаляет каталог без достаточной проверки;
- README содержит только краткую подпись с опечаткой.

Это не безопасная и не полная заготовка модуля. Нужен новый шаблон с корректными метаданными, install/uninstall lifecycle, событиями, правами, языковыми файлами и тестируемыми шагами установки/удаления.

## 4. Фрагменты из `compilation/`

Это не единый набор шаблонов: здесь смешаны сниппеты, тестовые скрипты, примеры работы с HL-блоками, корзиной, заказами, кешем, почтой, CSV/XML, архивами, скидками и другими задачами.

Проверенные фрагменты:
- `createOrderD7.php`: демонстрационный сценарий заказа с тестовыми персональными данными и жёстко заданными ID типа плательщика, доставки и платёжной системы; нет полноценной обработки результата сохранения и ошибок свойств. Не превращать в шаблон заказа.
- `Add2BasketByProductID.php`: самостоятельный endpoint с чтением `$_REQUEST`, подключением пролога, выводом JSON из бизнес-функции, неполной проверкой товара и количества. Нет явной защиты от CSRF и нормального контракта ответа. Не переносить.
- `EmailSender.php`: жёстко задан адрес получателя, прямой вызов `mail()`, некорректная проверка входных данных, смешение обработки POST и отправки почты, вывод результата из метода. Не переносить.
- `HL.php`: скрипт создания HL-блока с прямым выполнением операции при открытии файла; не является безопасной заготовкой.
- `cache.php`: смешивает несколько несвязанных примеров кеширования, содержит привязки к конкретным функциям и глобальным переменным. Не переносить как единый шаблон.
- `Singleton.php`: учебный пример с кодом, выполняемым при подключении файла; `setParams()` заменяет весь массив параметров вместо добавления значения. Не переносить без переписывания.

Остальные сниппеты требуют отдельной классификации по назначению и проверки полного содержимого. Пригодные небольшие идеи можно позже оформить самостоятельными примерами с описанием требований и ограничений.

## 5. Предварительная сверка с новым репозиторием

В `codematrix-studio/bitrix-quickstart` уже есть README для `local/components`, `local/modules` и `local/templates`, но полноценных стартовых шаблонов компонента и модуля в этих каталогах пока нет. Поэтому явного дублирования именно готовых шаблонов не обнаружено.

При этом в новом репозитории уже существуют компонентные вспомогательные классы и документация D7-сервисов. При проектировании будущих шаблонов необходимо проверить их совместимость и не создавать вторую, конкурирующую архитектуру.

## 6. Требования к будущим шаблонам CodeMatrix

Для всех переносимых/создаваемых шаблонов:
1. Русскоязычная документация и комментарии.
2. Полный PHPDoc для публичных и защищённых методов: назначение, типы параметров, возвращаемое значение, исключения и побочные эффекты.
3. Типизация там, где она совместима с поддерживаемой версией PHP и контрактами Bitrix.
4. Проверка входных параметров и зависимостей.
5. Отсутствие реальных персональных данных, доменов, ID инфоблоков, платёжных систем и других проектных настроек.
6. Отсутствие выполнения демонстрационного кода при подключении файла.
7. Разделение бизнес-логики, HTTP-обработки и представления.
8. README с назначением, структурой файлов, требованиями, примером подключения и ограничениями.
9. Проверка синтаксиса, автозагрузки и доступных автоматизированных тестов.
10. Интеграционные проверки на стенде — отдельно, после освобождения пользовательской VM.

## 7. Решение по переносу

На текущем этапе перенос кода не выполнялся. По уже проверенным файлам:
- не копировать старые шаблоны без изменений;
- взять за основу идеи минимального классического компонента и D7-компонента, но подготовить новые чистые каркасы;
- комплексный компонент оставить отдельным расширенным примером после актуализации SEF-маршрутизации;
- заготовку модуля разработать заново, используя старый файл только как историческую подсказку;
- сниппеты из `compilation/` не включать в каталог шаблонов автоматически: отбирать по одному после отдельной проверки.

**Аудит остаётся промежуточным:** необходимо завершить проверку всех оставшихся файлов `components/`, `compilation/`, а также `Bitrix.autosave.form`, `bxcert.resize` и архивов. До завершения этой проверки миграцию шаблонов не начинать.


## 8. Дополнительные проверенные каталоги и сниппеты

### 8.1. `Bitrix.autosave.form`

Это не нейтральная форма автосохранения, а законченный пример объявления/анкеты с привязкой к конкретным инфоблокам, разделам, свойствам и пользовательским сценариям. В `index.php` используются константы проекта и ID-сущностей, глобальный пользователь и прямые запросы к инфоблоку. В `save.php` зашиты ID инфоблоков и допустимых разделов, а также бизнес-правила для родителей/объявлений. Не переносить как шаблон компонента; при необходимости извлекать только отдельный UX-подход после проектирования безопасного API.

В `reg.php` обнаружена критичная логическая ошибка в проверке сессии: условие объединяет `check_bitrix_sessid()` и проверки CAPTCHA через `||`, из-за чего ветка обработки может выполняться при невыполнении проверки сессии. Кроме того, скрипт возвращает пароль регистрации в JSON-ответе. Такой подход недопустим для повторного использования. Не переносить; считать пример небезопасным.

### 8.2. `bxcert.resize`

Небольшой пример модификации размеров изображений в `result_modifier.php`. Есть полезная идея вынести параметры типа/ширины/высоты в параметры шаблона, но код не проверяет нулевую высоту/ширину исходного изображения до деления, не валидирует тип поля и числовые значения, а результат `ResizeImageGet()` используется без проверки. В текущем виде не переносить. Функциональность пересекается с задачами обработки изображений, для неё следует сначала проверить уже существующий `ImageWatermarker` и определить отдельный контракт ресайзера.

### 8.3. Дополнительные сниппеты из `compilation/`

- `csv_to_array.php`: простая заготовка чтения CSV, но фиксированный предел длины строки, нет контроля несовпадения количества колонок и заголовков, `array_combine()` может завершиться ошибкой на строках неправильной длины. Кандидат только на переписывание с явным контрактом и тестами.
- `createZipArchive.php`: не проверяет результаты добавления файлов/каталогов, не гарантирует закрытие архива при ошибке, читает каждый файл целиком в память и не задаёт политику обработки символических ссылок/вложенности. Не переносить как готовую реализацию.
- `xml_parse.php`: сценарий обновления групп пользователей по XML, с привязкой к конкретной схеме и ID групп. Не проверяет результат поиска пользователя до вызова `GetUserGroup()`, не является универсальным импортёром. Исключить из шаблонов.
- `addNewUfProperty.php`: пример пользовательского типа поля, но класс не имеет PHPDoc, использует старый стиль API и не показывает полный набор методов пользовательского типа. Может стать справочным примером после сверки с актуальным API Bitrix.
- `OnAdminListDisplayHandler.php`: привязан к таблице заказов и конкретному URL печати; глобальная регистрация обработчика и отсутствие PHPDoc. Не переносить как общий обработчик административного списка.

Остальные файлы из `compilation/` ещё требуют индивидуальной проверки; сам факт нахождения в каталоге не означает, что это шаблон или безопасный сниппет.


## 9. Остальные проверенные фрагменты `compilation/`

### 9.1. Корзина, скидки и доставка

- `AddDeliveryGroup.php`: фрагмент вызова `Delivery\\Services\\Manager::add()` с неинициализированной переменной `$fields`; отсутствует проверка контекста, прав и результата. Не является самостоятельным примером.
- `AddOrderProperty.php`: использует устаревшие `CSaleOrderProps*`, не проверяет типы/принадлежность заказа и не гарантирует корректную обработку множественных значений. Не переносить как D7-решение; функциональность заказа уже представлена в новом репозитории отдельными D7-сервисами.
- `CCatalogDiscount.php`: жёстко зашиты купоны конкретного магазина, логика определения заказа некорректна (пустой массив и проверка `is_array`), глобальная регистрация события. Исключить.
- `DeleteUpdateBasketItem.php`: удаляет строку корзины по переданному ID, не проверяя, что она принадлежит указанному заказу и что текущий пользователь вправе менять этот заказ; пересчитывает сумму вручную, не учитывая полноценный расчёт скидок/налогов/доставки. Критически не переносить.
- `GetDeliveries.php`: простой ORM-запрос к таблице служб доставки, но без PHPDoc, обработки отсутствующего модуля и типизированного результата. Справочная идея; не самостоятельный шаблон.
- `GetPreLinkProducts.php`: два варианта выборки соседних товаров с жёсткими предположениями о размере страницы и разделе; смешаны старые API и нестрогие сравнения ID. Переписывать только при реальной потребности.
- `addToBasket.php`: использует неинициализированные в сниппете `$pid`/`$quantity`, не валидирует доступность/количество и выводит ответ напрямую. Не переносить.
- `Add2BasketByProductID.php` ранее отмечен как небезопасный endpoint; дополнительно `AddNewFieldInEmail.php` содержит ID заказа 941 и абсолютный домен-заглушку, а также формирует HTML письма без корректного экранирования имени/URL. Исключить.

### 9.2. Инфоблоки, поиск и индексирование

- `GetPreLinkProducts.php`, `getSearchedElement.php`, `search.php`, `searchElements.php`, `sectionTree.php`: прикладные фрагменты, зависящие от контекста компонента, параметров и конкретной схемы инфоблоков. В `getSearchedElement.php` присутствуют тестовый запрос, глобальные переменные и неинициализированные значения; не переносить как готовую функцию.
- `createSmartFilterSeoXML.php`: зависит от константы конкретного проекта и глобального URL, XML формируется строковой конкатенацией, нет безопасного XML writer и атомарной публикации файла. Исключить.
- `reindexExneded.php`: обработчик поискового индекса дописывает свойства каталога, опираясь на константы и коды свойств конкретного проекта; нет защиты от повторной регистрации и достаточной проверки входной структуры. Только справочный пример.
- `scu_sort_available.php` и `sort_scu.php`: сложная логика SKU/остатков, глобальные обработчики событий, жёстко заданные ID инфоблоков, потенциально дорогие повторные выборки. Не переносить без отдельного проектирования и интеграционных тестов.
- `complects.php`: расчёт цены торговых предложений и скидок смешивает старый API каталога, валюты и пользовательские группы; код фрагментарный и требует проверки корректности расчёта. Не использовать как эталон расчёта цены.
- `setValueListProperty.php`: привязка к конкретному текстовому значению и ID enum 1453. Исключить.

### 12.8. Шаблон изменения размеров изображений

Повторно просмотрен полный bxcert.resize/result_modifier.php. Подтверждены риски:

### 12.10. Комплексные шаблоны и маршрутизация boilerplate

- super.component.complex/templates/.default/sections.php и element.php не реализуют собственный вывод, а делегируют работу компоненту cetera:super.component. Это зависимость от конкретного vendor/namespace и компонента из старого набора; перенос комплексной заготовки без него приведёт к неработающему маршруту.
- Вложенные шаблоны sections/template.php и element/template.php фактически пустые; result_modifier.php содержит только комментарий-заглушку. Следовательно, даже при наличии делегирования в дочерних компонентах не приложены реальные шаблоны вывода.
- component_boilerplate/sample/component.php реализует исторический SEF/non-SEF роутер. Входные параметры SEF_FOLDER, SEF_URL_TEMPLATES, VARIABLE_ALIASES и SET_STATUS_404 используются без полноценной нормализации и проверки структуры. При нераспознанном маршруте выбирается list и выставляется HTTP 404, но нет отдельного документированного контракта результата/ошибки; PHPDoc отсутствует. Это учебная заготовка, но не готовый безопасный роутер.
- В non-SEF режиме URL заранее пропускается через htmlspecialcharsbx() при формировании arResult. Экранирование следует выполнять в точке вывода с учётом HTML-контекста; хранение уже HTML-экранированного URL в данных компонента смешивает данные и представление и создаёт риск двойного экранирования.
- sample.list/component.php и sample.edit/component.php лишь вызывают IncludeComponentTemplate() и не содержат логики, параметров или PHPDoc. Их наличие создаёт видимость готовых подкомпонентов, но по факту это пустые точки расширения.
- super.component/templates/.default/result_modifier.php содержит исторический закомментированный пример выборки через CIBlockElement::GetList(), без современного контракта ошибок/результата. В активной части напрямую записывает $this->__component->arResult и сохраняет __TEMPLATE_FOLDER; это внутреннее взаимодействие с кешированием и структурой шаблона, не следует превращать в универсальный рецепт без проверки API и сценариев кеша.

Вывод по этому семейству: комплексную заготовку лучше спроектировать отдельно — с явной картой маршрутов, whitelist имён страниц, строгой нормализацией идентификаторов/параметров, документированным 404-поведением и независимыми шаблонами без обязательной зависимости от стороннего компонента.

## 12.11. Дополнительная проверка прикладной формы объявлений

Повторно разобраны ранее не выделенные отдельно файлы `Bitrix.autosave.form/array.php` и `Bitrix.autosave.form/bitrix/php_interface/include/advert/index.php`.

### `array.php`
- Файл содержит не универсальные настройки, а словари полей конкретной предметной области: объявления о собаках, щенках, родителях, родословных, заводчиках и фотографиях.
- Контракт массивов нигде не описан; нет PHPDoc с shape-типами и назначением ключей.
- Одни и те же поля родителей представлены большим количеством вручную продублированных ключей для матери и отца. Это повышает риск рассинхронизации при изменении схемы.
- В массиве `$arrPedigreeRod` повторяется подпись «Прадед по отцу» для ключей 9 и 10, хотя соседняя последовательность предполагает разные родственные ветви. Значение требует проверки по предметной модели, автоматически исправлять его нельзя.
- Имена инфоблоков и свойств зашиты в структуру и должны совпадать с конкретной конфигурацией сайта. Перенос в универсальную заготовку исключён.

### `index.php`
- Это полноценная страница конкретного пользовательского сценария, а не заготовка компонента: прямое подключение header/footer, Bootstrap и плагина fileinput, жёсткие пути к файлам темы, константы `ADVERT_IBLOCK`, `ADVERT_ROOT_SECTION`, `ADVERT_PARENTS_IBLOCK`.
- Используются короткие PHP-теги, глобальные `$APPLICATION`/`$USER`, старый API инфоблоков и `CModule::IncludeModule()` без проверки результата.
- Идентификатор объявления читается из `$_REQUEST`; далее доступ проверяется по автору для основного элемента, но связанная модель родителей имеет отдельную ветвящуюся логику доступа. Такой сценарий требует полноценной серверной авторизации на каждой операции, а не переноса UI-кода.
- В PHP формируются фрагменты JavaScript/HTML через конкатенацию и прямые вставки значений. AJAX-ответ поиска вставляется через jQuery `.html()` после сборки строк с `val.src`, `val.breed`, `val.name`, `val.owner`, `val.id`; без контекстного кодирования это DOM-XSS-поверхность. Данные об ошибках и имени загруженного файла также передаются в HTML-контекст.
- В конфигурацию fileinput передаются URL и ID файлов; серверные обработчики `save.php` должны независимо проверять сессию, право на объявление/родительскую запись, принадлежность файла и допустимые типы/размеры. Клиентские ограничения расширений и передача sessid не являются достаточной защитой.
- Встроенный JavaScript содержит многочисленные inline-обработчики и динамические селекторы; значения, выводимые PHP внутрь JS/HTML, требуют отдельного экранирования по контексту.
- Повторяются большие блоки для матери и отца, что затрудняет сопровождение и тестирование. Нужны отдельные сервисы/DTO для чтения анкеты, проверки прав, загрузки файлов и построения формы.
- Вывод: весь каталог `Bitrix.autosave.form` исключён из переноса. Допустимо позднее спроектировать отдельный безопасный пример обработки пользовательской формы, но не на основе копирования этой реализации.
