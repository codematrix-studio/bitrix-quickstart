# Аудит standalone-скриптов и старых парсеров

**Источник:** `ASDAFF/bitrix.quickstart`, ветка `master`  
**Дата:** 2026-11-20  
**Область:** выборочные самостоятельные PHP entrypoint в `local/codes` и вспомогательный скрипт GitHub API. Архивы и сторонние библиотеки не анализировались. Код не запускался.

## Приоритетные находки

### 1. Скрипт создания административной учётной записи

Файл: `local/codes/utilities/superuser.php`.

- В исходнике зафиксированы логин и пароль.
- Скрипт напрямую вызывает `CUser::Add()` и назначает новую учётную запись в группу с ID 1.
- Проверки административной сессии, прав текущего пользователя, одноразового токена или ограничения по IP в самом файле нет.
- Комментарий прямо описывает использование скрипта как скрытого механизма восстановления доступа к сайту заказчика.

**Оценка:** критический backdoor-подобный механизм. Если файл доступен через web root, посетитель, знающий URL, потенциально может создать привилегированную учётную запись. Фактическая доступность на сервере не проверялась.

**Действие:** не размещать на сервере; удалить из рабочей ветки/публичной поставки после подтверждения владельца; если файл когда-либо был доступен в интернете — проверить журнал пользователей и входов, сменить содержащиеся в нём учётные данные и проверить их повторное использование. Значения учётных данных в этот отчёт не копируются.

### 2. Выгрузка всего каталога upload

Файл: `local/codes/upload.zip.php`.

- Подключает Bitrix prolog, но не содержит явной проверки авторизации, административной группы, CSRF или одноразового ключа.
- Архивирует весь `BASE_PATH/upload`, а не ограниченный набор файлов.
- Создаёт временный каталог с правами `0777`, архиву выставляет `0666`.
- Архив отдаётся непосредственно HTTP-ответом; временный файл удаляется после передачи.

**Оценка:** потенциальное раскрытие пользовательских загрузок и документов при прямой web-доступности. Наличие prolog само по себе не доказывает проверку доступа к этому файлу.

**Действие:** убрать из web-доступа; при реальной необходимости реализовать защищённый административный экспорт с allowlist файлов, временным хранилищем вне web root и правами минимального доступа.

### 3. SOAP endpoint старого Yandex Parser

Файлы:
- `local/codes/soap/yandexparser/server.php`
- `local/codes/soap/yandexparser/stockquote.wsdl`
- `local/codes/soap/yandexparser/api.php`
- `local/codes/soap/yandexparser/index.php`
- `local/codes/soap/yandexparser/libs/antigate.php`

Находки:
- `server.php` принимает строку SOAP-аргумента и передаёт её в `unserialize()` без `allowed_classes` и проверки структуры. При доступности endpoint это создаёт риск PHP object injection.
- В самом `server.php` нет проверки Bitrix-сессии, прав пользователя или отдельной аутентификации.
- WSDL объявляет HTTP endpoint и содержит публичный адрес сервиса.
- `api.php::curl_request()` выводит ответ внешнего сервера и вызывает `die($httpcode)` до создания DOM-документа; дальнейший код обработки недостижим. Это ломает штатный путь SOAP-обработки.
- `index.php` отражает `modelID` из `$_REQUEST` в HTML-атрибут без экранирования; возможен reflected XSS при открытии страницы с вредоносным параметром.
- `modelID` используется при формировании URL без проверки формата/диапазона.
- HTTP-запросы к внешнему источнику используют устаревший HTTP, прокси и cookie-файл; ошибки/HTTP-коды обрабатываются неполно.
- Класс `pageHelper` записывает полученный HTML в cache-файл без проверки создания каталога и без явного лимита размера ответа.
- `antigate.php` принимает API key параметром функции; сам по себе этот файл не доказывает наличие отдельного hardcoded ключа. Использование функции и реальная конфигурация ключа требуют отдельной проверки.

**Действие:** не переносить. Если endpoint когда-либо был опубликован, отключить его до проверки журналов и входных SOAP-запросов; заменить `unserialize()` на JSON/строгую схему; закрыть endpoint авторизацией и сетевым ACL; удалить отладочный вывод и завершение `die()` из HTTP-клиента.

### 4. Парсер каталога Prist/Rusgeocom и внутренний API Bitrix

Файлы:
- `local/codes/parser/bitrix-parser/core.php`
- `local/codes/parser/bitrix-parser/api/26b8zNbvmDFkLBleFxwU.php`
- `local/codes/parser/bitrix-parser/classes/Request.class.php`
- `local/codes/parser/bitrix-parser/classes/Logger.class.php`
- `local/codes/parser/bitrix-parser/app/prist.php`
- `local/codes/parser/bitrix-parser/app/rusgeocom.php`

Находки:
- В `core.php` и принимающем API находятся статические shared token и URL внутреннего API. Токен хранится в Git; точное значение не дублируется в документации.
- API проверяет POST и токен, но токен статический и хранится в двух частях интеграции в исходниках. Передача идёт по HTTP, не HTTPS.
- API записывает/обновляет элементы инфоблока ID 1, цены, свойства и изображения. Значения из внешнего парсинга сохраняются в HTML-полях; серверная очистка HTML не подтверждена.
- В `addGood()` и `updateGood()` используется `MODIFIED_BY => 1`; результат части операций с файлами/свойствами проверяется непоследовательно.
- `Request::curl()` не задаёт общий connect/total timeout, не проверяет HTTP-код и CURL error отдельно; после `curl_exec()` соединение закрывается, но детали ошибки теряются.
- Парсеры используют HTTP для внешних сайтов и не имеют надёжного контроля изменения HTML-разметки.
- `getPrice()` в `rusgeocom.php` возвращает цену из старой цены товара в поле `num`, а скидку рассчитывает как old-new; требуется проверить, соответствует ли это ожидаемому контракту импорта.
- `getData()` и `getDataTable()` фильтруют HTML регулярными выражениями, что не является надёжной HTML-санитизацией.
- В `core.php` создаётся lock-файл, но обработка исключения и очистка/освобождение блокировки в entrypoint отдельно не видны; требуется проверить библиотеку lock и завершение процессов.

**Действие:** ротация токена внутреннего API, если он когда-либо использовался/публиковался; только HTTPS + секрет из окружения/настроек вне Git; HMAC/короткоживущий токен с ротацией; строгая JSON-схема и валидация цен/ID; отдельный импортёр с dry-run и транзакционной записью.

### 5. Другие самостоятельные скрипты в `local/codes/soap`

- `soap/remains.php` и `soap/yp.php` отключают `NOT_CHECK_PERMISSIONS` и напрямую запускают `remainUpdate()` / `yandexSoap::startAgent()`. В репозитории не найдены реализации модулей `remains` и `yandexparser`; их поведение зависит от внешнего окружения. При доступности по HTTP это потенциально незащищённые триггеры тяжёлых операций.
- `soap/remainUpdater.php` жёстко задаёт `DOCUMENT_ROOT=/var/www` и запускает `remainUpdater::scanDir()`; модуль `remains` в текущем дереве не найден.
- `soap/test1.php` читает активные элементы инфоблока ID 1 и пишет CSV в текущую рабочую директорию. Явной проверки доступа в файле нет.
- `soap/test.php` запускает `CCatalog::PreGenerateXML("yandex")` после подключения prolog; явная проверка доступа в самом файле отсутствует.
- Наличие этих файлов в Git не доказывает, что они размещены в web root или доступны извне.

### 6. Старый скрипт обращения к GitHub API

Файл: `local/modules/list_repo.php`.

- В исходнике хранится статический GitHub access token и используется в заголовке запроса к GitHub API.
- Файл не содержит явной проверки авторизации/административной сессии перед выполнением запроса и выводом списка репозиториев.
- Токен не копируется в отчёт; его валидность и текущие права неизвестны.

**Действие:** проверить в настройках GitHub, существует ли токен и какие у него права; отозвать/заменить, если он ещё активен; хранить секрет вне Git и закрыть скрипт от публичного доступа.
