# Аудит общего AJAX endpoint форм

**Источник:** `ASDAFF/bitrix.quickstart`, ветка `master`  
**Дата:** 2026-11-20  
**Файл:** `local/ajax/index.php`  
**Область:** все ветви POST-обработчика, найденные формы и JS-вызовы. Код не запускался.

## 1. Контроль доступа

- Prolog подключается только если присутствует `HTTP_X_REQUESTED_WITH`.
- Затем обработчик проверяет POST и массив соответствующей формы.
- `HTTP_X_REQUESTED_WITH` — произвольный HTTP-заголовок, который клиент может выставить сам; он не подтверждает, что запрос пришёл с сайта.
- В файле не найден вызов `check_bitrix_sessid()`, проверка CAPTCHA, авторизации, rate limit или иного CSRF-токена.
- Поэтому проверка метода POST и XHR-заголовка не защищает endpoint от CSRF/автоматизированных запросов.

**Подтверждённые вызовы:** формы `CALLBACK_MODAL`, `FEEDBACK_MODAL`, `ORDER_SCHEME` отправляются на общий endpoint; обработчики находятся в `local/ajax/ajax.js`, разметка — в `local/ajax/modal/order-call.php`, `form-feedback-modal.php`, `order-scheme.php`. Эти формы не добавляют защиту, проверяемую endpoint.

## 2. Недоверенные параметры

- `SITE_ID` берётся из POST и используется в `CSite::GetByID()`/ `CEvent::SendImmediate()`; allowlist сайта и проверка обязательности отсутствуют.
- В ветках `COMMENTS`, `ORDER`, `ORDER_SCHEME` `IBLOCK_ID` берётся напрямую из POST и передаётся в `CIBlockElement::Add()`.
- Значения `NAME`, `PREVIEW_TEXT`, свойства, email, комментарии, звёзды и другие поля копируются из POST без единой схемы валидации/нормализации.
- В нескольких ветках новые элементы создаются с `ACTIVE=N`, но модерация не устраняет возможность засорения любых доступных инфоблоков невалидными записями.
- Результат `CEvent::SendImmediate()` не проверяется; endpoint возвращает `ERROR=0` независимо от фактической отправки.
- В ветках записи в инфоблок результат Add проверяется частично, но ошибки и аудит не унифицированы.

## 3. Загрузка файла VACANCIES

Ветка `VACANCIES`:
- принимает `$_FILES['FILE']`;
- строит каталог под `DOCUMENT_ROOT + SITE_DIR + images + md5(time())`;
- использует исходное имя `$_FILES['FILE']['name']) в пути назначения;
- копирует временный файл через `copy()`, не используя `move_uploaded_file()`;
- не проверяет upload error, размер, MIME, содержимое, allowlist расширений и безопасный basename;
- не проверяет результат `mkdir()`, не задаёт безопасные права и не очищает файл после ошибки.

**Оценка:** unrestricted file upload в web-доступный каталог. Если multipart filename сохраняет компоненты пути, возможен выход из созданной папки; как минимум расширение и содержимое файла не ограничены. Загрузка исполняемого файла может привести к выполнению кода, если web-сервер разрешает PHP в целевом каталоге. Это зависит от конфигурации сервера и должно быть проверено на VM.

## 4. Ветки endpoint

| Ветка | Действие | Замечание |
|---|---|---|
| `CALLBACK`, `CALLBACK_MODAL` | `CEvent::SendImmediate(CALLBACK_FORM)` | Нет CSRF/rate limit, поля события напрямую из POST |
| `FEEDBACK`, `FEEDBACK_MODAL` | `CEvent::SendImmediate(FEEDBACK_FORM)` | Нет CSRF/rate limit, нет серверной схемы полей |
| `VACANCIES` | Приём файла и отправка `VACANCIES_FORM` | Неограниченная загрузка файла в web-каталог |
| `COMMENTS` | Добавление элемента в переданный IBLOCK_ID, затем email | IBLOCK_ID и поля из POST; элемент неактивен, но endpoint можно спамить |
| `ORDER`, `ORDER_SCHEME` | Добавление элемента в переданный IBLOCK_ID и email | Нет allowlist целевого инфоблока и валидации полей |
| `CONTACTS`, `CONTACTS_MODAL`, `NETWORK` | Отправка почтового события | Нет CSRF/rate limit и ограничения размера полей |

## 5. Решение

**Приоритет — закрыть endpoint до переработки**, если он доступен извне:
1. CSRF/sessid проверять до любых операций.
2. Проверять origin/host как дополнительную меру, но не вместо CSRF.
3. Для каждой формы определить отдельную схему и allowlist SITE_ID/IBLOCK_ID.
4. Для файлов — allowlist расширений и MIME, проверка содержимого, лимит размера, basename, безопасный storage вне web root, `move_uploaded_file()`, уникальное имя и запрет выполнения скриптов.
5. Добавить CAPTCHA/antispam/rate limit для гостевых форм.
6. Возвращать JSON только после подтверждённого результата операции; логировать ошибки и request ID.
7. Для записей в инфоблоки использовать отдельный сервис с проверкой прав и модерацией.

**Итог:** endpoint имеет подтверждённые формы и JS-вызовы в текущем дереве. В его POST-ветках не найдено CSRF-проверки; одна ветка принимает файлы и сохраняет их под web root без ограничений типа/имени/размера. Фактическая доступность и конфигурация PHP handler в upload path требуют проверки на VM.
