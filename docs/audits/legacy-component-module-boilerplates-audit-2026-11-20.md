# Аудит заготовок компонентов и модулей Bitrix

**Источник:** `ASDAFF/bitrix.quickstart`, ветка `master`  
**Дата:** 2026-11-20  
**Область:** выборочный статический просмотр основных шаблонов из `local/codes/blank/components` и `local/codes/blank/modules`. Архивы и сторонние библиотеки не анализировались. Код не запускался.

## 1. Инвентаризация заготовок

В `local/codes/blank/components` есть несколько параллельных вариантов:
- `component_boilerplate` — многостраничная SEF-заготовка с основным компонентом и подкомпонентами list/edit;
- `clear.component` — минимальный процедурный компонент;
- `clear.component.d7` — class-based компонент на `CBitrixComponent`;
- `empty_component` — минимальный компонент с API D7 Application/Request;
- `super.component` и `super.component.complex` — расширенные legacy-компоненты с дополнительным кешированием, RSS, include areas и шаблонами без кеша;
- `bx-components/examples`, `example`, `mscoder`, `sorting` и другие — отдельные примеры, а не единый согласованный шаблон.

В `local/codes/blank/modules/empty.module` лежит один старый пример установщика модуля. Это не готовый современный модульный каркас.

## 2. Проверенные компоненты

### `component_boilerplate`

Файлы:
- `sample.php`
- `sample/component.php`
- `sample.edit/component.php`
- `sample.list/component.php`
- шаблоны `list.php` и `edit.php`

Назначение — многостраничная компонента с SEF-маршрутами list/edit и дочерними компонентами.

Замечания:
- используются короткие PHP-теги `<?`; для переносимого каркаса лучше везде применять `<?php`;
- параметр `SEF_FOLDER` и шаблоны маршрутов заданы в примере прямо в подключающем файле, то есть это демонстрация сценария, а не конфигурируемый модульный контракт;
- list/edit подкомпоненты фактически пустые и только подключают шаблон;
- PHPDoc, типизация входных параметров и единая политика экранирования не сформированы.

Критической уязвимости в просмотренных фрагментах не выявлено. Требуется тестирование маршрутизации и 404 на реальной версии Битрикс.

### `clear.component`

Минимальная процедурная заготовка:
- проверяет `B_PROLOG_INCLUDED`;
- инициализирует `$arResult`;
- использует `StartResultCache()` и `IncludeComponentTemplate()`.

Это наиболее простой пример, но в нём нет подготовки параметров, контракта результата, PHPDoc, логирования и обработки ошибок. Использовать только как иллюстрацию минимальной структуры, не как готовый стандарт проекта.

### `clear.component.d7`

Файлы: `class.php`, `.parameters.php`, `.description.php`, `lang/ru/class.php`, шаблон.

Подтверждённые дефекты:
- `getResult()` создаёт локальный `$arResult`, но не записывает его в `$this->arResult`; результат теряется.
- `executeComponent()` передаёт в `includeComponentTemplate()` свойство `$this->page`, которое в классе нигде не инициализируется.
- исключение выводится пользователю через `ShowError($e->getMessage())`; это может раскрывать внутренние сообщения/пути.
- нет `catch (\\Throwable)`, нормального логирования и разделения публичного сообщения от диагностического.
- `CACHE_TIME` приводится к int, но значение по умолчанию/границы не заданы.
- `.description.php` описывает компонент «Пользователи на карте», хотя сам каркас пустой.
- языковой файл `class.php` содержит пустой ключ сообщения.

**Решение:** не использовать как эталон. Исправить жизненный цикл компонента, результат, страницу и обработку ошибок до включения в новый каркас.

### `empty_component`

- Использует `Bitrix\\Main\\Application` и `Request`, но объект запроса в текущем шаблоне не используется.
- При `ID < 10` вызывается `AbortResultCache()`, после чего выполнение продолжается до `IncludeComponentTemplate()`; поведение следует пересмотреть, чтобы не продолжать обычный cache/render flow после abort.
- `$arParams['ID']` используется без предварительной нормализации/проверки наличия.
- В шаблоне подключаются JS/CSS через глобальный APPLICATION; это рабочий legacy-подход, но для нового шаблона нужно унифицировать управление assets и проверку значений.
- README содержит указание авторства Studio Fact; при переносе сохранять сведения об авторе/лицензии, пока лицензия и право на повторное использование не выяснены.

**Решение:** допустим как источник структуры, но не копировать без нормализации параметров, кеша и проверки лицензии/атрибуции.

### `super.component` и `super.component.complex`

Это не пустые заготовки, а крупные расширенные компоненты:
- отдельная логика RSS и буферизации;
- дополнительные ключи кеша и собственный путь кеширования;
- подключение `result_modifier_nc.php`/`nc.php` и `template_nc.php`;
- динамические include areas для редактирования файлов шаблона;
- обработка SEF и фильтра.

Риски/ограничения:
- значительная зависимость от старого API и глобального состояния Битрикс;
- большое число ветвей и побочных эффектов для компонента, который должен быть базовой заготовкой;
- `$mod_name` может остаться неопределённым, если оба no-cache modifier-файла отсутствуют, но затем используется при отображении include area для администратора;
- не определён строгий контракт того, какие части `$arResult` обязательны для no-cache шаблонов;
- компонент требует отдельного тестирования RSS, кеша, режима правки и no-cache ветвей.

**Решение:** не использовать как универсальный шаблон. Если функциональность действительно нужна, выделить отдельные расширения и покрыть сценарии тестами.

## 3. Проверенный модульный шаблон

Файлы:
- `local/codes/blank/modules/empty.module/install/index.php`
- `install/version.php`
- `include.php`
- `lang/ru/install/install.php`

Находки:
- `MODULE_ID` содержит заглушку `.....`, а класс установщика называется `b1team_smartfilter`; это невалидный шаблон для копирования без ручной замены идентификаторов.
- Установщик использует старый `CModule` API и не показывает современную структуру `lib/`, namespace, Composer PSR-4, D7 ORM и сервисы.
- `InstallFiles()` копирует из `/bitrix/modules/empty.module/install/components`, но в текущем дереве этого каталога/набора файлов нет; результат `CopyDirFiles()` не проверяется, метод всегда возвращает true.
- `UnInstallFiles()` рекурсивно удаляет `/bitrix/components/empty.module`; если в этой директории появятся пользовательские файлы, удаление может затронуть их.
- `DoInstall()`/ `DoUninstall()` не проверяют результаты этапов и не обеспечивают откат частично выполненной установки.
- `InstallDB()` только регистрирует модуль; SQL/ORM-схемы, миграции, агенты и обработчики событий не реализованы.
- `MODULE_VERSION_DATE` — устаревшая дата 2014 года.
- В README есть опечатка и нет полноценной инструкции по установке/удалению.

**Решение:** не переносить как готовый каркас. Для нового модуля использовать актуальную структуру с явным ID/namespace, безопасным install/uninstall, проверкой каждого этапа, сохранением пользовательских файлов, миграциями и тестами.

## 4. Общий вывод

В репозитории нет одного согласованного и проверенного стандарта компонентов/модулей. Есть несколько исторических шаблонов разного возраста и качества. Наиболее перспективные источники для нового каркаса:
1. многостраничная структура `component_boilerplate` — только как пример SEF-разделения list/edit;
2. минимальный процедурный `clear.component` — только как пример входной структуры;
3. D7 `clear.component.d7` — только как набросок class-based API после исправления ошибок.

`super.component` не должен становиться базовым компонентом из-за чрезмерной сложности и побочных эффектов. `empty.module` не пригоден в качестве установщика нового модуля.

## 5. Рекомендуемая спецификация нового каркаса

Для нового компонента:
- единый class-based стиль и поддерживаемая версия PHP;
- обязательная проверка prolog;
- `onPrepareComponentParams()` с типами, значениями по умолчанию и границами;
- `executeComponent()` с явным заполнением `$this->arResult`, корректным кешем и `AbortResultCache()`;
- отдельные методы получения данных/формирования результата;
- безопасный вывод в шаблонах и запрет на raw HTML без явной очистки;
- PHPDoc на публичных/защищённых методах, комментарии на русском;
- локализация, описание и параметры без заглушек;
- тесты на кеш, пустой результат, ошибочные параметры и 404.

Для нового модуля:
- стабильный module ID и namespace;
- install/uninstall с проверкой каждого шага и обратимостью;
- отсутствие удаления пользовательских каталогов целиком;
- миграции схемы и версионирование;
- явная регистрация/снятие событий и агентов;
- конфигурация через Option/Environment, секреты не в Git;
- PHPDoc, русская документация и автоматические проверки.

**Итог:** статический просмотр основных заготовок выполнен. Полный аудит всех 106 PHP-файлов каталога `blank/components` и всех 43 PHP-сниппетов `blank/compilation` не заявляется; сторонние примеры и runtime-поведение требуют отдельного прохода.
