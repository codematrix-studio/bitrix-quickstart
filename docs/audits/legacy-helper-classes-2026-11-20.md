## Критичные замечания безопасности

### Секреты и внешние интеграции

- `Sms.php`: в исходнике присутствуют зашитые учётные данные внешнего SMS-сервиса. Запрос отправляется по незашифрованному HTTP; разбор ответа сделан строковыми регулярными выражениями без полноценной проверки статуса/структуры. Метод `send($phone, $message)` не устанавливает переданные аргументы в свойства объекта перед формированием запроса. **Не переносить. Секреты необходимо считать скомпрометированными и заменить у провайдера.**
- `CUserRegistration.php`: в исходнике присутствует токен внешнего сервиса проверки контрагентов; отключена проверка TLS-сертификата. ID HL-блока и путь CSV жёстко зафиксированы. Нет надёжной проверки cURL-ошибок, HTTP-кода и структуры JSON до обращения к вложенным полям. **Не переносить. Токен необходимо отозвать/заменить.**
- `GeoInfo.php`: ключ внешнего геосервиса хранится в коде, используется HTTP URL, не проверяются ошибки запроса и полнота ответа. **Не переносить; интеграцию проектировать заново с конфигурацией вне репозитория и HTTPS.**

Секреты намеренно не приводятся в отчёте. Ротация выполняется в соответствующих внешних сервисах; изменение старого репозитория не производилось.

## 2. Отдельная группа `local/codes/Ns/Bitrix/Helper/`

Эта группа проверена отдельно от `local/php_interface/classes/Helper/`: у неё другая структура, собственная фабрика и динамический базовый класс.

### Архитектурные классы

- `Ns\\Bitrix\\Helper` и фабрики `User`, `Files`, `IBlock`, `Grafic`, `Session`, `Subscribe` используют публичные статические массивы экземпляров, нестрогое сравнение типа и проверки через `!`. Нет типов, PHPDoc и явного контракта ошибок. Фабрика подписки подключает модуль без проверки результата. Это самодельный service locator, а не самостоятельная универсальная функциональность.
- `HelperCore::__call()` распознаёт подстроки `with` и `get` в любом месте имени метода, молча возвращает `null` для неизвестного свойства и хранит произвольные значения в динамическом массиве. Ошибки вызова скрываются, автодополнение и статический анализ практически невозможны. Не переносить; использовать явные конструкторы/методы или DTO.

## 3. Связанные реализации и оставшиеся риски

### `HblockObject`

`local/php_interface/classes/Helper/HblockObject.php` — самостоятельная динамическая обёртка над HL-блоками. Она кэширует скомпилированные сущности в статических массивах и проксирует ограниченный список методов DataManager через `__call()`.

Замечания:
- нет проверки подключения `highloadblock` и корректности ID до обращения к таблице;
- чтение полей через `__get()` может обращаться к несуществующим полям/параметрам;
- `getParam()` преобразует результат ORM в старый `CDBResult`, что усложняет типизацию и скрывает контракт;
- `offsetSet()/offsetUnset()` меняют локальные параметры объекта без синхронизации с БД;
- `fromParams()` и `setId()` допускают невалидное состояние объекта;
- `printable_*` делает дополнительные запросы и не проверяет результат;
- используется глобальная функция `ToLower()` при проверке проксируемых методов.

**Решение:** не переносить. В новом репозитории уже есть D7-слой для HL-блоков; повторная динамическая ORM-обёртка создаст конкурирующий API. Проверить, что все нужные сценарии покрываются новым сервисом, можно на этапе интеграционных тестов.

### `Grafic\\Background`

Класс зависит от жёстко заданных ID инфоблоков и пользовательских полей, получает URL из магического состояния `HelperCore`, не проверяет подключение модуля и результат запросов. CSS собирается вручную из значений инфоблока; цвет не проверяется по формату, а URL изображения не проходит полноценную проверку допустимой схемы/контекста. Возвращаемый тип зависит от строки `type`, неизвестный тип не обрабатывается явно.

**Решение:** исключить из универсального каркаса как оформление конкретного сайта.

### `WP`

`local/php_interface/classes/Helper/WP.php` — крупный проектный фасад с разнородными обязанностями (запросы к сущностям Битрикс, работа с деревьями, геокодирование, курсы валют, CSV, логирование, форматирование, корзина/заказы и другое). Внутри присутствуют прямые внешние HTTP-запросы без надёжной обработки ошибок, самописный JSON-кодировщик (сам файл помечает его как некорректный), вывод HTML/JS и глобальные зависимости.

Отдельный риск: метод `removeIBlock()` реализует пошаговое удаление элементов, свойств, разделов и самого инфоблока. Это разрушительная операция с частичной транзакционной защитой; в ветке удаления разделов используется переменная `$data` вместо полученного массива ID, поэтому условие завершения некорректно. Вызов этого метода нельзя считать безопасной универсальной утилитой.

**Решение:** не переносить фасад. Если отдельная функция действительно нужна, выделить её в самостоятельный класс, задать контракт и тесты; разрушительные операции должны быть отдельными административными действиями с проверкой прав, подтверждением, журналированием и корректной обработкой ошибок.

### Повторная реализация регистрации пользователя

Вложенный класс `local/php_interface/classes/Helper/User/CUserRegistration.php` повторяет сценарий регистрации контрагента из `Helper/CUserRegistration.php`, включая жёсткую конфигурацию и небезопасную работу с внешним API. Обнаружены две копии одного прикладного сценария; расхождения между копиями нужно учитывать при дальнейшем анализе использования.

**Решение:** обе копии исключить из универсального переноса; не выбирать одну из них как эталон.

## 4. Промежуточная классификация

На текущем объёме проверки:

- **Прямой перенос:** кандидатов нет.
- **Переработка при подтверждённой потребности:** отдельные чистые функции (дерево массивов, форматирование, потоковый CSV, безопасный разбор URL) — только после проверки фактических вызовов и сравнения с PHP/Bitrix API.
- **Исключить как проектное/опасное:** регистрация контрагентов, SMS, геолокация, скидки конкретного магазина, фоновое оформление, подписки с самодельными токенами, фасад `WP`.
- **Не дублировать:** HL/IBlock доступ, корзину и заказ — использовать сервисы нового каркаса.
- **Требует дальнейшего просмотра:** вложенные классы `Helper/MHT`, `Helper/UserProp`, `Helper/User` и остальные файлы каталога, а также поиск фактических точек входа/автозагрузки для классов без очевидных вызовов.

Аудит остаётся незавершённым: текущие выводы относятся только к прочитанным исходникам и не заменяют полный проход по всем файлам/зависимостям.

### Отдельные блокирующие риски

1. **Выполнение внешней команды:** `ImageEditorIM` использует `exec()` с собранной вручную строкой. Это не безопасный способ передачи путей и параметров процессу; код не переносить и не использовать с пользовательскими путями.
2. **Потеря корзины:** `SaleHelper::transferBasket()` удаляет корзину получателя до переноса исходной корзины и не использует транзакцию. Риск уже отмечен в отдельном аудите Sale; здесь подтверждён на уровне helper-класса.
3. **Создание учётных записей:** `BuyOneClickHandler` создаёт пользователя с детерминированным паролем, а также содержит ошибку передачи аргументов, из-за которой email/телефон используются не по назначению.
4. **XSS:** `Content\\CSection` и `Session\\Message` выводят данные без контекстного экранирования; `Paging` позволяет собирать HTML из внешних шаблонов/URL.
5. **SQL и глобальное состояние:** `shortUrl` и `SaleHelper` используют прямой SQL; `shortUrl` дополнительно изменяет глобальный `$_GET`.
