# Аудит legacy AJAX endpoints, wishlist и парсеров

**Источник:** `ASDAFF/bitrix.quickstart`, ветка `master`  
**Дата:** 2026-11-20  
**Область:** выборочный статический просмотр `local/codes/soap/includes`, JS-вызовов, parser-компонентов. Код не запускался.

## 1. Wishlist AJAX

Файлы:
- `local/codes/soap/includes/ajax/wishlist/add_category.php`
- `add_element.php`
- `delete_category.php`
- `delete_element.php`
- `rename_category.php`
- `local/codes/soap/js/js.js`

**Подтверждённый вызов:** `js.js` вызывает `/includes/ajax/wishlist/add_element.php` методом POST и передаёт `element`, `cat`, `name`. CSRF-токен не передаётся.

Находки:
- Все endpoints подключают `prolog_before.php`, но не используют `check_bitrix_sessid()` и не ограничивают метод запроса.
- `add_element.php` не проверяет, что переданный `cat` принадлежит текущему пользователю. Если `name` пустой, этот ID напрямую используется как родительский раздел для новой записи. Это позволяет авторизованному пользователю попытаться добавлять записи в чужую категорию/раздел инфоблока 2.
- При гостевом вызове `add_element.php` создаёт пользователя с паролем из `rand()`, после чего авторизует его; подтверждение email, ограничение частоты и защита от массового создания учётных записей отсутствуют.
- `add_element.php` печатает `$_REQUEST` через `pr()` и выводит отладочные значения в AJAX-ответ; это раскрывает входные данные и ломает строгий JSON-контракт.
- `add_category.php` также создаёт пользователя для гостя через `rand()`, затем создаёт раздел в инфоблоке 2. Нет валидации/ограничения длины имени и CSRF; ответ формируется конкатенацией строки, а имя не экранируется для JSON/JS/HTML.
- `rename_category.php` проверяет `CREATED_BY` текущего пользователя, но не защищена CSRF; обновление раздела вызывается дважды; имя напрямую включается в псевдо-JSON ответ.
- `delete_category.php` использует `$USER->GetParam("USER_ID")` вместо стандартного `GetID()`; корректность этого значения зависит от контекста и требует проверки. Удаление раздела выполняется без проверки CSRF.
- `delete_element.php` ограничивает выборку инфоблоком/разделом/владельцем, но использует REQUEST без CSRF и не ограничивает метод POST.
- Параллельные вызовы и повторные клики могут создавать дубли; нет транзакций, rate limit и нормального JSON-ответа.

**Решение:** переписать endpoints как единый контроллер с POST-only, sessid/CSRF, проверкой владельца раздела для каждой операции, серверной валидацией ID/имени, криптографическим генератором, rate limit, JSON response и журналом.

## 2. Подписка

Файл: `local/codes/soap/includes/subscribe.php`; вызовы:
- HTML-форма отправляет POST на `/includes/subscribe.php`;
- `local/codes/soap/js/subscr.js` отправляет AJAX на тот же URL.

Находки:
- Подписка создаётся с `SEND_CONFIRM=N` и `CONFIRMED=Y`: email автоматически считается подтверждённым.
- Нет CSRF/sessid, rate limit и проверки частоты/повторных запросов.
- В авторизованной ветке глобальный объект `$USER` перезаписывается ID пользователя; это ломает ожидаемый тип глобальной переменной для дальнейшего выполнения страницы.
- Email и текст уведомления вставляются в JS-строку без JS-экранирования.
- Redirect использует `HTTP_REFERER` без проверки хоста/схемы.
- Ответ смешивает JS, HTML и side effects; API-контракт отсутствует.

**Решение:** подтверждение подписки только через одноразовую ссылку; CSRF, rate limit, нормализация email, безопасный JSON и allowlist redirect.

## 3. Голосование

Файл: `local/codes/soap/includes/vote.php`.

- Из POST принимаются ID элемента и тег голосования без явной проверки авторизации, sessid, метода, существования элемента в инфоблоке 9 и допустимого значения.
- Любой вызывающий может увеличивать фиксированные свойства 36/37 для выбранного элемента; возможна накрутка рейтинга.
- Счётчик обновляется read-modify-write без атомарности, поэтому параллельные запросы теряют инкременты.
- Результат `Update()` не проверяется; ответ не является полноценным JSON.

Поиск вызова этого файла в доступном дереве не дал результата. Доступность и использование на сервере не подтверждены.

## 4. Информация о заказах

Файл: `local/codes/soap/includes/user_order_info.php`.

- При авторизованном пользователе выборка заказов фильтруется по `USER_ID` текущего пользователя — это правильное ограничение области данных.
- Данные о заказах, сумме, email, фамилии и телефоне выводятся без контекстного escaping.
- В расчёте количества используется `$arItems['CNT']`, хотя выборка запрашивает только `QUANTITY`; `$kol` и `$sum_price` не инициализируются.
- Этот файл выглядит как include-фрагмент, не содержит самостоятельного bootstrap; место подключения и контекст прав нужно подтвердить.

## 5. Парсер новостей Kolesa

Файл: `local/codes/parser/parser-html-and-save-to-bitrix-iblock/parser_html_and_save_to_bitrix_iblock.php`.

- При прямом запуске подключает Bitrix prolog и импортирует до 10 записей в инфоблок ID 13; явной проверки административных прав, POST/sessid или CLI-only режима нет.
- Внешняя страница и ссылки на статьи загружаются через `file_get_contents()` без тайм-аута, контроля размера, HTTP-статуса и проверки ошибок.
- Ссылка на статью извлекается из внешней разметки и передаётся в `file_get_contents()` без allowlist домена; при изменении/компрометации источника это может привести к запросам к произвольным URL.
- Внешние заголовок/описание/полный HTML сохраняются в инфоблок как HTML без надёжной санитаризации.
- Нет дедупликации, стабильного внешнего ID, блокировки параллельного запуска и журнала результата; повторный запуск создаёт дубли.
- Добавление элементов и загрузка изображений не проверяются на успешность.
- Используются короткие PHP-теги.

**Решение:** не оставлять как доступный HTTP endpoint; перенести в CLI импортёр с allowlist домена, timeout/size limits, dry-run, deduplication, санитаризацией HTML и журналом.

## 6. Парсер CSV свойств

Файлы: `local/codes/parser/bitrix_scv_parser/parser.php`, `conf_uslugi.php`.

- Скрипт выводит конфигурацию и строки CSV в браузер; режим CLI-only и права не заданы.
- Пути к CSV зашиты в исходнике, `fopen()` для чтения/записи не проверяется, результат `fputcsv()` не контролируется.
- Имя выходного файла частично генерируется через `rand()`, есть коллизии и жёстко заданный второй путь.
- При построении таблицы замен создаётся `$PROP["REPLACE"]`, но при применении используется внешний `$replace` от последней итерации; замены могут применяться не к тому свойству.
- Проверка `strpos(..., "P_PROP") == 1` жёстко зависит от позиции маркера и не проверяет `false`.
- Нет проверки количества колонок CSV и корректности кодировки.

**Решение:** оставить как одноразовый offline migration script только после переписывания с CLI-only, конфигурацией вне кода, backup, dry-run, проверкой схемы CSV и отчётом изменений.

## 7. AJAX parser component

Файл: `local/codes/parser/Bitrix-phpQuery-ajax-step-parser/components/tools/parser/component.php`.

- Компонент имеет проверку `GetGroupRight("main") != "D"` и `check_bitrix_sessid()` для шага запуска, но операция изменяет инфоблок, каталог, цены и файлы. Проверки прав на запись в iblock/catalog в самом фрагменте не видны.
- URL источника берётся из параметра компонента и используется через `file_get_contents()`; отсутствуют allowlist host/scheme, timeout и проверка размера/HTTP-ответа.
- Пишет в фиксированные IBLOCK_ID/SECTION_ID, устанавливает `MODIFIED_BY=1`; параметры и целевые ID не оформлены как проверяемый контракт.
- Данные внешнего HTML сохраняются в `DETAIL_TEXT` как HTML без надёжной санитаризации.
- Результаты Add/Update/CPrice::Add/CCatalogProduct::Add проверяются неполно; нет транзакции и идемпотентного обновления цены/товара.
- JS-ответы собираются вручную; требуется отдельная проверка escaping для всех динамических данных.

**Решение:** не переносить как есть. Требуется отдельный permission model для импорта, allowlist URL, строгая схема данных, dry-run, журнал и транзакционная синхронизация.
