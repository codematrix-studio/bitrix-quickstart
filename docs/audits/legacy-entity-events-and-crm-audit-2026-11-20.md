# Аудит legacy-классов Entity, событий и вспомогательного импорта

**Источник:** ASDAFF/bitrix.quickstart, ветка master  
**Область:** `local/php_interface/classes/CHelper1C.php`, `CIBlockPropertyCRM.php`, `Entity/*`, event handlers и `local/php_interface/include/handlers.php`  
**Дата проверки:** 2026-11-20  
**Статус:** статический просмотр перечисленных файлов и регистраций выполнен; фактические значения БД/агентов и runtime не проверялись. Перенос не выполнялся.

## 1. Регистрация событий — что действительно подключено

`local/php_interface/init.php` подключает Composer autoload, конфиги, `include/handlers.php` и `include/adm_tools.php`, если файлы существуют.

В `include/handlers.php` подтверждены регистрации:
- `main:OnPageStart` → `OnPageStart::authEmailClass`;
- `main:OnAfterEpilog` → `Urlrewrite::OnAfterEpilog`;
- `main:OnBeforeEventAdd` → `OnBeforeEventAdd::CEshopEmailFieldsHandlers`;
- `sale:OnOrderNewSendEmail` → `OnOrderNewSendEmail::bxModifySaleMails`;
- `main:OnEpilog` → `EventHandler::OnEpilogHandler`.

Это подтверждает регистрацию обработчиков в коде init, но не подтверждает фактический вызов на конкретном сайте: для этого нужны успешная загрузка классов, состояние init и runtime.

Не обнаружена регистрация:
- `OnBeforeBasketAdd::OnBeforeBasketAdd` из `OnBeforeBasketAdd.php`;
- `OnBeforeUserRegister::OnBeforeUserRegisterHandler` из `OnBeforeUserRegister.php`;
- отдельного `OnEpilog::OnEpilogHandler` из `OnEpilog.php`.

Указанные файлы не следует считать активными обработчиками только по факту существования. В репозитории есть другие регистрации событий с похожими именами (в том числе в модулях); это отдельные реализации.

## 2. Обработчики, зарегистрированные в init

### OnPageStart.php — авторизация по email

- Обращается к `$_REQUEST['USER_LOGIN']` без проверки наличия ключа; при обычном запросе без поля возможны notice/warning.
- Для поиска применяет `htmlspecialcharsbx()` к email, хотя это HTML-экранирование, а не нормализация идентификатора. Затем сравнивает исходный email с найденным значением строго и с учётом регистра.
- Перезаписывает одновременно `$_POST['USER_LOGIN']` и `$_REQUEST['USER_LOGIN']`; это глобальная мутация входного запроса в раннем событии.
- Нет явного контроля количества совпадений/неоднозначности email. Используется `GetNext()` и берётся первая запись.
- Сам обработчик не выполняет авторизацию, а только подменяет логин для дальнейшего штатного механизма. Это важно не трактовать как самостоятельный обход пароля.

### Urlrewrite.php — пересортировка правил URL

- Обработчик запускается на `main:OnAfterEpilog`; на каждом таком событии создаётся объект и вызывается проверка хэша.
- Конструктор вызывает `init()`, который создаёт каталоги `/upload/logs` и `/upload/tmp` без проверки результата `mkdir()`, читает служебный hash-файл и подключает `/urlrewrite.php`.
- При расхождении хэша файл `urlrewrite.php` перезаписывается напрямую через `file_put_contents()`, без временного файла, атомарного rename и блокировки. Параллельные запросы могут одновременно выполнять пересортировку/запись.
- Служебный hash-файл также записывается без блокировки и проверки результата.
- `_sort()` меняет порядок по SORT; при равных значениях comparator возвращает только -1 или 1, даже для равных условий. Это нарушает контракт сортировки (не возвращает 0).
- `_prepareText()` сериализует правила в PHP-код и полагается на глобальную `EscapePHPString()`; определение/гарантированная загрузка функции в просмотренной области не подтверждены.
- `_prepareText()` в пустой ветке обращается к неопределённой `$sAllLogMessage`.
- `_generateHash()` не проверяет `hash_file()`; `_getHashFile()` не проверяет существование/чтение файла.
- Логирование использует имя файла, собранное конкатенацией, и запись без проверки результата. В текущем вызове имя задано литералом, но публичный метод `logging()` принимает произвольное имя.
- Включение существующего `urlrewrite.php` исполняет PHP-файл; это ожидаемая механика самого Bitrix, но дополнительно повышает последствия некорректной генерации/порчи файла.

**Решение:** не переносить как есть. Сортировку лучше выполнять на этапе сборки/администрирования, а не в каждом запросе. Если функция необходима, нужна блокировка, атомарная запись, безопасная сериализация и тесты на параллельные вызовы.

### OnBeforeEventAdd.php — расширение полей писем заказа

- Читает `$arFields['ORDER_ID']` без проверки наличия ключа.
- Вызывает `CSaleOrder::GetByID()` до явного подключения модуля sale; подключение выполняется позже и только в ветке `SALE_NEW_ORDER`.
- Результаты `GetByID()`, `CSaleLocation::GetByID()` и `CSaleOrderPropsVariant::GetByValue()` не проверяются перед чтением полей.
- Данные свойств заказа добавляются в массив почтовых полей без единого контракта экранирования. Необходимо проверить шаблоны писем и контекст вывода, прежде чем классифицировать это как XSS.
- Условие `AND` написано как логический оператор PHP в верхнем регистре; синтаксически допустимо, но стиль не единообразен.

### OnOrderNewSendEmail.php — поля письма о новом заказе

- Вызывает Sale API без явной загрузки модуля в самом обработчике; работоспособность зависит от контекста события и порядка загрузки модулей.
- Не проверяет результат `CSaleOrder::GetByID()` и `GetOrderProps()`.
- `$email` присваивается только при наличии свойства EMAIL, но далее в показанном фрагменте не используется.
- Экранируются PHONE/FIO/EMAIL через `htmlspecialchars()`, но INDEX и ADDRESS не экранируются; корректность зависит от шаблона письма и ожидаемого контекста.
- Не проверяется результат получения службы доставки/платёжной системы.

### EventHandler.php — обработка 404

- Зарегистрирован как `main:OnEpilog`.
- Проверяет, что запрос не в ADMIN_SECTION, определены ERROR_404/PATH_TO_404 и файл существует.
- Подключает шаблонные header/footer по `SITE_TEMPLATE_PATH`, страницу 404 по PATH_TO_404; путь формируется из серверных/константных значений. Нужна runtime-проверка корректности этих значений и совместимости с шаблонами.
- Есть отдельный неиспользуемый в `handlers.php` класс `OnEpilog.php`, который жёстко подключает шаблон `/bitrix/templates/404` и `/404.php`. Не смешивать его с реально зарегистрированным `EventHandler`.

## 3. Файлы обработчиков, для которых регистрация не найдена

### OnBeforeBasketAdd.php

- По точному поиску по текущему репозиторию регистрация именно этого класса не найдена.
- Логика изменяет цену корзины на основе процента из модуля `tc` и пользовательского поля `UF_CARD`.
- Результат `CModule::IncludeModule('tc')`, чтения пользователя, `tcCards::GetByNum()` и выборки карты не проверяется.
- Нет проверки диапазона скидки/процента, валидности цены и валюты; если процент ошибочен, цена может стать отрицательной.
- Присваивает `CALLBACK_FUNC = ''`; влияние на дальнейший расчёт цены зависит от конкретной версии Sale и требует стендовой проверки.
- Не переносить, пока не подтверждена потребность и не восстановлена фактическая регистрация/контракт скидки.

### OnBeforeUserRegister.php

- Точная регистрация этого класса в просмотренных обработчиках не найдена.
- Метод отправляет LOGIN, PASSWORD, EMAIL, NAME, LAST_NAME через `CEvent::Send("REG", "s1", ...)`. Передача пароля в почтовый шаблон — критичный дефект безопасности, даже если обработчик сейчас не зарегистрирован.
- SITE_ID жёстко задан как `s1`; результат отправки не проверяется.
- Не переносить. Пароли не должны передаваться по почте; использовать штатное подтверждение/восстановление доступа.

### OnEpilog.php

- Регистрация в `handlers.php` не найдена; вместо него зарегистрирован `EventHandler::OnEpilogHandler`.
- Жёстко использует шаблон `404` и путь `/404.php`, не проверяет существование подключаемых файлов.
- Дублирует функциональность 404-обработчика, но с другим контрактом и без проверки ADMIN_SECTION/PATH_TO_404.
- Не переносить как отдельный обработчик без подтверждения внешней регистрации.

## 4. CHelper1C.php

- `agent1c()` немедленно возвращает строку `"agent1c();"`; весь код импорта после return недостижим. В текущем виде агент бесконечно планирует сам себя, но не выполняет импорт, если вызывается стандартным механизмом агента.
- Недостижимый код обращается к каталогу `/upload/1c_catalog/`, вызывает `scandirs()`, подключает модуль catalog и включает относительный путь `../components/devteam/catalog.import.1c/inc.php`.
- В коде используются неинициализированные `$NS` и `$arParams`; путь require зависит от текущей рабочей директории.
- Не проверяются результаты открытия файлов, импорта, удаления; временные таблицы сбрасываются/создаются для каждого файла, что опасно при параллельных запусках.
- Поиск по точному имени класса обнаружил только определение; регистрация агента/вызов не подтверждены.

**Решение:** не запускать и не переносить. Сверить наличие зарегистрированного агента в БД; если нужен файловый импорт, использовать отдельную блокируемую задачу с проверкой файлов и результатов.

## 5. CIBlockPropertyCRM.php

- Тип свойства зарегистрирован в `local/php_interface/include/adm_tools.php` через `iblock:OnIBlockPropertyBuildList`. Это подтверждает регистрацию типа в коде.
- `GetPropertyFieldHtml()` вставляет название компании CRM в HTML option без HTML-экранирования; название может содержать HTML/кавычки и привести к stored/reflected XSS в административной форме.
- Не экранируются значения `$strHTMLControlName['VALUE']` и значение из `$_REQUEST` при формировании select name/selected state.
- `GetFilterHTML()` читает `$_REQUEST[$key]` без проверки ключа/типа.
- Кеш общий для всех сайтов/пользователей с одним ID `CIBlockPropertyCRM`, TTL 3600; нет теговой инвалидации при изменении компаний. Возможны устаревшие названия.
- `InitCache()` и `StartDataCache()` используются без стандартной проверки состояния кеша/разделения ветвей; требуется проверить поведение при cache miss/hit.
- Зависимость от CRM опциональна: при отсутствии модуля список пустой. Фактическое наличие CRM и значений свойства в БД не подтверждено.

**Решение:** не переносить без переработки HTML-экранирования, кеша и контракта поля.

## 6. Entity-классы

### Entity/CurrencyCbr.php

- Внешний XML загружается через `simplexml_load_file()` без таймаута, проверки HTTP-статуса, размера и результата парсинга.
- Ошибка сети/невалидный XML может привести к обращению к свойству у false/null.
- Курс записывается в `b_option` через Option::set без проверки значений/результата и без отметки времени/источника.
- URL задан константой, поэтому SSRF через аргумент публичного метода не подтверждён; однако `parseXmlCbr($sUrl)` protected и принимает произвольный URL для наследников.
- Поиск не подтвердил внешние вызовы `addCurrencyRates()`; наличие агента/cron требует проверки БД.

### Entity/HLNumbersContracts.php

- Жёстко задан HL-блок ID 2; результат IncludeModule/getById/compileEntity не проверяется.
- Публичный `clearTable()` вызывает `truncateTable()` для таблицы HL-блока. Это разрушительная операция без подтверждения, проверки прав, резервной копии или отдельного административного контракта.
- `clearTable()` после truncate трактует результат как boolean, а в ветке ошибки вызывает `getErrorMessages()` у значения, которое может быть boolean.
- `add()` не проверяет наличие/тип UF_NUMBER, пустое значение и дубли; результат может быть непредсказуем при некорректном вводе.
- `prepareNumber()` удаляет неалфавитно-цифровые символы только по краям, не нормализует внутренние пробелы/разделители и не задаёт явную кодировку Unicode.
- Логирование выключено через `if (false)`; путь лога задан относительным `../logs/`.
- Статический поиск не подтвердил внешнее использование класса; до проверки БД/кода вызова считать `clearTable()` опасным API, не вызывать.

### Entity/HLSearchProgram.php

- Жёстко задан HL ID 1; результат загрузки/компиляции HL не проверяется.
- `add()` выполняет SELECT, затем INSERT/UPDATE без транзакции/атомарного инкремента; параллельные запросы могут потерять увеличение счётчика или создать дубли.
- Для существующей записи обновляется только UF_COUNTER; дата создания/обновления формируется строкой через date() и зависит от пользовательского формата HL-поля.
- Нет проверки обязательных полей/типа UF_QUERY; нет ограничения длины.
- Внешние вызовы не подтверждены точным поиском.

### Entity/Metro.php

- Зависит от внешнего `Defa\\Core\\Tools\\CIblock`; источник/автозагрузка этой зависимости в рамках текущего фрагмента не подтверждены.
- Не проверяется результат IncludeModule и получение ID инфоблоков по кодам.
- `getListById($id)` принимает произвольный формат ID; пустой массив/строка проверяется через empty(), но контракт типа не задан.
- При станции без корректной привязки к линии чтение `$arLines[$id]['NAME']` и COLOR может дать undefined index.
- Singleton не даёт возможности явно передать контекст/ID инфоблоков; кеширования нет.

### Entity/PageDates.php

- Конструктор публичный, хотя есть singleton; каждый прямой new вызывает запрос к инфоблоку.
- Зависит от `Defa\\Core\\Tools\\CIblock` и глобального `$APPLICATION`; нет проверки наличия объекта APPLICATION.
- Ищет запись по NAME, равному текущему каталогу, и берёт первую запись; неоднозначность URL/страницы не обрабатывается.
- Даты парсятся через DateTime и отбрасывают будущие даты; формат/часовой пояс не заданы явно.
- `Loc` импортирован, но в классе не используется.
- Внешние вызовы `getInstance()` точным поиском не подтверждены.

## 7. Решение по переносу

- Не переносить эти классы без отдельной переработки.
- Особенно опасный API `HLNumbersContracts::clearTable()` не должен попасть в публичный сервисный интерфейс без явного административного сценария и защиты.
- `CHelper1C::agent1c()` в текущем виде ничего не импортирует.
- Тип `CIBlockPropertyCRM` зарегистрирован, поэтому перед его удалением/заменой обязательно сверить свойства в БД и сохранённые значения.
- Зарегистрированные event handlers (OnPageStart, Urlrewrite, OnBeforeEventAdd, OnOrderNewSendEmail, EventHandler) имеют runtime-последствия и требуют стендовой проверки после статического исправления.
- Незарегистрированные классы OnBeforeBasketAdd/OnBeforeUserRegister/OnEpilog не считать активными без проверки других источников регистрации.

## Итог

В init подтверждены пять регистраций обработчиков; не все одноимённые классы активны. Найдено несколько функционально опасных мест: runtime-перезапись `urlrewrite.php` без блокировки, передача пароля в почтовое событие в незарегистрированном классе, потенциальный stored XSS в CRM user type, публичная очистка HL-таблицы через TRUNCATE и агент 1С с немедленным return. Внешние вызовы Entity и регистрация агентов не подтверждены. До сверки БД/runtime прямой перенос исключён.
