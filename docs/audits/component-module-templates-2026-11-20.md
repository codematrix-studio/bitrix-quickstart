Проверена структура `local/codes/blank/components/` и `local/codes/blank/modules/`, а также исходный код основных заготовок: пустые классические и D7-компоненты, комплексные компоненты, компонентные примеры и пустой модуль.

Старый репозиторий не изменялся. В новый репозиторий на этом этапе добавляется только отчёт аудита. Перенос исходников не выполнялся.

Архивы `empty.component.7z` и `hello.component.7z` присутствуют в каталоге, но не анализировались как исходный код: содержимое бинарных архивов через просмотр текстовых файлов GitHub недоступно. Перед переносом их нужно отдельно распаковать и проверить либо исключить.

## 3. Замечания по качеству

### 3.1. Классический пустой компонент

`clear.component/component.php` — минимальная и понятная отправная точка. Однако используются короткие PHP-теги, старый синтаксис массивов и отсутствует PHPDoc. Не описаны параметры, структура результата и контракт компонента.

**Решение:** оставить один лаконичный классический шаблон для совместимости со старым API, привести к единому стилю PHP и добавить русскоязычный PHPDoc там, где он несёт смысл.

### 3.2. D7-заготовка

В `clear.component.d7/class.php` обнаружены проблемы:

- `getResult()` создаёт локальный массив, но не записывает результат в `$this->arResult`;
- `$this->page` используется при подключении шаблона, но в классе не инициализируется и не определяется;
- метод `getResult()` объявлен `protected`, но контракт его результата не определён;
- обработчик исключений ограничен `Exception`, не описан ожидаемый способ отображения ошибок;
- `CACHE_TIME` приводится к целому числу без полноценной нормализации и согласования с параметрами кеширования компонента;
- описание компонента говорит о карте пользователей, хотя это пустая заготовка;
- PHPDoc частичный: нет типов параметров и возвращаемых значений у публичных методов, комментарии описывают действие, но не контракт.

**Решение:** это кандидат на основной шаблон D7-компонента, но только после переработки. Нужно определить понятный поток: подготовка параметров → проверка зависимостей → получение данных → заполнение `arResult` → кеширование → подключение шаблона.

### 3.3. Комплексные компоненты

В `super.component.complex` и `component_boilerplate` есть рабочие идеи по SEF-маршрутам, алиасам и выбору дочерней страницы. При этом код использует старые функции и не везде валидирует входные параметры. В boilerplate обработка 404 и построение URL смешаны с маршрутизацией.

**Решение:** подготовить самостоятельный компактный каркас комплексного компонента с SEF и не-SEF режимами, явным списком маршрутов, нормализацией параметров и PHPDoc для структуры переменных маршрута. Не переносить старую реализацию целиком.

### 3.4. Расширенные компоненты списка

`standard.elements.list` содержит полезные концепции: отдельные этапы выполнения, проверку модулей, постраничную навигацию, ключи кеша и получение ID инфоблока. Но выявлены существенные недостатки:

- прямое чтение `$_REQUEST` внутри нормализации параметров;
- небезопасная/непредсказуемая сборка кеш-идентификатора через `serialize($this->arParams)`;
- обращения к глобальному `$USER` без проверки объекта;
- смешение вычисления параметров, кеширования, запроса к инфоблоку и AJAX-ответа;
- вызов `die()` из компонента;
- управление тегированным кешем через глобальные статические вызовы;
- потенциально некорректная работа с переменными маршрута в соседнем `standard.elements`;
- PHPDoc местами неполный и содержит неточные типы (например, `array()` как тип свойства и общие `mixed` без описания структуры).

В `main.block.team` есть опечатка в ключе `widht` и некорректная обработка результата `CFile::ResizeImageGet()`: далее ожидается строка, хотя метод возвращает структуру данных. Кроме того, компонент наследуется от конкретного примера списка и потому не является самостоятельной заготовкой.

**Решение:** не переносить эти классы в текущем виде. При необходимости сделать отдельный учебный пример выборки элементов, но не строить на нём базовую архитектуру всех компонентов.

### 3.5. Универсальный super-компонент

`super.component` объединяет RSS, кеширование, подключение файлов вне кеша, административные иконки и возврат значения. Это слишком специфичный и сложный контракт для пустого шаблона. Используются глобальные переменные, прямой доступ к `$_SERVER`, ручная сборка URL административного редактора и динамическое подключение файлов по путям из результата.

**Решение:** не переносить. Отдельные приёмы можно документировать как необязательные рецепты, если появится подтверждённая потребность.

### 3.6. Пустой модуль

В `empty.module/install/index.php` класс называется `b1team_smartfilter`, а идентификатор модуля оставлен в виде заглушки `.....`. Код использует устаревший стиль объявления свойств и методов. Установка файлов обращается к каталогу `install/components`, наличие которого в каркасе не подтверждено; удаление файлов выполняется по жёстко заданному пути. Методы установки/удаления не проверяют результат операций и не обеспечивают безопасный откат при ошибке. Нет полноценной структуры классов модуля, автозагрузки, конфигурации и описания зависимостей.

**Решение:** не переносить реализацию. Создать новый каркас модуля с корректным идентификатором, метаданными, автозагрузкой, install/uninstall, регистрацией событий и файлов, локализацией и безопасной обработкой ошибок. Установщик должен удалять только принадлежащие модулю файлы.

## 4. Требования к PHPDoc и комментариям при переносе

PHPDoc — обязательная часть критериев приёмки, а не декоративное оформление.

Для каждого переносимого шаблона:

- PHPDoc на русском языке для классов и публичных/защищённых методов;
- типы параметров и возвращаемых значений должны соответствовать фактическому контракту;
- для массивов описывать форму данных через shape-аннотации, если это повышает ясность;
- описывать исключения, побочные эффекты и требования к загруженным модулям;
- свойства документировать там, где тип нельзя выразить нативным объявлением или он неочевиден;
- комментарии оставлять для объяснения причин и нетривиальных решений, а не пересказывать очевидный код;
- не добавлять ложный PHPDoc ради количества строк;
- примеры использования и инструкции в README писать на русском языке.

## 5. Рекомендуемый состав нового набора

Предлагается не переносить старые каталоги один к одному, а собрать небольшой согласованный набор:

1. **Классический компонент** — минимальный совместимый шаблон на `component.php`.
2. **D7-компонент** — основной рекомендуемый вариант на `CBitrixComponent`.
3. **Комплексный компонент** — SEF и не-SEF маршрутизация, список/детальная страница.
4. **Компонент с выборкой инфоблока** — отдельный пример, не обязательная основа каждого компонента.
5. **Модуль** — полный каркас с install/uninstall и автозагрузкой.
6. **Расширенный модуль** — пример сервисов, событий и ORM, только после проверки совместимости с поддерживаемыми версиями Bitrix.

Для каждого шаблона нужны README на русском языке, назначение, минимальные требования, порядок копирования/переименования и список точек, которые разработчик обязан настроить.

## 6. Что переносить и что исключить

**Кандидаты на переработку:**
- `clear.component`;
- `clear.component.d7`;
- `component_boilerplate` (только структура комплексного компонента);
- `example/compsimple` (только идеи разделения ответственности);
- `empty.module` (только как перечень ожидаемых файлов, не как исходный код установщика).

**Не переносить как готовые заготовки:**
- `super.component`;
- `super.component.complex` без полной переработки;
- `standard.elements` и `standard.elements.list` без переработки;
- `menu`, `sorting`, `main.block.team` — это функциональные примеры, не пустые каркасы;
- архивы `.7z` до отдельной проверки содержимого.

## 7. План следующего этапа

1. Утвердить по результатам аудита состав набора: классический компонент, D7, комплексный компонент и модуль.
2. Сверить целевые шаблоны с текущими стандартами проекта и поддерживаемой версией PHP/Bitrix.
3. Создать отдельную ветку переноса, не затрагивая `main`.
4. Реализовать шаблоны заново на основе проверенных идей, а не копированием старого кода.
5. Добавить русскоязычные README, PHPDoc и примеры.
6. Выполнить статическую проверку PHP-синтаксиса и доступные автоматические тесты.
7. Отдельно провести проверку установки/вызова шаблонов на Bitrix-стенде, когда стенд освободится.

**Итог:** в старом репозитории есть полезная база, но ни один из расширенных шаблонов нельзя безопасно переносить без переработки. Наиболее ценные заготовки — минимальный классический компонент, D7-компонент, структура комплексного компонента и модульный каркас.
