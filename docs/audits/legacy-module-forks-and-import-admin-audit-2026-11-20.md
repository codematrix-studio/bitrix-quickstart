# Аудит fork-модулей site.main / indi.main и административного импорта

**Источник:** `ASDAFF/bitrix.quickstart`, ветка `master`  
**Дата:** 2026-11-20  
**Область:** сравнение структуры `site.main` и `indi.main`, установщиков и административных импортёров. Сторонние библиотеки не анализировались; код не запускался.

## 1. Сравнение модулей

Статистика по Git tree:
- `local/modules/site.main`: 1 096 файлов;
- `local/modules/indi.main`: 623 файла;
- совпадающие относительные пути: 503; из них 371 имеют одинаковый blob SHA и 132 различаются;
- только в `site.main`: 593 файла;
- только в `indi.main`: 120 файлов.

Это не две идентичные копии с заменой namespace. Модули разошлись по функциональности и составу.

Примеры:
- `site.main/lib/user.php` содержит методы регистрации/обновления пользователя и дополнительные обработчики; `indi.main/lib/user.php` короче и не содержит этих методов.
- `site.main/lib/module.php` регистрирует обработчики регистрации/обновления пользователя и другие события; `indi.main/lib/module.php` имеет другой набор обработчиков, включая 404 и поиск.
- `site.main/options.php` и `indi.main/options.php` имеют разные настройки.
- `indi.main` содержит `lib/import.php`, `lib/util.php`, продуктовые сущности и специфичные HL-блоки; соответствующего `Site\\Main\\Import` в `site.main/lib` не найдено.

**Решение:** не объединять модули механической заменой namespace и не копировать файлы между ними без отдельного анализа контрактов, событий, таблиц и установочных сценариев.

## 2. Установщик site.main и сломанный маршрут импорта

Установщик `local/modules/site.main/install/index.php` копирует каталог `install/admin` в `/bitrix/admin`.

При этом:
- `local/modules/site.main/install/admin/indi_data_import.php` содержит только require файла `/local/modules/site.main/admin/site_data_import.php`;
- файла `local/modules/site.main/admin/site_data_import.php` в Git tree нет;
- следовательно, установленный административный endpoint ссылается на отсутствующий файл, если только его не создаёт внешний процесс вне репозитория;
- альтернативный файл `local/modules/site.main/admin/indi_data_import.php` в установщик не копируется и сам использует `Site\\Main\\Import::importRequsetManage()`;
- класса `Site\\Main\\Import` в исходниках `site.main/lib` не найдено.

**Вывод:** штатный import endpoint `site.main` по содержимому репозитория не завершён/нерабочий. Проверить на VM, не существует ли отсутствующий файл как локальная незакоммиченная модификация.

## 3. Административный импорт indi.main

Файлы:
- `local/modules/indi.main/install/admin/indi_data_import.php` — wrapper на основной admin script;
- `local/modules/indi.main/admin/indi_data_import.php` — основной обработчик;
- `local/modules/indi.main/lib/import.php` — класс Import.

### 3.1. Порядок проверки CSRF

В `admin/indi_data_import.php`:
1. принимается загруженный файл;
2. выполняется работа с путём/сессией и `move_uploaded_file()`;
3. вызывается `Import::importRequsetManage($_REQUEST)`;
4. только после этого проверяется `check_bitrix_sessid()`.

Таким образом, проверка CSRF расположена после side effects. Класс `Import` сравнивает переданный `sessid` со значением в `$_SESSION[$service]`, но при первом запросе сам получает объект и записывает переданный sessid в сессию; это не заменяет проверку текущего Bitrix sessid.

### 3.2. Загрузка файла

- Имя/расширение файла берутся из `$_FILES['inputFile']['name']`; нет allowlist расширений XML/XLS, проверки MIME, размера, upload error и безопасного имени.
- Конечный путь строится в публичном `/upload/` с именем на основе `time()`; возможны коллизии.
- `file_get_contents($uploadFile)` вызывается до `move_uploaded_file()`, то есть читается ещё не размещённый файл; результат записывается в `$_SESSION['xml_uploadfile']`.
- Ошибка перемещения выбрасывается после чтения; дальнейшая обработка не имеет полноценного recovery/cleanup.
- Не проверяется, что конечный путь остаётся в ожидаемом каталоге и что расширение безопасно для web-доступа.

### 3.3. Логика Import

- `importRequsetManage()` ограничивает тип сервиса switch-ветками `import_news` и `import_catalog`, но не валидирует размер `limit` и диапазон `lastIndex`.
- Возможны деление на ноль при пустом наборе, некорректный прогресс и обращение к отсутствующим элементам.
- `getImportObject()` проглатывает `Exception` без логирования и может вернуть неинициализированный `$importObject`.
- `getProducts()` поддерживает только XML/XLS, но не проверяет результат определения типа и парсинга.
- `importNew()` и `importProduct()` в текущем коде пустые заглушки; `getNews()` возвращает демонстрационные записи с повторяющимися CODE. Следовательно, заявленный импорт новостей/товаров в этом классе фактически не реализован.
- Обрабатывается только `\\Exception`, не `\\Throwable`; результаты отдельных операций и очистка сессии/временных файлов контролируются неполно.

### 3.4. Права

- Проверяется право на модуль `main`, но в обработчике не видна отдельная проверка прав записи на целевые инфоблоки/каталог.
- CSRF проверка после импорта не обеспечивает защиту операции.
- Endpoint административный, но не следует считать наличие admin prolog достаточной проверкой права на конкретную операцию импорта.

**Решение:** не использовать как готовый импортёр. Для замены: POST-only, проверка sessid до любых side effects, отдельные operation permissions, allowlist типов/размера, приватное временное хранилище, проверка MIME/расширения, JSON-контракт, ограниченный batch size, dry-run, журнал и очистка временных файлов.

## 4. Общие дефекты установщиков обоих модулей

- `installDB()` и `unInstallDB()` вызывают `RunSQLBatch()`, но игнорируют результат и всегда возвращают true.
- `installFiles()` игнорирует результаты `CopyDirFiles()` и всегда возвращает true.
- `DoInstall()` может зарегистрировать модуль при неуспешной установке SQL/файлов, поскольку методы возвращают true независимо от результата.
- `unInstallFiles()` возвращает true, но не удаляет установленные файлы; после удаления модуля могут остаться admin scripts, компоненты, шаблоны и cron-файлы.
- Копирование в `/local/components` выполняется с `rewrite=true`, что может перезаписать существующие компоненты при установке.
- Документация/комментарии в части файлов имеют повреждённую кодировку.

## Итог

`site.main` и `indi.main` — отдельные расходящиеся ветки модульной логики. Установочный импорт `site.main` ссылается на отсутствующий файл, а импорт `indi.main` проверяет sessid после операций с файлом и вызова импортёра; сам Import содержит незаполненные методы. Установщики обоих модулей не проверяют результаты SQL и копирования файлов.

Код не запускался и не изменялся. Нужна проверка фактического deployment на VM, особенно наличия отсутствующего `site_data_import.php`, состояния файлов после install/uninstall и прав групп.


## 6. Общие install targets

site.main и indi.main копируют файлы в одинаковые target directories. Для doc_root, templates, php_interface, cron, admin и js используется rewrite=false; для components — rewrite=true.

Это создаёт конфликт:
- оба модуля поставляют собственный /ajax/index.php;
- оба копируют свои шаблоны в /local/templates/main;
- первый установленный модуль сохраняет уже скопированные файлы, а второй не обновляет их;
- компоненты с одинаковыми путями могут, наоборот, перезаписываться.

Итоговое состояние зависит от порядка установки и обновления модулей. Проверить фактический router и /local/templates/main на VM обязательно.
