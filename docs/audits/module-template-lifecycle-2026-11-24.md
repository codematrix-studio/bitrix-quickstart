# Аудит базовой заготовки модуля и жизненного цикла

**Дата:** 2026-11-24  
**Проверенный код:** `templates/modules/basic` в `main`  
**Граница:** статический анализ исходников и smoke-тестов; ядро Битрикс и реальная установка не запускались.

## 1. Итог

Базовая заготовка пригодна как каркас простого собственного модуля после замены идентификатора, класса установщика и namespace. Подтверждённых дефектов в просмотренном install/uninstall flow не найдено.

Она покрывает:
- регистрацию модуля перед выполнением его install-этапов;
- последовательные этапы БД, событий и файлов;
- откат начатых этапов в обратном порядке;
- сохранение регистрации и маркера незавершённой установки, если откат не удался;
- повторный запуск восстановления;
- безопасный no-op при повторной установке уже исправного модуля;
- удаление регистрации только после успешных uninstall-этапов;
- проверку администратора в `DoInstall()` и `DoUninstall()`.

## 3. Что подтверждено

### Установка

1. Перед операциями проверяется `$USER->IsAdmin()`.
2. Если модуль ещё не зарегистрирован, он регистрируется до вызова `InstallDB()`, `InstallEvents()` и `InstallFiles()`. Это соответствует описанному в документации Bitrix порядку: собственный код модуля должен быть доступен после регистрации.
3. Этап записывается в список начатых до вызова метода. Поэтому при частичном выполнении и возврате `false` или исключении вызывается обратный метод этого этапа.
4. Откат выполняется в обратном порядке.
5. Если откат успешен при первой установке, регистрация снимается. Если откат не завершился, модуль остаётся зарегистрированным с опцией `INSTALLATION_INCOMPLETE=Y`; повторная установка может восстановить ресурсы.
6. Повторный вызов для установленного модуля без маркера восстановления не повторяет этапы.

### Удаление

1. Проверяется администратор.
2. Файлы удаляются раньше обработчиков событий и данных БД.
3. При ошибке следующий этап не выполняется, регистрация остаётся.
4. Регистрация снимается только после успешного завершения этапов удаления.

Это безопаснее безусловного удаления всего каталога партнёра: методы `UnInstallFiles()` и `UnInstallDB()` должны удалять только ресурсы, которыми владеет модуль.

## 4. Ограничения и незакрытые сценарии

Это не дефекты текущего базового каркаса, но границы его назначения:

- В `InstallDB()`/`UnInstallDB()` пока нет схемы таблиц или миграций.
- В `InstallEvents()`/`UnInstallEvents()` нет конкретных регистраций; симметрию обработчиков нужно реализовать в самом модуле.
- Нет регистрации/удаления агентов.
- Нет примера копирования публичных компонентов, административных файлов, JS/CSS или других файлов за пределами каталога модуля.
- Нет сценария обновления уже установленной версии.
- Smoke-тест подменяет классы и функции Битрикс. Он не доказывает совместимость с реальным ядром, контрактами конкретной версии или фактическим поведением административной страницы.
- Автозагрузка проверена по исходнику, но тестом не подтверждён вызов `Loader::includeModule()` и загрузка `Vendor\\Module\\ExampleService` в реальном ядре.

## 5. Обновления: важное архитектурное разделение

В Битрикс существуют два разных сценария, которые нельзя смешивать.

### 5.1. Поставка обновлений через SiteUpdate / Marketplace

Официальная документация описывает пакет обновления с:
- `install/version.php`;
- `description.<язык>`;
- необязательным `updater.php` или каталогом `updater/index.php`;
- необязательным `version_control.txt`.

Обновления устанавливаются последовательно по версиям. При этом updater:
- может запускаться повторно;
- выполняется до копирования файлов обновления;
- не должен рассчитывать на классы и API, которые появятся только в обновляемой версии;
- может запускаться для модуля, который не установлен на сайте;
- не должен полагаться на определённый порядок между обновлениями разных модулей.

Следствие: updater для Marketplace нельзя строить как обычный вызов нового класса из `lib/`. Это отдельный совместимый сценарий с минимальными зависимостями, проверками состояния и повторяемыми операциями.

### 5.2. Миграции схемы в коде установленного приложения

Для внутренних поставок и контролируемого развёртывания можно проектировать отдельный runner миграций:
- версия схемы БД хранится отдельно от версии релиза модуля;
- миграции имеют неизменяемые уникальные идентификаторы и порядок;
- применённые миграции фиксируются в таблице/хранилище состояния;
- повторный запуск не дублирует изменения;
- при конкурентном запуске предусмотрена блокировка;
- транзакции применяются только там, где это поддерживает используемый движок и тип DDL;
- destructive migrations и удаление данных требуют отдельной политики резервного копирования.

Такой runner не заменяет Marketplace updater. Если модуль будет распространяться через SiteUpdate, updater должен учитывать ограничения его отдельного контракта.

## 6. Рекомендуемое развитие шаблонов

Не перегружать `basic`. Оставить его минимальным install/uninstall каркасом.

Следующий отдельный шаблон разумно назвать `advanced` и включать туда только проверенные, реально используемые механизмы:
1. service/provider слой и автозагрузка;
2. симметричная регистрация обработчиков событий;
3. регистрация и снятие агентов с устойчивыми идентификаторами;
4. runner внутренних DB migrations с отдельной версией схемы;
5. отдельный пример Marketplace updater с явным предупреждением о его ограничениях;
6. тесты повторного запуска, частичного сбоя и безопасного удаления.

До реализации нужно отдельно сверить API выбранной версии ядра для EventManager, Agent, ORM/Connection и updater-контракта. Не следует добавлять демонстрационные таблицы или обработчики только ради заполнения шаблона.
