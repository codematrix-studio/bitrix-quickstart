# Аудит компонентов tools:parser и tools:request

**Источник:** `ASDAFF/bitrix.quickstart`, ветка `master`  
**Дата:** 2026-11-20  
**Область:** `local/components/tools/parser` и `local/components/tools/request`. Проверка статическая, код не запускался.

## 1. `tools:parser`

Файлы:
- `local/components/tools/parser/component.php`
- `.parameters.php`
- `.description.php`
- локальная копия парсера в `local/codes/parser/Bitrix-phpQuery-ajax-step-parser`

Назначение: импорт товаров с внешнего сайта в инфоблок 1, раздел 13, торговый каталог и цены.

### Контроль доступа

- Проверяется `$APPLICATION->GetGroupRight("main")` и при значении `D` вызывается `AuthForm()`.
- Для запуска шага требуется `check_bitrix_sessid()`; это защита от CSRF, но не замена авторизации и проверки прав на запись в iblock/catalog.
- В самом компоненте не проверяются права записи на целевой инфоблок и каталог; используется только право модуля main.
- Поиск вызовов компонента по строке `tools:parser` в дереве не выявил; фактическое размещение и доступность неизвестны.

### Основные дефекты

- `file_get_contents($url)` вызывается до проверки `work_start`: каждый рендер компонента инициирует внешний HTTP-запрос, даже когда импорт не запускают.
- URL задаётся параметром компонента без allowlist схемы/домена, timeout, лимита размера и проверки HTTP-статуса.
- Детальная ссылка берётся из HTML источника и передаётся в `file_get_contents()`; абсолютные ссылки с подстрокой `http` принимаются без ограничения домена.
- Внешние данные (имена/HTML/ошибки) собираются в `$JSParam`, конкатенируются в JS-аргумент и далее попадают в `innerHTML`. Замена одинарной кавычки на двойную не является JS/HTML escaping; возможен XSS в интерфейсе оператора при обработке специально сформированного контента источника.
- `DETAIL_TEXT` сохраняется как HTML без надёжной санитаризации.
- Внешние данные добавляются в инфоблок/каталог без транзакции; ошибки создания раздела, элемента, catalog product и цены проверяются неполно.
- Дедупликация проверяет код элемента только в фиксированном разделе 13, а найденные разделы ищутся по CODE без ограничения родительским разделом.
- `MODIFIED_BY` жёстко равен 1; целевые IBLOCK_ID/SECTION_ID и CATALOG_GROUP_ID зашиты.
- `NUM_NEWS` и `DATE` объявлены параметрами, но текущая реализация использует фиксированный размер страницы 20 и не использует дату.
- `date('d.m.Y h:m')` использует `m` (номер месяца), а не `i` (минуты), и 12-часовой формат без AM/PM; дата заполнения может быть некорректной.
- При отсутствии ожидаемого DOM-узла пагинации/деталей обращение к `get()`/ `textContent` не защищено.
- `$elementCounter` и часть входных параметров берутся из REQUEST без полной нормализации; прогресс и ответ строятся ручной конкатенацией.
- Компонент содержит определения глобальных функций `formatPeriod()` и `multi_implode()`; повторное подключение компонента в одном PHP-процессе может вызвать повторное объявление функций.

**Решение:** не переносить. Если импорт ещё нужен, выделить CLI/административный сервис, проверить права на целевые модули, добавить allowlist URL, timeout/size limits, безопасный JSON, escaping, дедупликацию по внешнему ID, транзакции, dry-run и журнал.

## 2. `tools:request` — форма обращения в техподдержку

Файлы:
- `local/components/tools/request/component.php`
- `.parameters.php`, `.description.php`
- `templates/.default/template.php`

Назначение: создание тикета модуля Support; опциональная регистрация нового пользователя.

### Что реализовано правильно

- Обработчик принимает POST и проверяет `check_bitrix_sessid()`.
- Для гостей по умолчанию включена CAPTCHA (если параметр не отключён).
- Значения имени/email/сообщения в части полей формы возвращаются через `htmlspecialcharsEx()`.

### Риски и дефекты

- `$GENERAL_MESSAGE` собирается с HTML-тегами `<b>`, но значения имени, email, дополнительных полей и сообщения вставляются без HTML-экранирования. Если Support/админский интерфейс отображает сообщение как HTML, возможен stored XSS в тикетах. Требуется проверить фактический renderer.
- `TITLE` тикета формируется с необработанным `MD_NAME`; дополнительные поля также напрямую включаются в HTML-тело.
- Для неавторизованного пользователя при выключенном AUTO_REGISTER в `MESSAGE_AUTHOR_USER_ID` передаётся email, хотя поле по контракту ожидает ID пользователя; нужно проверить поведение CTicket на целевой версии.
- В шаблоне названия категорий/критичности и часть сообщений ошибок выводятся без контекстного escaping. Значения категорий приходят из словаря Support, но требуют проверки доверия/вывода.
- Проверка существования пользователя выполняется отдельным запросом перед созданием; возможна гонка при параллельных запросах. Уникальность email должен обеспечивать сам CUser/БД.
- Результат `CUser::SendUserInfo()` не проверяется; ошибки отправки/создания тикета не журналируются полноценно.
- `CModule::IncludeModule("support")` и подключения зависимостей проверяются неполно.
- Функция `MDTicket::CheckUser()` объявляется глобально внутри component.php; повторное подключение компонента может вызвать повторное объявление класса.
- В параметрах компонента предусмотрен `AUTO_REGISTER`; при включении нужно отдельно проверить выдачу/доставку пароля, rate limit и abuse сценарии.

Поиск вызова компонента по строке `tools:request` в текущем дереве не выявил. Наличие компонента не подтверждает его размещение на публичной странице.

**Решение:** перед использованием очистить пользовательский ввод до формирования тикета, использовать безопасный формат/renderer, проверять типы полей и dictionary IDs, вынести класс из component.php, добавить журнал и rate limit для гостевых обращений/регистрации.

## Итог

Оба компонента нельзя переносить в новый каркас без переработки. `tools:parser` выполняет запись в каталог с недостаточным в самом компоненте permission model и небезопасной обработкой внешнего HTML/JS. `tools:request` имеет корректную базовую CSRF-проверку, но требует устранить риск HTML injection в тикетах и проверить контракт Support API.
