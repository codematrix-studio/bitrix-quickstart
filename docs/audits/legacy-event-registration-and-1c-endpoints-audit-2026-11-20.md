# Аудит регистрации событий и точек входа 1С-обмена

**Источник:** `ASDAFF/bitrix.quickstart`, ветка `master`  
**Дата:** 2026-11-20  
**Статус:** статическая сверка конфигурации, регистрации обработчиков и точек входа; состояние установленного модуля и веб-сервера не проверено.

## 1. Фактическая регистрация обработчиков пользователей

### 1.1. Две реализации Helper\CUserRegistration не подключены через проверенные точки регистрации

Проверены:
- `local/php_interface/init.php`;
- `local/php_interface/config/events.php`;
- `local/php_interface/include/handlers.php`;
- поиск по репозиторию для `OnBeforeUserRegisterCheckINN`, `OnAfterUserRegisterHandler`, `CUserRegistration`.

Результат:
- `config/events.php` содержит только заголовочный комментарий;
- `handlers.php` регистрирует обработчики авторизации по email, URL rewrite, почтовых событий и Epilog, но не регистрирует `Helper\CUserRegistration`;
- обе реализации `Helper\CUserRegistration` и `Helper\User\CUserRegistration` содержат одноимённые методы, но точек регистрации/вызова в текущем дереве не найдено.

**Вывод:** считать INN-проверку и автоматическое прикрепление контрагента активными нельзя. Это не доказательство, что их не подключает БД, внешний код или динамический вызов; это отсутствие регистрации в проверенной конфигурации репозитория.

### 1.2. В проекте предусмотрен другой активный путь регистрации

В `local/modules/site.main/install/index.php` модуль при установке регистрирует `\Site\Main\Module::onPageStart` на событие `main:OnPageStart`.

Далее `Site\Main\Module::onPageStart()` вызывает `setupEventHandlers()`, где добавляются:
- `main:OnBeforeUserRegister` → `Site\Main\User::OnBeforeUserRegisterHandler`;
- `main:OnAfterUserRegister` → `Site\Main\User::OnAfterUserRegisterHandler`;
- обработчики обновления пользователя.

Таким образом, именно `Site\Main\User` является предусмотренным исходниками действующим сценарием регистрации, если модуль `site.main` установлен и его обработчики не отключены в БД. Фактическую запись обработчиков в БД и состояние модуля по одному Git-репозиторию подтвердить нельзя.

### 1.3. Риски фактического обработчика Site\Main\User

Файл: `local/modules/site.main/lib/user.php`, методы около строк 435–495.

1. **Слабый пароль:** пароль и подтверждение генерируются через `randString(6)`. Длина 6 символов мала для учётных записей; стойкость зависит от реализации конкретной версии Bitrix. Нужен штатный безопасный механизм/криптографический генератор и достаточная длина.
2. **Передача пароля в открытом виде по почте:** после регистрации `CONFIRM_PASSWORD` отправляется через `CEvent::Send('NEW_USER_PASSWORD', ...)`. Это раскрывает временный пароль почтовой инфраструктуре и содержимому письма. Предпочтительнее одноразовая ссылка/механизм установки пароля без отправки самого пароля.
3. **Внешняя проверка reCAPTCHA без явного таймаута и полноценной обработки ошибки транспорта:** `HttpClient::post()` вызывается без настройки таймаутов; далее результат сразу передаётся в `json_decode()` и используется как объект. Нет отдельной проверки HTTP-кода, ошибки транспорта и структуры ответа.
4. **Проверка email по файлу ненадёжна:** результат `file_get_contents()` не проверяется. Если файл отсутствует/недоступен, обработчик получает false и дальше всё равно разбирает результат. Содержимое файла подставляется в регулярное выражение без экранирования; повреждённая строка может дать некорректный шаблон и предупреждение.
5. **Регулярное выражение не ограничено форматом:** email-подстроки из CSV используются как часть regex, хотя задача выглядит как сравнение адресов/доменов. Требуется явный формат файла и сравнение нормализованных доменов/адресов, а не сборка regex из данных.
6. **Жёстко задан site ID:** после регистрации письмо отправляется с `SITE_ID = s1`, что не учитывает многосайтовую конфигурацию.
7. **Нет явной проверки результата отправки письма:** результат `CEvent::Send()` не проверяется и не логируется безопасным способом.

**Решение:** не переносить обработчик как готовый сервис. Выделить регистрацию в отдельный сценарий с проверяемым контрактом, штатным подтверждением/установкой пароля, безопасной проверкой CAPTCHA, строгим источником denylist и наблюдаемой обработкой ошибок.

## 2. 1С: реальная точка входа и конфигурация

Файл `local/modules/mht/sale/admin/1c_exchange.php` подключает `mht:catalog.import.1c` при `type=catalog`. Для этого компонента передаются настройки из `COption`, включая `GROUP_PERMISSIONS`, `ELEMENT_ACTION`, `SECTION_ACTION`, лимиты файлов, CRC/ZIP и другие параметры. Если передан `KodUzla`, его значение напрямую передаётся как `IB_ID` параметр компонента.

Это подтверждает реальную проектную точку запуска активного компонента 1С. Отдельно обнаружены старые копии:
- `local/modules/mht/sale_old/admin/1c_exchange.php`;
- `local/modules/mht/sale/admin/old_1c_exchange.php`;
- `local/components/mht/catalog.import.1c/old_component.php`;
- `old2_component.php` ... `old5_component.php`;
- `local/components/mht/catalog.import.1c_old/component.php`.

В проверенном дереве основной admin endpoint вызывает именно `mht:catalog.import.1c`; ссылки на `catalog.import.1c_old` не найдены. Старые файлы в каталоге компонента не являются штатным именем точки входа Bitrix, но их нельзя считать недоступными без проверки веб-конфигурации и ручных include.

### 2.1. Повторяющаяся проблема source check

В актуальном `component.php` и нескольких резервных версиях алгоритм вычисления `SKIP_SOURCE_CHECK` сохранён, однако фактическая ветка проверки источника через `check_bitrix_sessid()` закомментирована. В активном компоненте это находится после обработки `checkauth`.

При этом остаются проверки авторизации пользователя и принадлежности к разрешённым группам. Поэтому корректная формулировка риска: **отключена дополнительная проверка source/session token на этапе обработки обмена**, а не полностью отсутствует авторизация.

### 2.2. Административная точка входа

В `1c_exchange.php` заданы `BX_SESSION_ID_CHANGE=false`, `BX_SKIP_POST_UNQUOTE=true`, `NO_AGENT_CHECK=true` и `STATISTIC_SKIP_ACTIVITY_CHECK=true`, затем подключается `prolog_before.php`. Доступ к endpoint и фактическая защита должны проверяться на установленном сайте, включая настройки веб-сервера, авторизацию 1С и параметры модуля `catalog`.

Параметр `KodUzla` приходит из GET и используется как `IB_ID`; необходима строгая проверка соответствия разрешённому инфоблоку и запрет на произвольные ID. Конфигурационные значения `COption` в репозитории не позволяют установить реальные production-настройки.

## Итог

Сценарий регистрации INN/контрагентов из двух классов Helper в проверенных исходниках не подключён. Проектный модуль `site.main` предусматривает другой путь регистрации через `Site\Main\User`; именно его нужно считать основным кандидатом на фактический runtime-сценарий до проверки таблицы событий на стенде. В действующем 1С-маршруте подтверждён вызов кастомного компонента, у которого дополнительная проверка source/session token закомментирована.
