# Аудит бизнес-агентов, купонов и файловых импортеров

**Источник:** ASDAFF/bitrix.quickstart, ветка master  
**Дата:** 2026-11-20  
**Область:** product2product agent, order.coupon, gift.certificate, discount.updater и trial serials. Код не запускался.

## 1. Product2Product: агент чистки связанных товаров

Файлы:
- local/modules/mht/sale/lib/product2product.php
- local/modules/mht/sale/install/index.php

Подтверждено:
- install/index.php регистрирует обработчики sale events для Product2ProductTable.
- Там же регистрируется агент Product2ProductTable::deleteOldProducts(10) с периодом 10 дней.

Дефект:
- deleteOldProducts() уменьшает счётчики пар товаров для заказов старше заданного срока.
- После этого updateRemStatusSql() выполняет UPDATE b_sale_order_processing SET PRODUCTS_REMOVED='Y' без WHERE.
- В результате статус PRODUCTS_REMOVED меняется у всех записей таблицы, а не только у обработанных старых заказов.
- Следующие запуски агента могут считать все заказы уже обработанными и больше не уменьшать счётчики для тех заказов, которые на момент первого запуска ещё не достигли срока хранения.

Дополнительные риски:
- SQL обновление выполняется без транзакции вместе с обновлением счётчиков.
- Не подтверждена идемпотентность при частичном сбое между decrement и массовым UPDATE.
- Проверка количества/ошибок SQL-операций неполная.

**Решение:** исправить updateRemStatusSql() на ограниченное обновление только ID обработанных order processing rows; выполнять decrement и mark в одной транзакции; добавить тесты на разные даты заказов и повторный запуск.

## 2. order.coupon: повторная выдача персональных купонов

Файлы:
- local/modules/order.coupon/classes/Event.php
- local/modules/order.coupon/install/index.php

Подтверждено:
- install/index.php регистрирует Event::OnSaleOrderSavedHandler на sale:OnSaleStatusOrder.
- Handler запускается при статусе P.
- Для каждого правила HL-блока проверяется условие заказа, создаётся новый купон через DiscountCouponTable::generateCoupon(true), затем отправляется почтовое событие.

Находки:
- Нет idempotency key или проверки, что купон по этому правилу уже создан для данного заказа.
- Если заказ повторно переводится в статус P после другого статуса, обработчик может создать ещё один купон по тому же правилу.
- Все правила HL-блока выбираются без фильтра активного состояния/срока; отдельной проверки статуса правила в handler нет.
- UF_CONDITIONS декодируется через base64_decode() и unserialize() без allowed_classes; данные управляются через HL-блок, поэтому прямой пользовательский контроль не подтверждён, но сериализованный payload требует строгого формата.
- CEvent::Send() не проверяется; нет журнала успешной выдачи купона с order ID и rule ID.
- Срок действия рассчитывается из UF_DAYS без валидации диапазона.
- При ошибке создания купона в лог пишется постоянный ITEM_ID=123, что затрудняет диагностику.

**Решение:** ввести уникальную связь order/rule/coupon и проверять её перед выдачей; транзакция/идемпотентность; валидация сроков; отказаться от unserialize либо использовать безопасную схему JSON; журналировать результат отправки.

## 3. gift.certificate: аналогичный риск дублирования

Файлы:
- local/modules/gift.certificate/classes/Event.php
- local/modules/gift.certificate/install/index.php

- Обработчик также регистрируется на sale:OnSaleStatusOrder и выполняется при статусе P.
- Для каждого товара заказа, относящегося к целевому инфоблоку, ищутся правила HL и создаются купоны.
- Нет проверки существования ранее выданного сертификата для пары order/product/rule.
- Повторный перевод заказа в P может повторно создать сертификаты.
- Результат отправки почты не проверяется.
- В обработчике не проверяется наличие заказа/пользователя до обращения к их полям.

**Решение:** idempotency key на order ID + product ID + rule ID; проверка заказа/пользователя; логирование.

## 4. discount.updater: XML файл под document root

Файлы:
- local/modules/discount.updater/admin/index.php
- local/modules/discount.updater/install/index.php

Что есть:
- Административная страница подключает prolog_admin_before и проверяет check_bitrix_sessid().
- Загруженный файл перемещается в DOCUMENT_ROOT/discount_cards.xml.
- Интерфейс показывает прямую ссылку на этот файл.

Риски:
- Если XML содержит номера скидочных карт/персональные данные, файл доступен как статический документ по публичному URL, если web server не закрывает его отдельно.
- Нет проверки размера и содержимого XML; имя назначения фиксировано, но расширение и MIME входного файла не валидируются.
- Файл хранится в web root, а не в закрытом временном хранилище.
- В текущем Git tree найден только upload endpoint и URL rewrite; обработчик, который должен забрать/обработать discount_cards.xml в течение 5 минут, не найден. Он может быть вне репозитория.

**Решение:** хранить XML вне document root, ограничить размер и схему, закрывать временный файл после обработки, проверить статический URL и права доступа. На VM найти фактический processor/agent.

## 5. Trial serials

Файл: local/modules/site.main/lib/mvc/controller/trials.php.

- Действие требует авторизованного пользователя, но не проверяет sessid/CSRF.
- Список серийных ключей читается из DOCUMENT_ROOT/serials4999.csv.
- Файл не входит в Git tree.
- Нет file lock/atomic replace; два параллельных запроса могут получить один ключ или потерять строку.
- Если файл находится в публичном document root без отдельного запрета, его содержимое может быть скачано напрямую.

**Решение:** хранить ключи вне document root и в БД с атомарным резервированием/уникальным индексом; CSRF; журнал выдачи и rollback при ошибке.

## 6. Итог

Есть подтверждённый массовый UPDATE без WHERE в агенте product2product, риск повторной выдачи купонов/сертификатов при повторном входе заказа в статус P и потенциальное раскрытие файлов discount_cards.xml / serials4999.csv из document root. Реальная доступность файлов и наличие внешнего processor проверяются на VM; код не запускался и не изменялся.
