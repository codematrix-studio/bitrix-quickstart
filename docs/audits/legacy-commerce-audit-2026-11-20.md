# Аудит старых торговых сценариев: корзина, заказ, обмен и личный кабинет

Дата проверки: 2026-11-20.

## Область и правила

Проверялись исходники старого репозитория `ASDAFF/bitrix.quickstart` (ветка `master`) и текущая реализация `codematrix-studio/bitrix-quickstart` (ветка `main`).

Старый репозиторий использовался только для чтения. В него не вносились изменения. Не переносились ядро Битрикс, сторонние библиотеки, содержимое `upload`, данные конкретных сайтов и клиентские настройки. Каталог `mvc.base` исключён из миграции.

Цель аудита — найти повторно используемую бизнес-логику, а не переносить старые компоненты и шаблоны целиком.

## 1. Корзина

### Найдено в старом репозитории

- `local/components/cart/sale.basket.basket/class.php` — крупная реализация компонента корзины.
- `local/components/cart/sale.basket.basket/ajax.php` — AJAX-действия с корзиной.
- `local/components/cart/sale.basket.basket/functions.php` — поиск торгового предложения по свойствам.
- `local/components/cart/ajaxBasket/component.php` и его шаблон — модальная обвязка.

Основной класс использует legacy API: `CSaleBasket`, `CSaleDiscount`, `CSaleLang`, `CSalePersonType`, `CIBlockProperty`, `CIBlockElement`, `CCatalogSku`, `CFile`, глобальные `SITE_ID`, `$USER` и `$APPLICATION`. Внутри компонента смешаны чтение корзины, расчёт скидок/НДС, обработка наборов и SKU, подготовка изображений, форматирование и данные для старого шаблона.

AJAX-файл принимает команды из POST и самостоятельно собирает данные для UI. Он также содержит legacy-операции с позициями корзины и зависит от компонентного класса.

### Уже реализовано в новой версии

- `BasketManager` — операции добавления, изменения количества, удаления и очистки D7-корзины.
- `BasketHandler` — фасад чтения и совместимых операций; не раскрывает изменяемый объект корзины и не принимает цену/валюту из входных данных.
- Тесты: `tests/d7_basket_manager_smoke.php`, `tests/d7_basket_handler_smoke.php`.

### Решение

Не переносить старый компонент, AJAX-контроллер, шаблоны, jQuery/Fancybox и функции целиком.

**Не считать полное поведение старой корзины перенесённым.** Отдельной интеграционной проверки требуют:
- отложенные позиции;
- недоступные товары и подписки;
- наборы товаров;
- SKU и наследование свойств торгового предложения от родительского товара;
- свойства позиций корзины;
- купоны, скидки, НДС и пересчёт цен;
- вес, единицы измерения и форматирование;
- обработка изменения/удаления через реальные запросы сессии и CSRF.

Это не повод копировать старый код: соответствующие правила должны оставаться в штатном D7 Sale/Catalog и в отдельном UI-слое. Если на VM обнаружится недостающий универсальный сценарий, его следует оформить отдельным сервисом с тестами.

## 2. Оформление заказа

### Найдено в старом репозитории

- `local/components/order/sale.order.ajax/component.php` — около 1 950 строк.
- `local/components/order/sale.order.ajax/functions.php` и `get.php`.
- `local/components/order/sale.order.ajax.v12/` — ещё одна версия компонента.
- Несколько шаблонов оформления заказа.

Компонент объединяет обработку HTTP/AJAX, параметры сайта, сессии, корзину, скидки, свойства заказа, местоположения, типы плательщика, доставку, оплату, предоплату, профиль пользователя и представление. В коде присутствуют `CSale*` API и глобальное состояние приложения.

В `local/codes/blank/compilation/createOrderD7.php` найден короткий пример D7-создания заказа, но он содержит демонстрационные персональные данные и жёстко заданные ID типа плательщика, доставки и оплаты. Это пример, а не готовый переносимый сервис.

### Уже реализовано в новой версии

- `OrderManager` — создание заказа из постоянной или переданной временной D7-корзины, установка свойств по символьным кодам, проверка обязательных свойств, доставка, оплата, финальный расчёт и сохранение.
- `QuickOrder` и `QuickOrderInput` — отдельный сценарий заказа из временной корзины без изменения постоянной корзины FUSER.
- `OrderSaveWarningsException` — предупреждения успешного сохранения не маскируются обычным возвратом ID.
- Есть автономные smoke-тесты OrderManager и QuickOrder.

### Решение и обязательные проверки

Не переносить старый checkout-компонент и его шаблоны. D7-сервисы уже покрывают ядро универсального сценария создания заказа.

До признания интеграции проверенной на реальном Битриксе необходимо проверить:
1. создание заказа для фактического пользователя и сайта;
2. пересчёт скидок/налогов на реальной корзине;
3. обязательные и множественные свойства заказа, включая свойства типов файл/местоположение, если они нужны проекту;
4. ограничения и расчёт доставки;
5. ограничения платёжных систем и сумму оплаты после финального расчёта;
6. сохранение заказа и обработку ошибок/предупреждений;
7. повторный POST, CSRF и отсутствие повторного создания заказа;
8. сохранение постоянной корзины при QuickOrder.

Автономные тесты с fake-объектами проверяют логику сервиса, но не заменяют интеграционные тесты на VM. Наличие в репозитории тестов не является подтверждением работы реального Sale-модуля.

## 3. Импорт и экспорт

### Экспорт YML

Старые исходники:
- `local/modules/lema.lib/lib/Base/XmlExport.php`;
- `local/modules/lema.lib/lib/Seo/YmlExport.php`.

Это общий экспортный каркас с Bitrix-загрузкой данных, JSON-файлами кеша и YML-представлением. Старый `YmlExport` выводит XML непосредственно из PHP-шаблона; часть значений (например, имя раздела, URL и изображение) выводится без полноценного XML-экранирования. Используются глобальные параметры сайта и HTTP_HOST.

**Миграция уже представлена в новой версии:**
- `Project\\Export\\BitrixCatalogExporter` — подготовка данных из репозиториев инфоблоков и кеширование;
- `Project\\Export\\YmlCatalogRenderer` — независимый от Битрикс рендерер;
- `Project\\Export\\XmlEscaper` — экранирование XML;
- `Project\\Support\\JsonFileCache` — файловый кеш;
- legacy-адаптеры `Lema\\Base\\XmlExport` и `Lema\\Seo\\YmlExport`.

Для этой части повторный перенос не нужен. Новая реализация разделяет загрузку данных, кеш и сериализацию; старые имена классов оставлены через адаптеры. Проверки запускаются командой `composer test:export` из каталога `local`.

### Обмен с 1С

Найдено:
- `local/components/catalog/catalog.import.1c/`;
- `local/components/catalog/card.import.1c/`;
- `local/components/mht/catalog.import.1c/`;
- `local/components/mht/sale.export.1c/`;
- `local/codes/utilities/1C/`;
- `local/modules/indi.main/lib/import.php`.

Компоненты `catalog.import.1c` реализуют протокол CommerceML и опираются на штатные классы импорта Битрикс (`CIBlockXMLFile`, `CIBlockCMLImport` и связанные механизмы), работу с файлами, временными каталогами и настройками инфоблоков. Каталог `local/modules/mht/sale` содержит копию/модификацию кода Sale-модуля Битрикс; его нельзя рассматривать как авторскую универсальную библиотеку для переноса.

`Indi\\Main\\Import` — отдельный импорт с клиентской схемой данных, русскоязычными полями, хранением промежуточного объекта в сессии и прямым вызовом `CIBlockElement`. Он зависит от конкретной структуры входного файла и настроек сайта.

### Решение

Не переносить CommerceML-компоненты, копии модуля `mht/sale`, клиентские XML/CSV и `Indi\\Main\\Import`. Универсальная часть штатного обмена должна использоваться из установленного модуля Битрикс, а не копироваться в каркас.

Если потребуется отдельный импортёр для внешнего формата, его следует проектировать как самостоятельный адаптер с явной схемой входных данных, валидацией, журналированием, идемпотентностью и тестовыми фикстурами без клиентских данных. В рамках текущего аудита такого готового переносимого кандидата не выявлено.

## 4. Личный кабинет и история заказов

### Найдено в старом репозитории

- `local/components/personal/personal.area/` — маршрутизация вкладок профиля, заказов и адресов, HTML-навигация.
- `local/components/personal/personal.info/` — получение профиля пользователя, города и количества товаров в корзине.
- `local/components/personal/main.profile/` — форма редактирования профиля на legacy `CUser`.
- `local/components/cm/sale.personal.order.list/` — история заказов, фильтры, копирование заказа, статусы, доставка и состав заказа.

История заказов построена на `CSaleOrder`, `CSaleBasket`, `CSaleStatus`, `CSalePaySystem`, `CSaleDelivery`, `CSaleDeliveryHandler`, сессионных фильтрах и старых шаблонах. Компоненты личного кабинета тесно связаны с URL, параметрами и UI конкретного сайта. В `personal.info` дополнительно присутствуют определение города и файловые справочники, не являющиеся универсальной логикой личного кабинета.

### Решение

Не переносить эти компоненты и шаблоны в библиотеку. В новой версии есть универсальный сервис создания заказа, но это не означает, что уже реализованы история заказов, просмотр заказа, повтор заказа, отмена, адресная книга или профиль пользователя.

Если эти функции понадобятся в каркасе, их следует проектировать отдельными D7-сервисами с проверкой принадлежности заказа текущему пользователю и ограничением доступа к данным. Сейчас переносить нечего: найденные реализации — UI/сайт-специфичный legacy-код.

## 5. Сводный реестр решений

| Область | Решение | Причина |
|---|---|---|
| Корзина | Не переносить компонент; использовать D7-сервисы | Старая реализация смешивает Sale API, расчёты и UI |
| Checkout | Не переносить компонент; проверить D7-сервисы на VM | Старая реализация — большой HTTP/UI-сценарий |
| Быстрый заказ | Использовать `QuickOrder` | В новой версии уже есть изолированная временная корзина |
| YML/XML-экспорт Lema | Повторно не переносить | Уже мигрирован через новые классы и legacy-адаптеры |
| CommerceML 1С | Не переносить штатные компоненты | Это интеграция штатного модуля Битрикс |
| `mht/sale` | Исключить | Копия/модификация модуля Битрикс, не универсальная библиотека |
| `Indi\\Main\\Import` | Не переносить | Клиентская схема данных и прямые зависимости от сайта |
| Личный кабинет | Не переносить компоненты | UI, маршрутизация и данные конкретного сайта |
| История заказов | Отложить до отдельного требования | Нет готового универсального D7-сервиса в текущем каркасе |

## 6. Следующие шаги

1. На VM выполнить интеграционную проверку `BasketManager`, `BasketHandler`, `OrderManager` и `QuickOrder` на фактической версии PHP/Битрикс и настроенных Sale/Catalog.
2. Отдельно пройти перечисленные сценарии корзины: SKU, наборы, отложенные/недоступные позиции, купоны и скидки. Не добавлять функциональность без подтверждения исходного контракта.
3. Продолжить аудит самостоятельных helper-классов старого `local/php_interface`, в том числе `ImageSitemapFile`, проверив зависимости и возможность изоляции от сайта.
4. После проверки каждого кандидата принимать отдельное решение о миграции; изменения оформлять отдельной веткой и PR. Старый репозиторий остаётся неизменным.

## Ограничения проверки

Аудит выполнен по исходникам GitHub. Интеграционные сценарии не запускались на установленном Bitrix VM в рамках этой проверки. Поэтому выводы о реальном поведении D7 Sale, доставок, платёжных систем, скидок и провайдера каталога остаются условными до VM-тестирования.
