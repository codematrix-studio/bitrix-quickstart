# Дополнительный аудит helper-классов

**Источник:** `ASDAFF/bitrix.quickstart`, ветка `master`  
**Дата:** 2026-11-20  
**Статус:** статический просмотр выбранных классов и точек использования. Runtime не выполнялся.

## 1. SQL и работа с данными

### 1.1. CMLNameConnector — SQL injection через данные обмена

Файл: `local/php_interface/classes/Helper/CMLNameConnector.php`.

Метод `addXID()` формирует INSERT конкатенацией значений `$prev`, `$new` и `$code`. Они не проходят SQL-экранирование и используются как значения SQL. Класс вызывается из механизма сопоставления XML_ID/имён в импорте 1С; значения могут происходить из внешнего XML. Это подтверждённый дефект построения запроса, а при контролируемых данных импорта — потенциальный SQL injection.

**Решение:** параметризованный запрос/ORM; таблицу выбирать только из внутреннего enum, а не из произвольного значения. Валидация и экранирование должны быть отдельными для значений и идентификаторов.

### 1.2. shortUrl — динамический SQL и имя таблицы

Файл: `local/php_interface/classes/Helper/shortUrl.php`, метод `checkShortUrl()`.

`$IBLOCK_ID` и `$CUR_SECTION_ID` напрямую конкатенируются в SQL, в том числе в имя таблицы `b_uts_iblock_{ID}_section`. До построения запроса они не приводятся к положительным целым числам. Поскольку имя таблицы нельзя безопасно передать обычным bind-параметром, ID нужно строго валидировать и формировать имя таблицы только после такой проверки. В запросе также отсутствует проверка результата/ошибки.

Метод `setFilter()` переносит все параметры разобранной строки URL в глобальный `$_GET`, меняя входное состояние запроса. Нет allowlist параметров, ограничений типов и защиты от перезаписи служебных параметров.

**Решение:** строгая валидация ID, allowlist параметров фильтра, локальный массив вместо изменения глобального `$_GET`.

### 1.3. WP — универсальный SQL helper и генератор структуры

Файл: `local/php_interface/classes/Helper/WP.php` (2674 строки).

- В ветке HL-запросов таблица берётся из `$data['filter']['table']` и напрямую вставляется в FROM; имена полей собираются динамически. `ForSql()` не является валидацией SQL-идентификатора. Требуется allowlist сущностей/полей и параметризация значений.
- В том же HL builder при обходе списка select используется `$data['select']` вместо текущего элемента `$row`; это функциональная ошибка формирования SELECT.
- `WP::query()` строит SQL заменой плейсхолдеров через `preg_replace()`. Даже при SQL-экранировании значений такой механизм хрупок: replacement string интерпретирует обратные ссылки/спецпоследовательности, плейсхолдеры не токенизируются, нет контроля количества/типа параметров. Заменить на параметризованные запросы.
- `makeStructure()` строит физические пути из `DOCUMENT_ROOT + parent + translit(name)`, создаёт каталоги и записывает PHP-файлы через `file_put_contents()`. Содержимое `name` вставляется в генерируемый PHP без PHP-контекстного экранирования. При недоверенном источнике структуры возможны запись за пределами ожидаемого каталога и внедрение PHP-кода. Нет атомарной записи и проверки ошибок.
- `log()` выводит `print_r()` произвольного объекта прямо в HTML без экранирования; если логируемые данные контролируются пользователем, возможен XSS в странице отладки.
- `uncsv()` принимает путь и открывает `DOCUMENT_ROOT . path` без ограничения корня/нормализации; вызывать только с доверенным путём и добавить проверку containment.

**Решение:** не использовать WP как универсальный слой доступа к данным нового каркаса. Выделять конкретные репозитории с ORM/Query API, безопасный writer файлов и отдельный структурированный logger.

## 2. BuyOneClickHandler — критичная заготовка оформления заказа

Файл: `local/php_interface/classes/Helper/BuyOneClickHandler.php`.

1. Конструктор читает только `email` и `phone`, а `Execute()` передаёт их в `Buy($productId, $coupon)`. В результате email используется как ID товара, а телефон — как купон. Отдельного параметра productId в классе нет. Это явная ошибка контракта и, вероятно, делает оформление заказа некорректным.
2. Новый пользователь получает пароль `md5(EMAIL)`. Он детерминирован и вычислим из публичного/известного email; после создания аккаунта такой пароль можно угадать. Это критичный риск компрометации новых аккаунтов, если endpoint доступен.
3. При поиске пользователя email и телефон объединяются в один AND-фильтр. Несовпадение одного из полей создаёт новый аккаунт, даже если второй идентификатор уже принадлежит существующему пользователю.
4. Нет полноценной проверки email/телефона, CSRF, частоты запросов и согласия на создание учётной записи в самом классе. Не проверяются результаты создания пользователя, товара, доставки и платёжной системы.
5. Заказ сохраняется до добавления купона и пересчёта скидки; после пересчёта повторного сохранения заказа в коде нет. Применение купона к сохранённому заказу требует отдельного runtime-теста.
6. Файл класса подключает `prolog_before.php` на уровне файла. Подключение класса имеет побочный эффект и нарушает разделение bootstrap/бизнес-логики.
7. В текущем дереве поиск не обнаружил внешних вызовов `BuyOneClickHandler`; наличие доступного HTTP endpoint не подтверждено.

**Решение:** не переносить. При необходимости перепроектировать handler с отдельными типизированными полями productId/email/phone/coupon, штатным созданием пользователя и пароля, CSRF/rate limit, проверкой товара и единым сохранением заказа после применения скидок.

## 3. Прочие классы

### CValidator.php

- `validate()` не проверяет наличие поля перед чтением и не инициализирует массив результата для пустого набора правил.
- Правило email использует устаревший ограниченный шаблон (доменная зона только 2–4 символа).
- `emailExists()` и `emailIsFree()` объявляют `$errorMessage`, но возвращают неинициализированный `$defaultMessage`.
- Правила вызываются динамически по имени метода; нужно ограничить список доступных валидаторов и формализовать структуру конфигурации.
- Нет использования найденного класса вне самого файла, поэтому активность не подтверждена.

### CCheckINN.php

- `checkingCSV()` читает весь файл целиком без ограничения размера; не проверяет результат чтения и результат определения кодировки; индексы столбца не валидируются.
- `checkingHL()` не проверяет успешность подключения модуля, существование HL-блока и результат compileEntity(); массив результата не инициализирован при пустой выборке.
- Парсинг CSV самописный и чувствителен к разделителям/кодировке; использовать штатный CSV reader и строгую схему колонок.

### ChangePriceEventHandler.php

- `InvalidArgumentException` указан без ведущего `\\` и без импорта; внутри namespace `Helper` PHP будет искать `Helper\InvalidArgumentException`.
- Для расчёта жёстко зашиты группы пользователей `[2]`, сайт `s1` и код свойства `MIN_PRICE_DISCOUNT`.
- Результат `GetOptimalPrice()` и обновления свойства не проверяются; событие может завершиться с некорректным значением.
- В текущем дереве регистрации/вызовы обработчика не найдены.

### CheckSubscriptionAvailabilityHandler.php

- Bootstrap `prolog_before.php` подключается на уровне файла.
- Метод отвечает по POST email, есть ли запись в форме с жёстко заданными FORM_ID/FIELD_ID; нет CSRF-проверки, нормализации email, ограничения частоты запросов и проверки доступа в классе.
- Если этот метод опубликован через общий handler без дополнительной защиты, он может стать каналом проверки факта подписки/записи по email. Сам endpoint и вызовы в дереве не найдены.

### CMLNameConnector.php / WP.php / shortUrl.php

Регистрации и внешние вызовы части этих классов в полном дереве не найдены или не подтверждены. Это не снимает дефекты: при подключении в проект следует учитывать их контракт и источник данных.

### CLinkHelper.php / CLWLinkHelper

Файл `CLinkHelper.php` объявляет класс `CLWLinkHelper`. Это не просто несовпадение имени: поиск по дереву нашёл реальное использование `CLWLinkHelper` в `UserProp/CYouTubeProperty.php`, где класс разбирает YouTube URL и получает параметр `v`. Вызов по фактическому имени класса подтверждён; переименование файла/класса без изменения потребителя сломает этот сценарий.

В `parseUrl()`:

- результат `parse_url()` не проверяется на `false`;
- ключи `query` и `path` читаются без проверки существования;
- строка query разбирается вручную через `explode('&')` и `explode('=')`: значения с символом `=` обрезаются, URL-кодирование не декодируется, повторяющиеся параметры теряются;
- параметры без `=` могут привести к чтению отсутствующего индекса.

**Решение:** сохранить совместимое имя класса на этапе миграции либо обновить потребителя одновременно; заменить разбор query на `parse_str()`, валидировать URL и ожидаемый host/формат YouTube-ссылки.

### FollowService.php

В дополнение к ранее зарегистрированной находке `AUTH-FAV-01` подтверждено:

- cookie `FollowProducts` десериализуется через `unserialize()` без `allowed_classes => false` и без проверки типа результата до вызова `in_array()`/изменения массива;
- `DropFollowProductFromCookie()` проверяет `in_array($productId, $products) || $products`. Если массив непустой, но искомого ID нет, `array_search()` вернёт `false`, а `unset($products[false])` удалит элемент с ключом 0;
- `InvalidArgumentException` не импортирован и не указан как глобальный `\\InvalidArgumentException`; в namespace `Helper` это может вызвать ошибку разрешения класса при некорректном ID;
- `UpdateCookie()` устанавливает `HttpOnly=false` и вызывает `flush("")` внутри сервиса, создавая побочный эффект отправки ответа из бизнес-метода;
- загрузка модулей в конструкторе не проверяется.

Поиск по текущему дереву не обнаружил вызовов `FollowService` вне самого класса. Это не отменяет риск при возможном динамическом подключении; активный endpoint не подтверждён.

**Решение:** не переносить. Для хранения списка использовать безопасный формат (JSON/валидированный массив), строгую проверку ID, корректное удаление по найденному ключу, отдельный слой ответа/cookie и тесты.

### CouponConditions.php

Метод `toString()` вызывает `unserialize()` для `CSaleDiscount::GetByID()['CONDITIONS']`, затем без проверок обращается к `CHILDREN`, `CLASS_ID`, `DATA` и индексам справочника контролов. Источник — сохранённая конфигурация скидки в БД, а не напрямую HTTP-параметр, поэтому не квалифицируется как подтверждённая внешняя PHP Object Injection. Но результат десериализации и схема условий не валидируются; удалённые/неполные записи скидок могут приводить к warning/error. Возвращаемое значение документировано как bool, фактически метод возвращает массив строк либо false.

**Решение:** перед чтением проверять результат и схему; для современных версий PHP использовать `unserialize(..., ['allowed_classes' => false])` либо штатный механизм хранения условий Битрикс; исправить PHPDoc/контракт результата.

### GetSection.php

- `$arLincs` не инициализирован до цикла; при пустой выборке вызов `array_shift($arLincs)` работает с неопределённой переменной.
- `array_merge(defaults, $filter)` позволяет вызывающему коду переопределить `ACTIVE` и `GLOBAL_ACTIVE`, несмотря на описание метода как списка активных разделов.
- Нет проверки результата `CIBlockSection::GetList()`.

**Решение:** инициализировать массив; определить, должны ли статусы быть жёстким условием или параметром; документировать контракт и типы.

### IblockObject.php

Класс загружает элементы через `CIBlockElement::GetList()` с `CHECK_PERMISSIONS => N`. Следовательно, он отключает стандартную проверку прав Битрикс; безопасность зависит от того, где вызывающий код проверяет доступ. Магическим геттером `printable_*` вызывается форматирование значения, но класс не гарантирует контекстное HTML-экранирование для всех типов/потребителей. Метод `fromParams()` принимает внешний массив без валидации схемы и может напрямую заполнить внутренние параметры.

**Решение:** не использовать в публичных сценариях без явной ACL-проверки; новый слой должен разделять получение данных, авторизацию и экранирование на стороне вывода.

### Остальные классы

- `BaseHandler.php`: абстрактный контракт минимален; конструктор и `Execute()` не имеют типов параметров/результата на уровне сигнатур. Критичный риск не установлен.
- `GetBasket.php`: legacy API `CSaleBasket`; товары индексируются по `PRODUCT_ID`, поэтому несколько строк корзины одного товара перезапишут друг друга. Сумма считается как `PRICE * QUANTITY` без учёта возможных нюансов скидок/валюты/округления; использовать только как упрощённую выборку, не как источник итоговой суммы заказа.
- `IBlockData.php` и `LIBlock.php`: дублируют практически один и тот же кеширующий справочник ID инфоблоков по CODE. При пустом наборе инфоблоков кэш считается пустым и запрос повторяется; ключи зависят от SITE_ID. Не переносить оба класса параллельно — выделить один сервис с явным контрактом.
- `IBlockMenu.php`: в сортировке при равном SORT ID упорядочивается по убыванию; рекурсивный обход меняет локальную копию массива и не всегда отражает ожидаемое отсечение глубины. Требуется тест на структуру дерева/DEPTH_LEVEL.
- `SendForms.php`: рекурсивная конвертация вызывает `urldecode()` для каждого скалярного значения и `iconv()` без проверки результата; это не универсальная безопасная конвертация массива, может менять данные и возвращать false при ошибке кодировки.
- `SimpleHblockObject.php`: тонкая обёртка над `HblockObject`, передаёт ID без локальной валидации; основные риски находятся в родительском классе.
- `Translit.php`: самописная транслитерация с регулярными выражениями и нестрогим контрактом входного типа; критичная уязвимость в просмотренном коде не установлена. Для новых реализаций предпочтителен единый проверенный транслитератор с тестами на кириллицу/латиницу/пустые и некорректные входы.

## 7. Установочные копии sale и sale_old: что подтверждено

Проверены `local/modules/mht/sale/install/index.php`, `local/modules/mht/sale_old/install/index.php`, их каталоги `install/admin`, а также административные endpoint-файлы.

- Оба install-скрипта вызывают `CopyDirFiles()` из пути `/bitrix/modules/sale/install/admin` в `/bitrix/admin`, а не напрямую из `/local/modules/mht/sale/admin` или `sale_old/admin`.
- Файл `local/modules/mht/sale/install/admin/1c_exchange.php` — короткая обёртка, которая подключает `/bitrix/modules/sale/admin/1c_exchange.php`. Аналогичная обёртка присутствует в `sale_old/install/admin/1c_exchange.php`.
- При этом в репозитории есть самостоятельные файлы `local/modules/mht/sale/admin/1c_exchange.php`, `sale/admin/old_1c_exchange.php` и `sale_old/admin/1c_exchange.php`. Они содержат отличающиеся реализации, но рассмотренные install-скрипты сами по себе не доказывают, что именно эти файлы копируются в web-root.
- Следовательно, наличие резервных файлов в Git не доказывает их доступность по URL. И наоборот, из одного статического дерева нельзя установить, какие файлы фактически лежат в `/bitrix/modules/sale/admin` на работающем сервере.

**Вывод:** фактический deployment path и доступность старых endpoint остаются открытой runtime-проверкой. На стенде сверить реальный путь модуля, содержимое `/bitrix/admin/1c_exchange.php`, `/bitrix/modules/sale/admin/1c_exchange.php`, регистрацию/версию модуля и веб-серверные правила. Не удалять резервные копии до этой сверки.

## 9. Пространство имён Ns\\Bitrix\\Helper: фабрики, пользовательские данные и подписка

Проверены все перечисленные файлы в `local/codes/Ns/Bitrix/Helper/`, включая вложенные `Files`, `Grafic`, `IBlock`, `Session`, `Subscribe`, `User`. Проверены фабрика `local/codes/Ns/Bitrix/Helper.php` и базовый `HelperCore.php`.

### 9.1. Subscribe/Users.php — предсказуемая ссылка авторизации

Класс содержит константу `DATA_SALT` в исходнике и формирует hash как `md5(login . DATA_SALT)`. Метод `checkAuthLink($login, $hash)` сравнивает переданный hash с этим значением. Если вызывающая страница использует этот метод для входа/авторизации, любой, кто знает login и может получить соль из исходного кода, способен вычислить корректный hash. Это не криптографический одноразовый токен: он постоянен для одного login и не имеет срока действия/одноразового использования.

Ссылки `authLink()` и `unsubscribeLink()` формируются с жёстким `http://` и вставляют login/hash в URL без URL-кодирования. Ссылка авторизации и ссылка отписки используют один и тот же hash, поэтому компрометация hash влияет на оба сценария.

Дополнительные дефекты:

- при валидных email/name переменная `$e` может остаться неопределённой, но далее проверяется через `is_array($e)`;
- в неуспешной ветке `checkAuthLink()` возвращается опечатка `Fasle`, то есть строка вместо boolean false;
- `DeleteByLogin()` не проверяет, найден ли пользователь и существует ли подписка, прежде чем обращаться к ID;
- обработка исключений вызывает нестандартную функцию `prentExpection()`; после неё не гарантирован корректный выход;
- в email-отправке логируются пользовательские данные через ChromePhp.

**Важное ограничение:** поиск по текущему дереву не обнаружил внешних вызовов `checkAuthLink()`, `Subscribe::useVariant('users')` или вызовов этого сервиса из страницы `/o_banke/press-center/`. Поэтому риск подделки ссылки подтверждён в реализации механизма, но фактическая доступность входа по этому механизму пока не доказана. Проверить шаблон/страницу и реальный autoload на VM.

### 9.2. Subscribe/CRUD.php — авторизация по ID без локальной проверки

Метод `Add()` получает ID из `$this->getSubscriber()`, загружает пользователя и вызывает `CUser::Authorize($this->user['ID'])`. Источник subscriber устанавливается через магический `HelperCore::__call()` (например, вызовом вида `withSubscriber(...)`). В самом классе нет проверки, что ID принадлежит текущему пользователю или что операция разрешена.

Если вызывающий код позволяет внешнему пользователю задавать subscriber ID и запускать `Add()`, это приводит к авторизации под чужим аккаунтом. Однако поиск по репозиторию не нашёл внешних вызовов `Create('subscribe')`/варианта `crud` или `withSubscriber()`; эксплуатация через текущий код не подтверждена.

Дополнительно подписка создаётся сразу как `ACTIVE=Y`, `CONFIRMED=Y`, `SEND_CONFIRM=N`, то есть без подтверждения email. Это должно соответствовать только доверенному административному/внутреннему сценарию, но не публичной форме.

**Решение:** не переносить. Не выполнять `CUser::Authorize()` на основании произвольного ID. Использовать текущего пользователя из серверного контекста, а подписку создавать через отдельный сервис с подтверждением и проверкой прав.

### 9.3. User/CRUD.php — детерминированный пароль

Новый пользователь получает пароль как первые/выбранные 6 символов MD5 от email и статической соли `alfa`. Значение предсказуемо, соль раскрыта в исходнике, длина пароля крайне мала. Метод `generate()` дополнительно проверяет неопределённую локальную переменную `$arFields[$type]` вместо `$this->arFields[$type]`; это нарушает проверку уже переданных значений и создаёт warning/неверную генерацию.

Исключение `CRUDGenerateExceprion.php` объявляет класс `CRUDGenerateException`, но имя файла содержит опечатку. Автозагрузка по PSR-4/имени файла может не найти класс, если нет отдельного classmap.

**Решение:** не переносить. Не генерировать пароль из email/статической соли; использовать штатный сценарий установки пароля через одноразовую ссылку. Исправить namespace/autoload и контракт генератора.

### 9.4. HelperCore.php — слишком широкая магия вызовов

Метод `__call()` распознаёт вызовы по вхождению подстрок `with` и `get` в любом месте имени метода, а не по строгому префиксу. Нет allowlist свойств, проверки количества аргументов и существования переменной; неизвестный getter возвращает неопределённый индекс. Любой неизвестный метод с `with` молча изменяет состояние и возвращает объект.

**Решение:** заменить на явные setters/getters или строгий builder с разрешённым списком полей и проверкой типов.

### 9.5. Session/Message.php — XSS в flash-сообщениях

`setFlashMessage()` принимает произвольный текст и сохраняет его в сессию; `getFlashMessage()` конкатенирует сообщения в HTML напрямую, добавляя только `<br/>`. Если в сообщение попадают пользовательские данные, при отображении возможен stored XSS. Метод также перебирает `$_SESSION['FLASHMESSAGES']` без проверки, что ключ существует и содержит массив.

**Решение:** хранить текст отдельно от HTML, экранировать при выводе; для доверенного HTML использовать отдельный тип/allowlist. Проверить фактические вызовы и место рендеринга.

### 9.6. Остальные реализации

- `IBlock/Pagination.php`: URL и атрибуты HTML формируются конкатенацией; `$url` вставляется в `href` и `data-url` без контекстного экранирования. Параметр page приводится к int, но не ограничивается допустимым диапазоном; `perPage` также не валидируется и может быть 0/отрицательным. При недоверенных значениях URL возможна инъекция в HTML-атрибуты.
- `Grafic/Background.php`: значения `PROPERTY_HEX_COLOR` вставляются в CSS без проверки формата цвета; путь изображения HTML-экранируется, но контекст CSS URL требует отдельной валидации/allowlist. Источник свойств — контент инфоблока, поэтому риск зависит от прав на редактирование.
- `Files/Checker.php`: не проверяет результат `CFile::GetFileArray()` перед чтением `CONTENT_TYPE`; константы определяются глобально через `define()`, возможны конфликты повторного подключения.
- `IBlock/Checker.php`: фильтр из `HelperCore` напрямую передаётся в API инфоблоков; класс не ограничивает разрешённые поля/операторы фильтра. Безопасность зависит от формирования фильтра вызывающим кодом.
- `IBlock/Validator.php`: `htmlspecialchars()` вызывается без явной кодировки/флагов и используется как «xss»-фильтр. Это не заменяет контекстное экранирование при выводе; метод email может изменить исходное значение до валидации.
- `IBlock/Text.php`: использует `substr()`/позицию последнего пробела без проверки результата; возможен пустой/неожиданный preview для короткого текста или строки без пробелов.
- `HelperCore.php`, фабрики `Files/Grafic/IBlock/Session/Subscribe/User`: статические singleton-свойства не инициализированы массивом; PHP создаёт массив при первом присваивании ключа, но обращение к отсутствующему ключу даёт notices. Нет строгой проверки типа variant.
- `Grafic/Background.php` использует жёстко заданные ID инфоблоков 12 и 38; перенос требует конфигурации, а не сохранения этих ID.
- `Modules.php` подключает `prolog_before.php` на уровне файла и бросает `Exception` без ведущего `\\`/импорта внутри namespace `Ns\\Bitrix`; bootstrap-побочный эффект и неверное разрешение класса.

### 9.7. Автозагрузка и фактические вызовы

`local/php_interface/init.php` подключает только `local/vendor/autoload.php` (если файл существует), конфиги и handlers. Комментарий README об отдельном создании `BitrixQuickStart\\Autoloader` не подтверждён содержимым текущего `init.php`. Наличие/настройки vendor autoload и фактическая загрузка namespace `Ns\\Bitrix` требуют проверки `composer.json`, vendor map и стенда.

Поиск по исходному дереву выявил использование фабрики `Ns\\Bitrix\\Helper::Create('iblock')` из парсеров `Ns\\Parser\\ABlog`, `Alfa`, `SbsTerminals`, `AlfaDocuments`, `AlfaTaxes`. Это подтверждает использование части IBlock helper (текст/проверка), но не подтверждает использование публичных сценариев Subscribe/User CRUD. Для подписки и авторизации внешние вызовы не найдены.

**Общее решение:** не переносить namespace helper-пакет как есть. Выделить необходимые функции, перепроектировать авторизацию/подписку, заменить магический builder на типизированные сервисы и закрыть XSS на выходе.

## 11. Уточнение фактического использования ранее просмотренных классов

Дополнительный поиск по вызовам и проверка потребителей уточнили статус:

- `IBlockData::getByCode('CATALOG')` реально вызывается в `local/php_interface/config/const.php` при определении константы `IBLOCK_ID__CATALOG`. Этот класс — активная зависимость конфигурации, а не неиспользуемая заготовка. Его миграция требует сохранить порядок загрузки/кеша и проверить доступность SITE_ID/iblock на раннем этапе bootstrap.
- `IBlockMenu::sort()` и `IBlockMenu::display()` реально вызываются статически из `local/components/menu/auto_menu/component.php`, хотя в классе методы объявлены нестатическими. Это несовместимо с корректным вызовом в PHP 8 и может приводить к fatal error. Требуется либо объявить методы static (если они не используют состояние объекта), либо создать экземпляр и передать корректный callable.
- `SendForms::convert_charset_array()` встречается в `local/ajax/index.php` только в закомментированных строках. Активное выполнение этого конвертера по найденному коду не подтверждено.
- `LIBlock.php` копируется установщиком `lema.lib` в его install include, но поиск не обнаружил вызовов `LIblock::getId()` в исходном дереве. Факт копирования в состав модуля подтверждён, активное использование метода — нет.
- `CLWLinkHelper` реально используется в `UserProp/CYouTubeProperty.php`; это имя класса необходимо сохранить или заменить одновременно с потребителем.
- Поиск не обнаружил вызовов `FollowService`, `CouponConditions`, `GetBasket`, `GetSection`, `SimpleHblockObject`, `IBlockMenu` кроме указанного menu component, а также Subscribe/User CRUD-фабрик. Для них активность не подтверждена; поиск не исключает динамические вызовы.

**Решение:** в реестре разделять «класс найден» и «вызов подтверждён». Для `IBlockData` и `IBlockMenu` учитывать фактические зависимости при планировании миграции; `SendForms` и `LIBlock` не считать активными только по наличию файла/копированию установщиком.
