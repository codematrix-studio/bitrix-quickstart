# Протокол интеграционной проверки advanced-модуля

Документ предназначен для проверки заготовки на отдельном тестовом сайте с установленным ядром 1С-Битрикс. Автономные smoke tests и CI не подтверждают работу на реальной базе данных и не заменяют этот протокол.

## 1. Условия и безопасность

Перед началом:

- Используйте отдельную копию сайта, не рабочий проект.
- Сделайте резервную копию файлов и базы данных.
- Зафиксируйте версию ядра Битрикс, версию PHP, тип и версию СУБД.
- Убедитесь, что PHP CLI и веб-среда используют ожидаемую версию PHP и одинаковую конфигурацию подключения к БД.
- Установите файлы модуля в штатный каталог модулей под ID `vendor.advancedmodule`; проверьте, что `include.php` и каталог `lib/` доступны автозагрузчику.
- Не запускайте проверки конкурентной установки на общем или рабочем сайте.

Первая версия MigrationRunner поддерживает только штатный класс `Bitrix\\Main\\DB\\MysqliConnection` с MySQL. PostgreSQL и пользовательские драйверы отклоняются до любых изменений БД. Одного значения `getType()` недостаточно для подтверждения фактической поддержки блокировки.

## 2. Проверка окружения до установки

Зафиксируйте:

- PHP version;
- версию главного модуля `main`;
- класс объекта `Application::getConnection()`;
- значение `getType()`;
- доступность и успешность именованной блокировки на тестовом соединении.

Ожидается штатный класс соединения для выбранной СУБД. Если класс или тип не поддерживаются, runner должен завершиться понятным исключением до изменения схемы.

## 3. Первая установка

На чистой тестовой копии, где модуль ещё не зарегистрирован:

1. Запустите штатную установку модуля из административной части.
2. Убедитесь, что установка завершилась успешно и модуль зарегистрирован.
3. Проверьте наличие таблицы примера `b_vendor_advancedmodule_example`.
4. Проверьте наличие ledger `b_vendor_advancedmodule_migrations`.
5. Проверьте, что в ledger присутствует одна запись с ID `202611240001_create_example_table` и SHA-256 checksum.
6. Проверьте, что постоянная подписка `main:OnAfterUserAdd` зарегистрирована ровно один раз.
7. Проверьте, что системный агент `Vendor\\AdvancedModule\\Agent\\ExampleAgent::run();` зарегистрирован для `vendor.advancedmodule` с `USER_ID = NULL/false`.

Не добавляйте реальную бизнес-логику в примерный обработчик и не создавайте тестовых пользователей на рабочем сайте.

## 4. Повторная установка

Повторно запустите процедуру установки уже установленного модуля.

Ожидается:

- модуль остаётся зарегистрированным;
- существующая таблица примера не пересоздаётся;
- запись о применённой миграции не дублируется;
- checksum ранее применённой миграции не меняется;
- обработчик события и агент не регистрируются повторно;
- установщик не выполняет повторно этапы установки файлов, событий и агентов исправной установки.

Ветка повторного вызова `DoInstall()` для установленного модуля предназначена для проверки и применения новых миграций.

## 5. Проверка агента

1. Найдите агент в административном списке агентов.
2. Сверьте точную строку вызова, ID модуля и системный `USER_ID`.
3. Вызовите `ExampleAgent::run()` в контролируемом тестовом контексте.
4. Убедитесь, что метод возвращает ту же строку вызова для следующего запуска.
5. Убедитесь, что пример не выполняет побочных действий.

Для проверки собственного рабочего агента отдельно добавьте тест его бизнес-логики, ограничений времени, повторного запуска и обработки исключений. Наличие записи в `b_agent` само по себе не доказывает корректность фоновой задачи.

## 6. Проверка миграций

Проводите только на одноразовой копии БД:

- Повторный запуск runner не должен повторно применять уже записанную миграцию.
- Новая миграция с новым возрастающим ID должна примениться и получить одну запись в ledger.
- Повторный запуск после успешного применения должен пропустить её.
- Изменение файла уже применённой миграции должно приводить к ошибке checksum.
- Неизвестный ID в ledger должен приводить к ошибке.
- Неподдерживаемый класс соединения должен быть отклонён до создания ledger.
- Если блокировку получить не удалось, runner не должен создавать ledger или запускать миграции.
- Ошибка транзакционной миграции должна откатить изменения и не оставлять запись в ledger.
- Нетранзакционная миграция после частичного сбоя должна безопасно повторяться; это ответственность самой миграции.

Не редактируйте уже применённые миграции. Для изменения схемы добавляйте новую миграцию.

### Конкурентный запуск

На отдельной одноразовой БД запустите два независимых процесса, которые одновременно вызывают runner с одним и тем же новым тестовым ID.

Ожидаемый результат: только один процесс выполняет миграцию; второй после получения блокировки видит запись в ledger и пропускает её либо корректно завершается по тайм-ауту блокировки. В ledger должна остаться одна запись. Проверку выполняйте отдельным тестовым harness, а не одновременным нажатием кнопки установки в административной части.

## 7. Проверка событий

1. Найдите постоянную подписку `main:OnAfterUserAdd` в списке обработчиков событий.
2. Проверьте модуль-источник, тип события, модуль-получатель, класс и метод.
3. Убедитесь, что регистрация выполнена через `registerEventHandlerCompatible()`, поскольку `OnAfterUserAdd` относится к классическому API.
4. Убедитесь, что обработчик получает массив полей пользователя по ссылке: `array &$fields`. Не передавайте в него объект `Bitrix\\Main\\Event` — это другой контракт событий D7.
5. Для собственных D7-событий используйте отдельные обработчики с контрактом `Bitrix\\Main\\Event` и соответствующую регистрацию через `registerEventHandler()`.

Примерный обработчик намеренно пустой. Проверка его бизнес-эффекта не входит в этот протокол.

## 8. Удаление

На тестовой копии выполните штатное удаление модуля.

Ожидается:

- модуль снят с регистрации;
- постоянная подписка удалена;
- агент удалён;
- ledger и таблица примера сохранены, поскольку текущая заготовка по умолчанию не удаляет пользовательские данные.

Повторите удаление. Оно должно завершиться безопасно. Отдельно проверьте, что повторная установка после удаления не ломается из-за сохранённых таблиц и ledger.

## 9. Проверка восстановления после сбоя

Этот сценарий выполняйте только на отдельной одноразовой копии.

Имитируйте сбой после каждого этапа установки: база данных, события, агенты и файлы. Для каждого случая проверьте:

- установка сообщает об ошибке;
- уже начатые этапы откатываются в обратном порядке;
- при успешном откате регистрация модуля снимается;
- если откат не завершён, модуль остаётся зарегистрированным и сохраняет отметку `INSTALLATION_INCOMPLETE`;
- повторный запуск после устранения причины завершает восстановление;
- ошибка обновления схемы уже установленного модуля не удаляет существующую регистрацию и данные.

Не внедряйте fault injection в рабочую копию модуля. Используйте временный тестовый вариант установщика или отдельный harness.

## 10. Матрица результатов

Заполните отдельно для поддерживаемой конфигурации MySQL:

| Проверка | MySQL |
|---|---|
| Первая установка | Не проверено |
| Повторная установка | Не проверено |
| Ledger и checksum | Не проверено |
| Именованная блокировка | Не проверено |
| Конкурентный запуск | Не проверено |
| Транзакционная миграция | Не проверено |
| Частичный сбой DDL | Не проверено |
| События и агент | Не проверено |
| Удаление и повторная установка | Не проверено |
| Восстановление после сбоя | Не проверено |

После каждого прогона укажите дату, версии PHP/ядра/СУБД, SHA проверяемого коммита и ссылку на журнал проверки.

## 11. Критерии завершения

Интеграционную проверку можно считать пройденной только если все обязательные строки матрицы проверены на реальном ядре и MySQL, а результаты сохранены. Успешный CI на PHP 8.1–8.5 и автономные smoke tests отмечаются отдельно и не подменяют эти результаты.
