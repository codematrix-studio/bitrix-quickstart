# Проверка advanced-каркаса на реальном Bitrix

Этот протокол дополняет автономные smoke-тесты. Он не заменяет их и не должен выполняться на рабочем сайте.

## Условия стенда

- Отдельная тестовая установка 1С-Битрикс с возможностью восстановить базу из резервной копии.
- MySQL и штатный драйвер `Bitrix\\Main\\DB\\MysqliConnection`. Первая версия MigrationRunner намеренно не заявляет поддержку PostgreSQL и других драйверов.
- Версия PHP входит в матрицу проекта.
- Шаблон размещён как модуль `vendor.advancedmodule` в `/local/modules/vendor.advancedmodule`; ID и namespace пока оставлены тестовыми.
- До начала записаны версия ядра, PHP, MySQL и движок таблиц.

## 1. Первая установка

1. Установить модуль штатным механизмом административной части.
2. Убедиться, что модуль зарегистрирован и подключается через `Loader::includeModule('vendor.advancedmodule')`.
3. Проверить наличие таблиц:
   - `b_vendor_advancedmodule_migrations`;
   - `b_vendor_advancedmodule_example`.
4. Проверить, что в ledger есть ровно одна запись `202611240001_create_example_table`, а `CHECKSUM` содержит 64 шестнадцатеричных символа.
5. Проверить наличие колонок `ID` и `NAME` в таблице примера.
6. Проверить, что обработчик события и агент зарегистрированы ровно по одному разу.

## 2. Повторный запуск установщика

В административном контексте повторно вызвать `DoInstall()` экземпляра класса `vendor_advancedmodule`.

Ожидаемый результат:

- вызов завершается успешно;
- в ledger остаётся ровно одна запись на каждую миграцию;
- checksum не меняется;
- повторные вызовы не создают дубли обработчика события или агента;
- таблица с пользовательскими данными не очищается.

## 3. Проверка блокировки

Проводить в двух отдельных HTTP/CLI-процессах, чтобы это были разные DB-соединения.

1. В первом процессе получить `$connection->lock('vendor.advancedmodule.migrations', 30)` и удерживать блокировку.
2. Во втором процессе запустить установочную процедуру модуля.
3. Убедиться, что runner ждёт не более заданного таймаута (10 секунд), завершает запуск понятной ошибкой и не меняет ledger.
4. Освободить блокировку в первом процессе через `unlock()`.
5. Повторить установку и убедиться, что она проходит успешно.

Не запускайте оба сценария через один объект соединения: такой тест не проверит конкуренцию между запросами.

## 4. Проверка безопасного удаления

1. Добавить тестовую строку в таблицу примера.
2. Удалить модуль штатным механизмом административной части.
3. Проверить, что модуль снят с регистрации, а принадлежащие ему обработчик события и агент удалены.
4. Проверить, что ledger, таблица примера и тестовая строка сохранены.
5. Повторно установить модуль и убедиться, что существующая миграция распознана по ID/checksum и не очищает данные.

## 5. Проверка частичного сбоя миграции

Только на одноразовой копии стенда:

1. Добавить отдельную временную миграцию, которая создаёт собственную тестовую таблицу, а затем намеренно выбрасывает исключение.
2. Убедиться, что миграция не записана в ledger, а диагностическое сообщение содержит её ID.
3. Изменить временную миграцию на идемпотентный вариант, который безопасно продолжает работу с уже созданной таблицей.
4. Повторить запуск и убедиться, что миграция записана в ledger один раз.
5. Удалить временную миграцию только после восстановления тестовой копии или удаления её тестовых объектов. Не менять файлы уже применённых постоянных миграций.

## Результат проверки

Зафиксировать версию ядра, PHP, MySQL, движок таблиц и результат каждого сценария. Любой сбой — отдельная задача с логом и точным шагом воспроизведения. Не объявлять поддержку версии ядра или СУБД только на основании автономного smoke-теста.
