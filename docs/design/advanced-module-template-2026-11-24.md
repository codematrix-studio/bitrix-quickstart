# Проектирование расширенной заготовки модуля Битрикс

**Статус:** архитектурное решение перед реализацией  
**Дата:** 2026-11-24  
**Область:** `templates/modules/advanced`

## Цель и границы

`basic` остаётся минимальным каркасом. `advanced` предназначен для модулей, которым действительно нужны постоянные обработчики событий, агенты и эволюция собственной схемы БД.

Заготовка должна быть копируемым примером, а не фреймворком поверх Битрикс. Не добавлять демонстрационные таблицы, обработчики и бизнес-логику, не нужные для объяснения контракта. Все идентификаторы `vendor.module`, namespace и имена классов явно помечаются как заменяемые.

Отдельно рассматриваются два разных механизма обновления:

- **Внутренние миграции БД** — выполняются установленным модулем на сайте и изменяют его собственную схему.
- **SiteUpdate / Marketplace updater** — поставляет файлы и переходы между пакетами обновлений. Не является migration runner и не должен рассчитывать на классы из файлов, которые ещё не скопированы.

Marketplace updater будет отдельным примером в документации/фикстуре пакета обновления, а не исполняемым файлом рядом с внутренними миграциями. Это подчёркивает различие двух жизненных циклов.

## Жизненный цикл установщика

1. Проверить права администратора.
2. Зарегистрировать модуль, чтобы его классы были доступны через штатную загрузку.
3. Выполнить этапы установки в определённом порядке: подготовка схемы/миграции, постоянные обработчики, файлы.
4. Каждый этап должен быть повторяемым и возвращать явный результат; частично выполненный этап должен быть безопасен при повторном запуске.
5. При ошибке откатывать только то, что действительно можно безопасно компенсировать. Не обещать транзакционный rollback для DDL.
6. При удалении снять регистрации обработчиков и выполнить политику удаления данных отдельно от снятия регистрации модуля. Удаление пользовательских данных не должно быть скрытым побочным эффектом.

Уже проверенный lifecycle из `basic` — отправная точка, но переносить его код следует после отдельной сверки и тестов, а не копированием вслепую.

## Обработчики событий

- Постоянные обработчики регистрируются через `Bitrix\\Main\\EventManager::getInstance()->registerEventHandler()` во время установки.
- Снятие выполняется через `unRegisterEventHandler()` с тем же полным набором идентифицирующих аргументов.
- Вынести параметры регистрации в одно место, чтобы install/uninstall не расходились.
- Для современных D7-событий пример принимает `Bitrix\\Main\\Event`.
- Для старых событий, передающих legacy-аргументы (в том числе по ссылке), показать отдельный совместимый вариант через `registerEventHandlerCompatible()`, только если конкретный пример действительно требует старого контракта.
- Не использовать `addEventHandler()` как замену постоянной регистрации: это регистрация только на текущий запрос.
- Не рассчитывать, что `ModuleManager::unRegisterModule()` удалит обработчики: это отдельная обязанность модуля.

## Агенты

- Пример регистрирует агент через `CAgent::AddAgent()` с точным строковым именем вызова и MODULE_ID.
- Формат имени вызова должен совпадать при регистрации и ручном снятии. Не использовать ведущий обратный слеш, если он приводит к несовпадению сохранённой строки и строки поиска.
- Метод агента возвращает строку следующего вызова либо пустое значение для завершения.
- Проверять результат регистрации; при `false` извлекать исключение через предусмотренный legacy API и прерывать обязательный этап установки.
- Удаление агента при штатном `ModuleManager::unRegisterModule()` уже выполняется ядром для агентов данного MODULE_ID. Не дублировать это удаление без конкретной причины. При этом отдельно документировать поведение частичного uninstall до снятия регистрации.

## Внутренние миграции БД

### Контракт миграции

Каждая миграция — отдельный неизменяемый PHP-файл с уникальным упорядочиваемым идентификатором и явными методами применения/отката. После публикации изменять уже применённую миграцию нельзя: исправление оформляется новой миграцией.

Runner обязан:

- хранить ledger применённых миграций в таблице модуля (идентификатор, время применения, при необходимости checksum);
- выполнять миграции строго в детерминированном порядке;
- пропускать уже применённые миграции и безопасно завершаться при повторном запуске;
- обнаруживать изменённый checksum ранее применённой миграции и останавливать процесс с понятной ошибкой;
- не отмечать миграцию применённой до успешного завершения её обязательных операций;
- выдавать понятный отчёт о текущей и целевой версии схемы;
- не выполнять автоматический destructive rollback при ошибке.

### Транзакции и блокировки

Нельзя обещать атомарность всех миграций: MySQL DDL может вызывать implicit commit, а поведение зависит от движка и версии. Транзакция допустима только для операций и платформ, где она действительно поддерживается.

До реализации выбрать и зафиксировать минимально поддерживаемые СУБД и версии ядра. Механизм конкурентной блокировки должен быть специфичен для поддерживаемого драйвера и проверять результат получения блокировки. Если надёжную блокировку обеспечить нельзя, runner должен отказаться от параллельного выполнения с явным сообщением, а не продолжать молча.

Миграции не должны автоматически удалять данные. Для destructive изменений нужна отдельная явная политика, резервная копия/план восстановления и документация.

### Bitrix DB API

Реализация должна опираться на публичный DB connection API ядра (получение соединения через `Bitrix\\Main\\Application`, выполнение SQL через connection и quoting через SQL helper), а не на прямое использование `mysqli`/PDO. До написания runner повторно сверить точные сигнатуры транзакций, исключений, параметров запросов и доступность нужных методов на заявленном диапазоне версий Битрикс.

## Marketplace / SiteUpdate updater

Пример пакета обновления документируется отдельно. Учитывать контракт SiteUpdate:

- пакет содержит `install/version.php` и языковое описание;
- updater может запускаться повторно — его операции должны быть идемпотентны;
- updater исполняется до копирования файлов текущего пакета;
- он может быть запущен для сайта, где модуль не установлен;
- нельзя вызывать классы/методы, которые появятся только после копирования обновляемых файлов;
- последовательность пакетов одного модуля сохраняется, но порядок обновлений разных модулей не гарантируется.

Внутренний migration runner не запускается из updater как скрытая обязанность. Если пакет обновления должен менять схему, это делается через совместимый с текущей версией код и явно документированный переход, а не через предположение, что новая версия модуля уже загружена.

## Тестовая стратегия

Автономные smoke-тесты на PHP 8.1–8.5 с контролируемыми заглушками должны покрыть:

- повторный install и uninstall;
- сбой на каждом этапе и повторное восстановление;
- симметрию параметров регистрации/снятия event handler;
- отсутствие дублей обработчиков при повторной установке;
- точное имя агента, MODULE_ID и реакцию на ошибку AddAgent;
- порядок миграций, ledger, повторный запуск и checksum mismatch;
- ошибку миграции без ложной отметки об успешном применении;
- отказ при невозможности получить блокировку;
- отсутствие автоматического destructive rollback;
- идемпотентность updater-примера и отсутствие вызовов классов из ещё не установленного пакета.

Эти тесты проверяют логику шаблона, но не заменяют проверку на реальном ядре Битрикс. Перед production использованием обязательны стендовые install/update/uninstall тесты на поддерживаемых версиях ядра и СУБД.

## Порядок реализации

1. Каркас `advanced`, lifecycle и постоянные обработчики событий.
2. Агент и тесты его идентичности/регистрации.
3. Migration runner и ledger после окончательного выбора DB/locking contract.
4. Отдельный SiteUpdate updater example и документация.
5. Финальная сверка документации, CI и ручной стендовый чек-лист.

Каждый этап — отдельный небольшой PR. `basic` не усложнять.
