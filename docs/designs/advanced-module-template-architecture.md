# Архитектура расширенной заготовки модуля Bitrix

**Статус:** проектирование, до реализации  
**Дата:** 2026-11-24  
**Цель:** определить границы и проверяемые контракты шаблона `advanced`, не усложняя `basic`.

## 1. Назначение

`basic` остаётся минимальным каркасом собственного модуля: регистрация, автозагрузка и безопасный жизненный цикл установки/удаления.

`advanced` предназначен для модулей, которым действительно нужны постоянные обработчики событий, фоновые агенты и управляемое изменение схемы БД. Это не «обязательная правильная структура» для каждого модуля: ненужные подсистемы можно не переносить в конкретный проект.

Marketplace/SiteUpdate updater рассматривается отдельно от runtime-кода и внутренних миграций. Эти механизмы имеют разные точки запуска и ограничения.

## 2. Принципы

1. **Явные границы ответственности.** Installer управляет жизненным циклом; Events — постоянными подписками; Agents — фоновыми заданиями; Migrations — схемой данных.
2. **Идемпотентность.** Повторный запуск install, uninstall, восстановления и migration runner не должен создавать дубликаты или повреждать состояние.
3. **Обратимость там, где она реальна.** Установка откатывает начатые этапы; удаление снимает только принадлежащие модулю ресурсы. Уже применённые изменения данных не следует автоматически «откатывать» разрушительными обратными миграциями.
4. **Безопасный отказ.** Ошибка обязательного шага не маскируется успешным результатом; состояние остаётся диагностируемым и допускает повторную попытку.
5. **Совместимость с заявленной матрицей PHP.** Не использовать синтаксис и API выше минимальной поддерживаемой версии.
6. **Минимум магии.** Миграции и регистрации читаются из явных списков/классов; не сканировать произвольные каталоги и не исполнять неизвестные файлы.
7. **Проверяемость.** Smoke-тесты проверяют собственную логику на заглушках; реальные контракты ядра отдельно подтверждаются на тестовом сайте.

## 3. Предлагаемая структура

```text
templates/modules/advanced/
├── README.md
├── include.php
├── install/
│   ├── index.php
│   ├── version.php
│   ├── events.php
│   ├── agents.php
│   └── migrations/
│       ├── MigrationInterface.php
│       ├── MigrationRegistry.php
│       ├── MigrationRunner.php
│       └── Version202611240001CreateExampleTable.php
├── lib/
│   ├── Event/
│   │   └── ExampleEventHandler.php
│   └── Agent/
│       └── ExampleAgent.php
├── updater/
│   └── README.md
└── lang/
    └── ru/
        └── install/
            └── index.php
```

Это ориентир, а не требование создать каждый файл независимо от необходимости. В частности, пример таблицы должен быть включён только если он демонстрирует полезный законченный сценарий и сопровождается корректной миграцией удаления/обновления.

Marketplace-пакетный updater не обязан находиться в runtime-каталоге установленного модуля. В документации будет показан отдельный минимальный пример структуры пакета обновления SiteUpdate; его нельзя подключать как обычный install-stage.

## 4. Жизненный цикл установки

Планируемые этапы:

1. Проверить административные права.
2. Зарегистрировать модуль, если он ещё не зарегистрирован.
3. Подключить модуль и его классы.
4. Подготовить/обновить схему БД через migration runner.
5. Зарегистрировать постоянные обработчики событий.
6. Зарегистрировать необходимые агенты.
7. Завершить установку и очистить служебное состояние.

Порядок удаления:

1. Проверить административные права.
2. Снять постоянные обработчики событий.
3. Удалить принадлежащие модулю агенты либо положиться на документированную очистку при снятии регистрации модуля — выбрать один согласованный путь, не выполнять дублирующие операции без причины.
4. Удалить данные только согласно явно выбранной политике сохранения/удаления.
5. Снять регистрацию модуля последней.

Фактический порядок будет уточнён при реализации на основе текущего install-контракта и выбранной политики данных. Нельзя удалять таблицы или пользовательские данные по умолчанию без явного решения автора модуля.

Для каждого этапа обязательны:
- чёткий результат успеха/ошибки;
- идемпотентность;
- безопасный повторный запуск после частичного сбоя;
- диагностическое сообщение без утечки секретов.

## 5. Постоянные обработчики событий

Регистрация выполняется через `Bitrix\\Main\\EventManager::getInstance()->registerEventHandler()` при установке, снятие — через `unRegisterEventHandler()` при удалении.

Требования к реализации:

- Описать каждую подписку одной неизменной декларацией: fromModuleId, eventType, toModuleId, class, method, при необходимости path и method arguments.
- Использовать один и тот же набор аргументов для регистрации и снятия.
- Не использовать `addEventHandler()` для постоянной регистрации: это подписка на текущий запрос.
- Для D7-событий показать обработчик, принимающий объект `Bitrix\\Main\\Event`.
- Для legacy-события с аргументами по ссылке, если такой пример будет нужен, использовать совместимый API и отдельный пример; не смешивать его контракт с D7.
- Не считать снятие регистрации модуля эквивалентом удаления подписок: события снимаются явно.
- Проверить поведение повторной регистрации и точное совпадение аргументов при unregister.

В шаблоне не должно быть фиктивного обработчика, который меняет данные сайта только ради демонстрации. Пример должен быть безвредным и показывать контракт.

## 6. Агенты

Агенты регистрируются через `CAgent::AddAgent()` с явными параметрами и module ID.

Требования:

- Код callback доступен через установленный модуль и его `include.php`.
- Имя вызова стабильно и точно совпадает с тем, которое передаётся при удалении.
- Повторная установка не добавляет дубликат.
- Callback возвращает корректную строку следующего вызова либо прекращает выполнение согласно контракту выбранного API.
- Ошибка регистрации проверяется; при неуспехе install-stage завершается ошибкой.
- Учитывается, что снятие регистрации модуля удаляет связанные с ним агенты. Не добавлять второй общий механизм удаления без доказанной необходимости.
- Пример не должен выполнять тяжёлую или потенциально опасную работу при каждом запуске.

Поддержку `Bitrix\\Main\\Type\\Callback` не считать базовой, пока не определена минимальная версия ядра. Для переносимого примера сначала использовать документированный строковый callback.

## 7. Внутренние миграции БД

Миграции предназначены для изменения схемы/данных уже установленного модуля при его обновлении или контролируемом развёртывании. Они не являются SiteUpdate updater.

### 7.1. Идентификаторы и реестр

- Каждая миграция имеет уникальный неизменяемый ID, например timestamp + короткое имя.
- Реестр миграций явный и упорядоченный; не выполнять произвольные PHP-файлы из каталога.
- Запись о применении содержит ID миграции, время, результат/метаданные версии и, если это оправдано, контрольную сумму.
- Уже применённый ID повторно не запускается.
- Изменённое содержимое миграции с уже применённым ID считается ошибкой процесса разработки; исправление оформляется новой миграцией.

### 7.2. Runner

Runner должен:
- читать текущее состояние схемы из отдельного ledger;
- проверять пропуски/неизвестные применённые ID;
- выполнять миграции в детерминированном порядке;
- записывать применение только после успешного выполнения;
- безопасно останавливаться на первой ошибке;
- предотвращать конкурентный запуск через механизм блокировки, выбранный после проверки DB API;
- поддерживать диагностический режим без выполнения изменений, если его можно реализовать надёжно.

Версия схемы БД независима от `MODULE_VERSION`: релиз модуля может содержать несколько миграций, а не каждое обновление PHP-кода меняет схему.

### 7.3. Транзакции и DDL

Нельзя обещать универсальный rollback DDL. Поддержка транзакций и поведение DDL зависят от СУБД, движка таблиц и конкретной операции.

До реализации нужно выбрать и документировать конкретный Bitrix DB abstraction API для заявленной матрицы. Не смешивать прямые вызовы драйвера, ORM и абстракцию соединения без необходимости. Для каждой миграции явно указывать, является ли она транзакционной и как восстанавливается после частичного выполнения.

### 7.4. Удаление и данные

По умолчанию uninstall не должен безусловно удалять таблицы с пользовательскими данными. Шаблон должен явно разделять:
- снятие runtime-регистраций;
- сохранение данных при удалении модуля;
- полное удаление данных по отдельному подтверждаемому сценарию.

Destructive migrations требуют отдельного описания риска и резервного копирования. Автоматические down-миграции не являются обязательной частью первого runner: для многих изменений безопаснее forward-only миграции с отдельной процедурой восстановления.

## 8. SiteUpdate / Marketplace updater

Это отдельный формат поставки обновлений, не вызывающий внутренний migration runner как обычный runtime-сервис без проверки доступности кода.

Документация примера должна учитывать:

- пакет обновления содержит обязательные `install/version.php` и `description.<lang>`; updater-файл/каталог и `version_control.txt` опциональны;
- updater может запускаться повторно и обязан быть идемпотентным;
- updater исполняется до копирования файлов текущего пакета;
- нельзя вызывать классы/API, которые появятся только после копирования этого пакета;
- updater может запускаться даже если модуль на сайте не установлен;
- обновления одного модуля применяются последовательно, но порядок между разными модулями не гарантирован.

Поэтому пример должен быть минимальным, самодостаточным, совместимым с PHP, который реально поддерживает распространяемый модуль, и не зависеть от нового runtime-кода. SiteUpdate updater и внутренние DB migrations должны иметь раздельные README и тестовые сценарии.

| Этап | Содержание | Проверки |
|---|---|---|
| 0. Проектирование | Этот документ; границы и контракты | Ревью документации |
| 1. Каркас + события | Каталог advanced, installer, симметричная регистрация EventManager | Stub-тесты install/uninstall, повторов и парности аргументов |
| 2. Агенты | Один безопасный пример агента и его lifecycle | Точное имя callback, повторная регистрация, очистка |
| 3. Migration runner | Ledger, явный registry, runner и одна полезная миграция | Порядок, повтор, ошибка, неизвестный ID, lock, частичный сбой |
| 4. Marketplace updater | Отдельный пример пакета и документация | Статические проверки структуры/идемпотентности; ограничения отмечены |
| 5. Финальная проверка | Общая матрица PHP и проверка на реальном ядре | CI + отдельный стендовый протокол |

Каждый PR должен иметь одну понятную ответственность. Не сливать PR до успешного CI. Реальные проверки на ядре не имитировать автономными заглушками.

## 10. Что нужно подтвердить до PR с кодом

1. Точный DB abstraction API и поддерживаемые сигнатуры для минимальной версии Bitrix, которую мы заявим.
2. Практический механизм блокировки migration runner без зависимости от одной СУБД либо честно ограниченная матрица СУБД.
3. Контракт и размещение updater-файла для целевого способа публикации.
4. Реальный формат callback агента для выбранной матрицы версий ядра.
5. Состав минимального полезного примера миграции без ненужной демонстрационной таблицы.

До подтверждения этих пунктов не закладывать предположения в публичный шаблон.

## 10.1. Проверка DB API Битрикс (2026-11-24)

Проверено по официальному справочнику BitrixFramework:

- Соединение получать через `Bitrix\\Main\\Application::getConnection()`; вручную создавать объект `Connection` нельзя.
- Для прямого SQL и операций со структурой БД использовать `Bitrix\\Main\\DB\\Connection`. Для сущностей, описанных ORM-классами, использовать `DataManager`.
- Для запросов доступны `query()`, `queryExecute()`, `queryScalar()`; значения и имена SQL подготавливать через `getSqlHelper()`.
- `startTransaction()`, `commitTransaction()` и `rollbackTransaction()` доступны с Bitrix 14.0.0. Вложенная транзакция использует SAVEPOINT. Это не означает, что DDL любой поддерживаемой СУБД можно откатить.
- `Connection::lock()` и `unlock()` — именованные блокировки, но поведение зависит от конкретной реализации соединения: базовая реализация ничего не блокирует и возвращает `true`; MySQL использует `GET_LOCK`; PostgreSQL вызывает `bx_get_lock` / `bx_release_lock`. В PostgreSQL имя блокировки сводится к CRC32, поэтому возможны коллизии имён.

### Решения для первого migration runner

1. Получать соединение только через `Application::getConnection()`; передавать один и тот же объект соединения runner, ledger и миграциям.
2. Не считать `lock() === true` достаточной гарантией. Сначала определить поддерживаемые типы соединений и реализовать явные lock adapters. Для первого рабочего варианта безопаснее заявить MySQL и использовать `Connection::lock()/unlock()` только на проверенной реализации; неизвестный тип БД должен завершать запуск понятной ошибкой, а не продолжать без блокировки.
3. PostgreSQL не включать в заявленную матрицу до отдельной проверки наличия и жизненного цикла функций `bx_get_lock` / `bx_release_lock` на чистой установке, а также поведения при потере соединения. CRC32-коллизии должны быть отмечены как ограничение.
4. Не оборачивать все миграции в одну автоматическую транзакцию. Миграция явно определяет допустимость транзакции; DDL и частично выполненные операции требуют идемпотентного сценария продолжения/восстановления.
5. Запись в ledger создавать только после успешного завершения миграции. Если процесс оборвался после изменения схемы, но до записи ledger, повторный запуск должен безопасно распознать уже выполненную часть либо остановиться с диагностикой; считать такую ситуацию автоматически откатываемой нельзя.
6. Runner должен удерживать именованную блокировку на всём цикле «прочитать ledger → выполнить миграции → записать ledger» и освобождать её в `finally`. Если освобождение не удалось, ошибка должна попасть в диагностику, но не подменять исходную ошибку миграции.

Минимальная матрица первого релиза migration runner: MySQL на проверенной версии Bitrix. Поддержка PostgreSQL — отдельная задача после подтверждения инфраструктурных функций и интеграционных тестов. Это ограничение относится к конкурентному запуску runner, а не является утверждением о невозможности работы остального шаблона на PostgreSQL.
