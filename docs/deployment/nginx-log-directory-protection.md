# Защита каталога логов при использовании Nginx

В проекте файловый логгер `Project\\Support\\Logger` по умолчанию выключен. При включении он записывает JSON Lines в `local/logs/app-YYYY-MM-DD.log`.

В репозитории уже есть:
- `local/logs/.htaccess` — запрет HTTP-доступа для Apache 2.4;
- `local/logs/web.config` — запрет доступа для IIS;
- `local/logs/index.php` — закрывает листинг/вход в каталог через индексный URL.

**Важно:** Nginx не обрабатывает `.htaccess` и не использует `web.config`. Если сайт работает под Nginx, эти файлы сами по себе не защищают прямые запросы к `/local/logs/*.log`.

## Обязательное правило для Nginx

Добавьте правило в конфигурацию соответствующего server/location и проверьте его после reload:

```nginx
location ^~ /local/logs/ {
    deny all;
}
```

После изменения конфигурации проверьте, что прямой запрос к существующему тестовому файлу в `/local/logs/` возвращает отказ (обычно HTTP 403), а не содержимое файла.

## Предпочтительный вариант

Если конфигурация проекта позволяет, храните рабочие логи вне document root. Тогда доступность каталога не будет зависеть только от правил веб-сервера.

## Данные в логах

`Logger` сериализует переданные `message` и `context` без автоматической фильтрации. Не передавайте в них пароли, токены, cookie, платёжные реквизиты и лишние персональные данные. Текущая проверка `tests/logger_smoke.php` подтверждает формат записи и переключение логгера, но не проверяет HTTP-доступ к логам или настройки конкретного веб-сервера.

## Границы проверки

Это требование к развёртыванию, а не утверждение об уязвимости конкретного production-сайта. Наличие или отсутствие внешнего Nginx deny-rule можно установить только по конфигурации фактического сервера.
