# Стандарты библиотеки CodeMatrix STUDIO

## 1. Совместимость

- Базовый синтаксис новых решений: PHP 8.1+.
- Если решение требует более высокой версии PHP, это явно указывается в README и composer-конфигурации.
- Использовать D7 API, когда он покрывает задачу.
- Совместимость с редакциями, версиями модулей и версиями ядра БУС не предполагать автоматически: указывать проверенную конфигурацию.
- Не ломать существующие публичные контракты без явного major-изменения и описания миграции.

## 2. Архитектура

- Одна директория — одно решение и одна основная ответственность.
- Минимизировать глобальное состояние и статические зависимости.
- Не выполнять регистрацию событий, создание таблиц, HL-блоков, агентов или файлов при простом include/autoload.
- Побочные эффекты должны запускаться явным методом/командой и быть документированы.
- Для внешних зависимостей использовать интерфейсы или адаптеры, если это оправдано сложностью решения.
- Не добавлять абстракции «на будущее», если они не решают текущую задачу.

## 3. Безопасность

- Валидировать и нормализовать все внешние данные на границе приложения.
- Проверять авторизацию и право доступа к каждому целевому объекту, а не только к исходному запросу.
- Для изменяющих действий в веб-контексте проверять CSRF/сессию средствами БУС.
- Не доверять ID, переданным клиентом: проверять принадлежность объекта, тип, инфоблок и допустимую связь.
- SQL — только параметризованный/безопасный API; не конкатенировать пользовательский ввод.
- Ограничивать сортировку, поля и направления сортировки allowlist-ом.
- Экранировать вывод в соответствии с контекстом HTML, атрибутов, URL и JavaScript.
- Для файлов проверять допустимый тип, размер, путь и права; не строить путь напрямую из пользовательского ввода.
- Не писать пароли, токены, персональные данные и секреты в логи или ответы API.
- Не возвращать секреты и внутренние исключения клиенту.

## 4. Код и документация

- Стиль: PSR-12, если он не конфликтует с требованиями окружения БУС.
- Для публичных классов и методов — PHPDoc на русском языке.
- Указывать типы аргументов и возвращаемых значений; избегать неограниченных mixed там, где можно описать контракт.
- Имена классов и методов — предметные, без неоднозначных сокращений.
- README каждого решения должен содержать назначение, требования, установку, API, примеры, ограничения и статус.
- Комментарии объясняют причины и нетривиальные решения, а не пересказывают код.

## 5. Ошибки и логирование

- Предпочитать предсказуемые исключения или типизированный результат вместо неоднозначных false/null.
- Не подавлять ошибки оператором @ без веской причины.
- Логировать контекст, достаточный для диагностики, но без секретов и лишних персональных данных.
- Не менять глобальные настройки обработки ошибок.

## 6. Производительность

- Не выполнять запросы в цикле, если можно получить данные пакетно.
- Кэшировать только при определённой стратегии ключей, TTL и инвалидации.
- Не вводить кэширование без понимания актуальности данных.
- Учитывать пагинацию и ограничивать объём выборки.

## 7. Тестирование и статусы

- Автономные тесты не должны требовать установленного ядра БУС, если тестируется чистая логика.
- Интеграционные тесты с БУС хранить отдельно и явно обозначать требования к окружению.
- Проверять успешные сценарии, граничные значения и отказ в доступе.
- Для исправления уязвимости обязательно добавить регрессионный сценарий.
- CI и локальные проверки фиксировать в README или отчёте.
- Статус Bitrix Verified допустим только после проверки на реальном ядре БУС; заглушки не считаются такой проверкой.

## 8. Запрещённые практики

- Копировать старые сниппеты без ревью.
- Считать наличие check_bitrix_sessid() достаточной проверкой права на объект.
- Использовать клиентские ID без проверки принадлежности и допустимого типа объекта.
- Выполнять необратимые действия при подключении PHP-файла.
- Вшивать ID пользователей, платежей, доставок, инфоблоков, домены и секреты в код решения.
- Объявлять решение проверенным без воспроизводимого результата.
